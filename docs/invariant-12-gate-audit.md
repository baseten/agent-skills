# Invariant 12 gate audit — every condition, every consumer, one pass

Deliverable of [issue #29](https://github.com/baseten/agent-skills/issues/29), part 2. Audited 2026-08-28, against the repository state after PR #27 and PR #28 merged.

## Why this audit exists

Seven Codex review rounds on [PR #27](https://github.com/baseten/agent-skills/pull/27) produced thirteen findings, ten of them on the merge path, and all ten the same shape: an assumption the gate's author could make for `backlog-orchestrator` that silently does not hold standalone. The gate was written for a world with a validated DAG, a preflight, a ranking step, and a tranche-wide view; `implement-issue` has none of those. Each round discovered one more missing supplier reactively. This audit walks the whole gate once instead.

**Method.** Take invariant 12's gate condition by condition — plus its implicit suppliers — and for each condition and each consumer that can reach the gate, answer one question: *what supplies this here?* Three possible answers:

1. **supplied identically** — the condition reads the same from any run (durable forge/tracker state);
2. **supplied by a different mechanism** — the consumer has its own machinery for the same condition;
3. **not supplied at all** — the defect class every reactive finding fell into.

**Consumers.** Every skill that can reach a gate-authorized merge: `backlog-orchestrator` (BO) and `implement-issue` (II). No other skill evaluates the gate — `merge-stack` executes merges under a caller's authorization and performs its own readiness refresh, but never opens the gate itself.

**Closed examples pattern-matched against**, all from PR #27: gate inputs did not exist before the summary ran (`da05c3e`); walkthrough rulings reached the gate untranslated (`8b8d8a7`); settle-phase outcomes re-entered the settle phase (`da974c1`); evidence freshness did not survive a draft→ready transition (`7d0a96f`, `6166a3e`); `merge-stack` was not required where the gate was reachable in II (`7d0a96f`); dependency completeness had no gate condition standalone (`2550206`).

## Findings and their fixes

Three cells came back **not supplied at all**. All three are fixed in the change this document ships with.

### Finding 1 — settle-originated `IN_FLIGHT_FIX` had no compliant repair path (row 3, both consumers)

Issue #29 part 1, reported by Codex on PR #27 round seven, pre-existing and shared rather than introduced there. `summarize-tranche` can derive an `IN_FLIGHT_FIX` solely from durable evidence that is neither CI- nor review-shaped; both callers instructed a repair dispatch; `repair-pr` accepted only `ci` and `review`, each requiring its corresponding evidence, with budgets per type. A settle finding with neither a failing check nor a thread named no compliant invocation and no counter — and both callers require `repair-pr`, so the documented action point forced a block or an improvisation.

**Fix:** `repair-pr` gains a third repair type, `finding`, taking the summary's action point or the recorded walkthrough ruling verbatim as its evidence — the way `ci` takes logs and `review` takes threads — under the same bounded one-pass contract, with `NO_CODE_CHANGE` (no cycle consumed) for a finding a later push already mooted. The budget is a new per-PR key, `finding-repair-cycles` (default 2), deliberately its own counter rather than a draw on `review-repair-cycles`; the argument for that choice — the two budgets bound different loops, and one counter lets either starve the other, against the real but thinner config-surface objection — is stated once in `backlog-orchestrator`, *A settle finding is the third repair shape*, and both callers' `IN_FLIGHT_FIX` sites now name the type and the budget instead of "the repair" and "budget".

### Finding 2 — dependency completeness at BO's gate under `dependency transport unavailable` (row 12, `backlog-orchestrator`)

The preflight's acceptance of `dependency transport unavailable` is a dispatch decision, argued as such (blocking on it halts every GitHub backlog permanently). Nothing carried a merge-time consequence: the warning raises no `NEEDS_USER`, so the gate's outstanding-item test never saw it, and a cloud-container GitHub run with `auto-merge` opted in would have merged PRs built on a prose-only dependency view — while `implement-issue` held its gate on exactly this condition, so the shared `auto-merge` key meant two different assurances depending on which skill evaluated it, the precise drift the shared-grant argument forbids.

**Fix:** invariant 12's gate gains the condition once — *the dependency view the PR was built on is proven complete or explicitly answered for* — with *Merge behavior* naming each consumer's supplier: BO's validated preflight discharges it for boundaries with a working transport, `dependency transport unavailable` is proceedable for dispatch and not discharged for merge (both premises of the dispatch acceptance stop at the gate: holding a merge degrades to the default no-merge behavior rather than a dead run, and the gate is precisely where the person between the PR and the default branch is removed), and II's supplier is core's completeness report. II's *Merge* paragraph is re-pointed at the gate definition — its previous "invariant 12 never tests for it" framing would have become false — keeping its mechanics intact.

The hold's **discharge answers for the whole view, because completeness is what is unproven** (tightened on Codex's round-one review of this change): one user-confirmed edge cannot discharge it — under this boundary caller context is a targeted answer whose omissions prove nothing, and the known-true-case proof needs a working transport to observe the edge through — so the two real discharges are a run whose transport can read the graph and prove the boundary, or the owner explicitly answering for the view itself, recorded as a ruling that retires the hold the way the translation rules retire a constraint, never opening the gate.

### Finding 3 — `merge-stack` not required where BO's gate is reachable (row 13, `backlog-orchestrator`)

PR #27 closed this for `implement-issue` (`7d0a96f`) and not for the orchestrator, whose parent required-skills list never named `merge-stack` and whose preflight never checked it.

**Fix:** the parent layer now requires `merge-stack` wherever any repository's resolved `auto-merge` leaves the gate reachable, checked at the run's first preflight where policy is read. The unavailable case is handled asymmetrically from II, and the asymmetry is argued in place rather than left as drift: II returns `BLOCKED` at an invocation its user is typically attending and loses one issue's worth of nothing, while blocking a tranche would trade twelve issues of authorized implementation for the tool their optional final step needs — so BO applies a documented default instead: the gate is unreachable for that run (the narrowing direction an invocation is always permitted), reported at preflight and at the gate, with a closing `NEEDS_USER` naming the missing skill. Both consumers fail closed; neither improvises a raw merge. The same paragraph also states the previously unwritten rule for other parent-required settle skills: unavailable means that step's outputs are absent and reported, never improvised — and a gate whose summary inputs never existed stays shut.

## Notes on cells that passed with nuance

- **Row 7 (recovery refs) in II** — the *test* is supplied identically because the refs are durable remote state, but the *ender* machinery is BO's, applicable by reference. A standalone run that adopts a branch carrying a stale ref holds the gate and reports; reconciling the ref is recoverable work, and the failure direction is a withheld merge. Accepted as-is.
- **Row 2's tranche-wide reach in BO** — a translated disposition ruling ("hold PR A") becomes a `MERGE_RISK`-shaped constraint, and the gate's tranche-wide test then holds every sibling's merge, not only PR A's. That is the tranche-wide clause working as written ("anywhere in the tranche, not only on that PR") — conservative by design, not a defect.
- **Row 14's publish flip** — marking a draft ready is an authored forge write performed by the consumer itself (deliberately: `merge-stack`'s readiness check stops on drafts, so the publish precedes its invocation). It is covered by *Posting identity*'s blanket rule over every authored write; no per-site restatement is added, per that section's own instruction.
- **A degraded (coverage-finding) PR can pass the gate** — its `Part of:`/`Blocked by:` linkage keeps the issue open, the prerequisite is filed, and merging reviewed, green, correctly-linked partial work is consistent with the completion semantics. The gate guards the merge's safety, not the issue's completeness; row 15's proviso guards the latter.

## Scope

The gate and its suppliers only, per issue #29: every consumer that can reach a gate-authorized merge, currently `backlog-orchestrator` and `implement-issue`. This is not an open-ended review of every skill. Rows may be added as the gate gains conditions or consumers; a new consumer of `auto-merge` owes this table a column before it ships.
