# Review trigger

This is the rule other skills mean when they cite *review trigger*: which convention a PR's automated review trigger follows, what it is and from which account, how its taking effect is confirmed, what a refused round and a stalled one are, and when review is triggered again.

**It is not a skill and nobody invokes it.** It is a shared rule, held once at
`rules/review-trigger.md` and copied into each skill that applies it by
`scripts/refresh_shared_rules.sh`. A skill reads its own
`references/review-trigger.md`, which works after `bootstrap.sh` has
installed only that skill's directory, and travels with the skill if it is
moved into a plugin. Edit the source, never a copy; check_shared_rules.py fails if a generated copy diverges.

It governs every trigger a skill issues — the first one after a PR is created, a re-trigger after a repair, and a trigger on a PR the run never created, such as a bot's. **Which of those a skill issues is that skill's own; what each one is, how its taking effect is confirmed, and the conditions every re-trigger is bounded by, are this rule's.**

## The convention

Use the trigger the repository documents in its own `CLAUDE.md`/`AGENTS.md`; with none, default to `@codex review` where that convention is supported.

## Documentation-review routing

- **Where the repository documents a documentation-review convention and the PR's diff qualifies, that convention is the trigger** — that convention is the `review-docs` skill, **invoked on the PR rather than posted as a comment**, so confirmation that the trigger took effect is its completed pass and the review comment it posts, not a reviewer arriving. On a **documentation-only** diff it runs *instead of* the ordinary review trigger; on a **mixed** diff, only where the repository documented the mixed case as well, and then *in addition to* the ordinary trigger, which is still issued in full. `review-docs` owns the documentation test, its rounds, and what it reports — do not restate them here. Cannot tell whether a path is documentation → it is not, and the ordinary trigger stands alone.
  - **This governs re-triggers as much as the first trigger**: a routed convention is **re-invoked, not re-posted**, so there is no trigger comment and **no trigger author to select from the posting-identity map** — the selection step a re-triggering skill performs has nothing to select and is not skipped by oversight. `review-docs` bounds its own rounds and declines past them; **a decline is that convention's completed answer to a re-trigger**, not a trigger that failed, and is recorded with the residue it returned.
  - **Skill unavailable → the ordinary trigger stands alone, and report that it did.**
  - **There is no arrival window to wait out and no refusal path to reissue through**, so a routed pass that did not complete is an error to surface now — never a PR left unreviewed-pending against a reviewer that was never going to come.

## The trigger comment

**The trigger comment must come from the invoking user's own account, or the convention does not fire, and it carries the trigger text and nothing else — no attribution footer.** Both are exemptions from rules that govern every other authored write, and each is stated once where it lives: the authorship exception, with how the trigger's author is selected, in `references/posting-identity.md`, *The review trigger*; the footer exemption, with the reason to state for it, in `references/authored-write-form.md`. Apply them from there; do not restate them. **Both exemptions reach the trigger comment alone**: every other authored write the triggering skill makes follows both rules as written.

## Re-triggers

- **The trigger is the only review action a run takes: it never requests, re-requests or removes a human reviewer on any PR** — including once their changes-requested review is fixed. Code owners a forge requests for a ready PR are the forge's act: the run neither adds nor removes them, and reports any request at `settle-and-merge` step 7, or in the caller's output where no settle follows.
- **Do not re-trigger merely because subsequent CI checks run.**
- **Re-trigger the automated review convention after every substantive push this workflow makes** — a repair pass that pushed, a released head, a reconciled capture, a substantive caller push — whether or not the repository's docs mention re-review, **and never after a mechanical push.** `references/mechanical-pushes.md` is the test for which is which; apply it from there. **Nor after a pass that pushed and returned `FAILED`**: its head is known red and the PR `needs-user`, so a review of it is wasted. The rounds stay bounded because every push that re-triggers is either budgeted — a repair cycle of its type — or paced by a person or caller: the invoking user's own rounds, a caller's push. **One exception, under `ci-mode: deferred` only:** a round owed on a head the supervisor holds a refresh owed for is not requested there; it is held, and requested on the refreshed head once the refresh lands, mechanical or not, so the final review covers the head that merges and neither review nor CI runs twice.
- **A reviewer that reviews every push on its own takes no trigger** where the repository's own configuration says so — its `CLAUDE.md`/`AGENTS.md`, or the reviewer's trigger configuration committed in the repository. Confirm instead that a review arrives on the new head within the window (*Confirming a trigger took effect*), and trigger once if none does. A bot's description of itself in a PR comment is not that configuration; cannot tell — the sources disagree, or say it loosely — → trigger.
- **A round stalled in progress is re-triggered once** (*A stalled round*); an unanswered round this workflow requested is otherwise requested again only where *Confirming a trigger took effect* reissues it, or an owner reply chose it from a stalled round's options.
- **Never re-trigger a round recorded `refused`** (*A refused round*), **nor in a repository where triggering was suppressed** (*Confirming a trigger took effect*).

## Confirming a trigger took effect

**Issuing the trigger is not the end of that step.** Whichever skill supervises the PR confirms it took effect — and confirms it against the artifact, not against the absence of one (the *absence is not a verdict* shared rule): a review from the repository's automated reviewer materializes within a bounded window, and the reviewer does not instead answer indicating it is not configured or not authorized. Verify per attempt, on every PR.

**Read the posted trigger back, and compare its body with the trigger text.** A transport can add to what it was given — an MCP server appending its own attribution footer is the case observed — and a trigger carrying anything beyond the trigger text may not have fired (*The trigger comment*). Record the pair `appends footer` on its map entry (`references/posting-identity.md`, *The review trigger*), and report the trigger as possibly not fired, naming the transport. **Through such a transport, a trigger is confirmed only by the reviewer answering it** — a reaction or reply to the trigger comment, or a review on the head where nothing else requested one — and never barred by the read-back alone. A check run alone confirms nothing: it can belong to a round something else requested. The altered body stays on the PR's timeline, so a later pass or a restart that confirms the trigger reads it again rather than taking the trigger as `verified` without that answer. **It is not yet a failure, and it is never re-posted blindly**: a second trigger on the same head is a second review request, not a correction, and *A stalled round* is the one made for a request the provider took up. Before deciding it failed, establish whether the repository also requests review on the event that produced this head — `pull_request: opened` for the first trigger, `synchronize` or a push after a repair push — through a workflow or the reviewer's own configuration, since that round arrives either way, and let the window run: a review arriving on the head answers the question. Only once the window has elapsed with no such answer and nothing else requesting one — the one case where an elapsed window is evidence, because the read-back already showed why the convention may not have matched — bar the pair from further triggers on its map entry and reissue it once — never where its round already carries its one further request (*A stalled round*), which leaves that trigger reported possibly not fired — from the account the map selects, through a different available mechanism, and read that one back too; where no mechanism posts the text alone, it is posting identity's provisional *Unavailable for now* — a transport limit, never the repository-wide suppression below.

**An elapsed window is not a refusal**, the read-back case above apart. A reviewer that is merely queued or slow leaves the PR unreviewed-pending, reconciled through ordinary supervision and visible as such in the run's output — one showing its in-progress signal on a head its round spans past 20 minutes apart, which takes *A stalled round*'s one re-trigger; only an explicit not-configured/not-authorized response marks the trigger unavailable.

**A refusal of the write** is first evidence of the wrong write path, not of insufficient authority — this is about the comment failing to post, and it does not reach a reviewer's answer that it is out of budget, which is a successful write and a refused *review* (*A refused round*). Where the platform offers more than one way to perform the write, reissue the trigger once through a different available mechanism before drawing any conclusion. Where the platform exposes only one write mechanism, the available paths are already exhausted. Do not otherwise repeat the same write path.

Only once every available path has failed, record it as `NEEDS_USER`: surface once, with the affected PRs, that review could not be triggered, and stop issuing the trigger for the remainder of the run in that repository. One escalation per affected repository, not one per PR; suppression is scoped to the repository that refused, because review configuration is repository-specific. Never conclude from a refusal alone that review cannot be triggered from this run at all — that conclusion is cheap to draw, hard to disprove afterwards, and costs precisely the reviews it skips.

## A refused round

**A reviewer that is *triggered* — as against a review skill that is invoked — and answers saying it is out of budget has refused, and a refusal is neither a clean review nor a trigger to reissue.** An invoked skill declining because its own round budget is spent is the opposite case (*Documentation-review routing*): that review happened and its answer is that it is over. Record the round as `refused` with what the reviewer said and when — a quota, a window, a reset — and hold the PR: a merge gate wants every required round *completed*, and a round that did not run is not a round that found nothing (the *absence is not a verdict* shared rule). The trigger write succeeded, so the trigger itself stays `verified`; the refusal is on the round.

**Do not put the retrigger on a schedule, and do not reissue it on a later pass.** Establishing that the provider is back is only possible by asking it, so each attempt is another review request, and a queued run of them is answered all at once when the budget resets — one observed run put twelve rounds on a PR whose cap is two, that way (the *establish it, do not assume it* shared rule, *Establishing it by trying it costs what the attempt costs*). Re-issuing on a supervision wake, at a re-adoption or at a restart is the same scheduled retry, arrived at without anyone arming a job. A trigger already posted stays posted and is answered when the provider returns; report the PR as owing a round and let the owner decide whether to wait or to lift the cap. A round the provider took up and has not answered is not refused, and is *A stalled round*'s, below.

## A stalled round

**An automated review showing its provider's in-progress signal on a head its round spans for more than 20 minutes is stalled, and is re-triggered once — never again for that round.** It is the owner's ruling.

- **The in-progress signal is the provider's own mark that it took the request up and has not answered it**, authored by the provider's account: a reaction on the trigger comment, or its own check run or commit status in an in-progress state on a head the round spans (the *CI and review verdicts* shared rule, *A review is clean*, says which) — as its convention reports it; Codex's reaction to its trigger is the observed case. **Not stalled**: no signal at all, which is *Confirming a trigger took effect*'s window; a state the provider marks queued rather than running, since a re-trigger only joins the queue; a signal for a head the round does not span; a request already answered by a review or reply, whatever mark remains.
- **The 20 minutes run from the signal's own timestamp where the forge records one, else from the first read that saw it** — never from the trigger, which would count the queue. They are a threshold a read observes, not a timer: nothing is armed or shortened for them, and the first pass that reads the PR past it — on an event, or the check-in the *wake budget* shared rule schedules — acts.
- **Only a round this workflow requested qualifies**: a convention it performs, on a head whose round it owes — a reviewer that reviews every push included. Never a round `refused` or `deferred`, one owed after a head move nobody here made, one a caller performs or one routed to a review skill, which has no queue; nor where triggering was suppressed.
- **The re-trigger is an ordinary trigger**: the convention's text, from the account the map selects, read back and confirmed.
- **It is the round's one further request.** A round already carrying a further trigger — a second trigger on any head the round spans, the read-back reissue or one anyone posted, the owner included; or any trigger for a reviewer that reviews every push — gets none. Count it from those heads' timelines at the decision, whatever a record or an input says, record it with its head and time, and report it.
- **Every request on the heads one round spans is one round**, counted once: any one's review establishes the round, and every thread any of them roots is feedback (the *CI and review verdicts* shared rule), so a late answer with findings makes it not clean. **A request is unanswered until the provider answers it** — a review, a refusal, or a not-configured or not-authorized reply; never an acknowledgement or progress note — whatever mark remains after one, and **one that shows its provider's mark, running or queued, or is a trigger still inside its confirmation window, keeps the review from clean** (*A review is clean*, item 1, which the merge gate reads). **Its own time** is 20 minutes past that mark, or its confirmation window elapsed with no mark; an answered request has had it. `waiting` on it until then.
- **A round still held once its one further request has had its own time** — no answer on it, or a request on it unanswered under a mark, running or queued, beside an answer — **is stalled after its re-trigger**: report it, naming every request and since when, and **raise it to the owner as a `DECISION` offering: merge without the unanswered request; re-trigger once more; or leave it waiting** — posted on the PR as a supervision comment, its write id recorded, so the PR is the item's site. Nothing else requests that round again — no later pass, wake, re-adoption or restart. **It holds the merge, and only a request answering or an owner reply choosing one of those options changes that** — what counts as one is `backlog-orchestrator`, *Arming the wait when nothing is in flight*, and no trigger comment or other write this workflow posted is one; the walkthrough's ruling recorded at the site is its attended form (`settle-outstanding-decisions`), the same choice as any reply it retires the item from. Chosen: **merge without** releases this hold, and stands in for the round's completion, for the requests the item named on the heads the round spans — and nothing else: every other gate condition governs, an outstanding `DECISION` among them, so an unattended reply reaches the gate once the walkthrough retires the item; a gate with no walkthrough never takes it, and leaves that merge to the owner; a head move needing a new round ends it; **re-trigger once more** is the owner's request, not the round's allowance spent twice: the next pass that reads the site posts that one trigger as an ordinary one — one per item, none where the timeline already shows a trigger after the choice; the hold stands until a request answers, and a round still held once that trigger has had its own time is raised again the same way; **leave it waiting** keeps the hold until a request answers, and raises nothing again. It is surfaced like a refused round: it holds its PR's merge by item 1, and the wave's while its `DECISION` is outstanding, never the PR's finishing.
- **A head move that needs a new round resets this allowance and nothing else**: the new head's round is requested, or not, by *Re-triggers*, and carries its own one. A move the round carries forward across resets nothing — the round and its spent allowance travel together, so a mechanical push never buys another.
