# Notes — review-trigger

Reasoning for `rules/review-trigger.md`. Deliberately *not* bundled into
each skill: a copy of this per consumer would be design history with no reader,
and the audience for it is a person editing the rule, who has this checkout.

Moved here with the rule itself, from `create-pr/NOTES.md` — *The review trigger's authorship*, *Routing documentation PRs to a review skill* and the trigger half of *The PR body's brevity, and the trigger's second exemption* — when the rule was split out of `create-pr` (#142). "This skill" and "this step" in the moved entries are `create-pr` and its *Automated review trigger*, as they stood when the entry was written.

**Why this is a shared rule (#142):** four skills issue a trigger under it. `create-pr` issues the first one after creation. `backlog-orchestrator` and `implement-issue` re-trigger after a repair "where repo convention requires it", and `backlog-orchestrator` also issues an untriggered PR's trigger at adoption. `npm-dependency-upgrade-orchestrator` posts one on PRs that never went through `create-pr`, such as a bot's. `create-pr` said as much itself — every caller that re-triggers inherits it — so three of the four applied a rule that lived in the fourth, and the npm orchestrator's pointer into it ran into a skill it does not compose for that PR at all. `settle-and-merge` gates on every round the PR's routing requires, so it reads the routing too and carries the rule for it. What stayed in `create-pr` is what only it does: the first trigger after creation, and the deferred trigger a caller can ask it for.

**Why the general rules name this rule path-neutrally — "the *review trigger* shared rule" — rather than cite `references/review-trigger.md`.** `rules/posting-identity.md`, `rules/authored-write-form.md` and `rules/review-feedback.md` mention the trigger convention's owner in passing, and each is carried by skills that never trigger a review — `create-pr` said it owned the convention, and each of them said so too. A `references/` citation there would make every one of those skills carry this rule, and the mechanical-push test it cites, by derivation — nearly every skill in the repository, for a pointer none of them needs in order to act. Nor do they write `rules/review-trigger.md`: that path does not exist in an installed skill, so the name is path-neutral and reads right both installed and in this checkout. `review-docs` names it the same way, for the same reason. Every skill that does trigger carries this rule itself.

## The convention and the account

The trigger comment is the one post exempted from the posting-identity rule because there its authorship is **functional, not cosmetic**: authored by anything but the invoking user, the repository's review convention silently does not fire — nothing refuses it, so the run waits out a review that was never going to arrive. `rules/posting-identity.md` states the rule once, including the bootstrap for a fresh run's first trigger; this rule carries only the exception, not a restatement.

The trigger comment's exemption from the footer is the same argument as its exemption from the posting-identity rule: the comment must match what the convention matches on, and a convention that does not fire fails silently. Two exemptions, one cause — which is why they are stated together.

Under the approval test that now governs the footer (`rules/authored-write-form.md`), the trigger has **two** independent reasons to carry none, and only one of them is worth stating. The functional one — it must read exactly as the convention expects — is the one that fails silently and the one a reader has to know. The approval test on its own would ask for a footer here, since nobody reads a trigger comment before it is posted; the exemption overrides it. Stating both would invite someone to satisfy the weaker reason and think the rule met.

## Documentation-review routing

Added with `review-docs` (Sept 2026). The routing was placed in `create-pr` rather than in a repository list inside `review-docs` because `create-pr` already reads `CLAUDE.md`/`AGENTS.md` for review-trigger conventions — the decision point existed, and a list of repository names inside a general skill would be a second place to maintain, invisible to the repositories it governed. The rule still reads the convention from the repository's own docs, which is why it names them.

**Why the routing governs re-triggers explicitly rather than leaving them to the first sentence.** Four sites re-trigger review "where repo convention requires it" — two in `backlog-orchestrator`, two in `implement-issue` — and three of them additionally say to select the trigger's author from the posting-identity map. Under a routed convention there is no comment and therefore no author to select, and a reader finding a step it cannot perform will either improvise a comment or skip the re-trigger silently. Both are wrong and neither is visible. So the rule says what a re-trigger *is* under a routed convention, and those sites cite it.

**Why an unavailable review skill falls back rather than stopping.** It is the same fail-safe direction as the cannot-tell rule beside it: a PR reviewed by the wrong instrument costs one reading, and a PR reviewed by nothing costs the review. Reported either way, because a silent fallback is how a repository discovers months later that its documentation convention never fired.

**Why every substantive push re-triggers by default (#191):** the rule said to re-trigger after a substantive fix "only where repository convention requires it", while `supervise-prs` said to re-trigger after every pass that pushed. A run that read the rule never re-triggered in a repository whose docs said nothing about re-review, and the merge gate wants a clean review on the current head, so two PRs sat with unreviewed repairs until the owner stepped in. The default flipped, and `supervise-prs` cites it rather than restating it. It costs no unbounded loop (protected rule 5): every push that re-triggers is either a budgeted repair cycle of its type or paced by a person or caller — the invoking user's own rounds, which spend no cycle, and a caller's push — so no budget alone caps the rounds, but nothing re-triggers without one of the two. The trigger is the automated convention only, so rule 4 is untouched. A pass that pushed and returned `FAILED` is the one pushing pass not re-triggered: its head is known red and the PR goes to `needs-user`, so a review there would read code the next repair replaces. **A reviewer that reviews every push on its own** would be asked twice, so it is stood down only on what the repository committed — its docs or the reviewer's trigger configuration — and its review is still confirmed on the new head, with one trigger if none arrives. A bot's comment describing itself is not that evidence: it is the reviewer's claim about its own behaviour, posted where anyone can write, and wrong when the configuration changed after it was posted. `.claude/agent-policy.json` is not among the sources because it has no key for this, and an unknown key fails closed. Cannot tell → trigger, since an extra review costs a reading and a missing one holds the merge forever.

## Confirming a trigger took effect, and a refused round

Moved here from `backlog-orchestrator`, *Implementation worker contract* — the confirmation step, the write-refusal path and the refused round — with the note on confirming a skill invocation (#144). Every skill that issues a trigger under this rule needs to know whether it took effect, and `implement-issue` re-triggered after a repair with no refusal exception at all: a provider that had answered it was out of budget would have been asked again after every later pushed repair.

Added with `review-docs` (Sept 2026). The confirmation step was written for an external reviewer and its whole vocabulary assumes one: an arrival window, a not-configured refusal, a reissue through a second write path, and an unreviewed-pending state for a reviewer that is merely slow. None of those exist when the routed convention is a skill this run invokes — it either ran or it did not, and there is no queue to wait out. The *Documentation-review routing* carve-out that there is no arrival window to wait out is stated there deliberately, ahead of *An elapsed window is not a refusal*: that sentence is the negation-class hazard, and a reader reaching it without the carve-out would park a PR as unreviewed-pending against a reviewer that was never coming.

**Why the trigger's body is read back (#154):** a trigger posted through an MCP server came back with the server's own attribution footer appended, although *The trigger comment* requires the trigger text and nothing else. The server added it; the run never wrote it, so nothing in the run's own view of the write was wrong. Only reading the posted body shows it. It is reported as *may not have fired* rather than *failed* because some conventions match the text within a longer comment and some repositories review on `pull_request: opened` regardless, and the window, not the footer, settles which. Re-posting at once would be the scheduled-retry failure in small: two requests on one head, both answered. The one reissue waits for the window, goes through a different mechanism, and is read back itself. A body a transport altered is a fact about that transport, not about the repository, which is why its dead end is posting identity's provisional unavailability and never the run-long suppression a reviewer's refusal earns.

**Why a declined pass is completed rather than failed.** `review-docs` bounds its own rounds and declines past them, returning the residue. Read through the error clause above it, a decline looks exactly like a pass that did not happen, and this run would surface an error on the one outcome that means the review is finished. The two are distinguished by what comes back, not by whether a comment was posted — a decline deliberately posts nothing.

**Why confirmation is owed at all:** a trigger that silently no-ops is worse than one that fails loudly, because the run then reports PRs as reviewed and clean when nothing reviewed them.

**Why the run never touches a human reviewer (#163, owner's ruling 2026-09-30):** a run re-requested review from a person after fixing their changes-requested review, because the platform's session posture said to and nothing here said otherwise. Asking a person for their time is theirs to be asked by the owner, not by an automated loop; the automated trigger is the one review request a run's budgets bound.

**Why an unavailable review skill falls back to the ordinary trigger:** the same fail-safe direction as the cannot-tell rule — a PR reviewed by the wrong instrument costs a reading, a PR reviewed by nothing costs the review.

**Why a refused write path is not retried:** it will not start working on the next PR, and each failed attempt leaves trigger and refusal comments behind on the PR.

**Why code-owner requests on publish are named (#163 review):** a forge can request code owners on `ready_for_review` by itself, which reads exactly like the reviewer request the run is banned from making; saying whose act it is keeps the run from undoing it and keeps it visible. Since #190 a PR the gate may merge opens ready, so the same request can come at creation; it is the same act and named once more for that reason.

**Why confirmation is per attempt, on every PR:** one review arriving elsewhere in the run is not evidence the trigger works.

**Why a footer-appending transport is confirmed by a run, not barred (#183):** a read-back with an appended footer shows the body differs, not that the reviewer ignored it. Barring on it alone can push every later trigger off a transport that works, which in some sessions is the only one that posts. Seeing the reviewer's run start is direct evidence; the read-back is only a reason to look for it.

**Why a check run alone does not confirm a footer-appending trigger (blind audit of #184):** a check run on the head can belong to a round a workflow requested on the push, so it says nothing about whether this trigger matched. A reaction or reply to the trigger comment answers that comment; a review counts only where nothing else requested one.

## A stalled round

**Why a stalled round is re-triggered once (owner's ruling, Oct 2026).** In a `backlog-orchestrator` run two Codex reviews sat in progress on their PRs' current heads for 35 to 60 minutes. The rule as it stood read that as a slow reviewer — unreviewed-pending, and a second trigger on the same head a second review request — so the run waited and reported, and only the owner posting `@codex review` again by hand got both reviews through. The ruling reverses that part of the same-head rule for this one case: past 20 minutes in progress, the run re-triggers once, and never again for that round. Everything else stands — no scheduled re-trigger, no re-trigger on a refused or completed round, and a head move that needs a new round resets only this allowance.

**Why this is not the twelve-round failure.** That run re-asked a provider that had *answered* it was out of budget, on every wake, and every queued request was answered at once when the budget reset (*A refused round*; the *establish it, do not assume it* shared rule). A stalled round has taken the request up and not answered; the condition is a positive signal from the provider, never the absence of one, and the allowance is one per round, counted off the timeline so a restart does not repeat it. The heads themselves are bounded by the repair budgets or paced by a person or caller (*Re-triggers*), so the extra requests are too — protected rule 5 holds without a budget of its own. At most two trigger comments are ever posted against one round on the run's own initiative — a request the repository's own workflow or the provider's configuration makes is not a trigger and is not counted — and the cost of the second answering as well is a duplicate review, read as one round.

**Why protected rule 4 is untouched.** Rule 4 forbids requesting, re-requesting or removing a *human* reviewer: a person's time is the owner's to ask for. The stall re-trigger is the automated convention's trigger comment, the one review action a run takes, and asks no person for anything.

**Why the signal is the provider's own, and why queued is not stalled.** "Running" has to be something a read can establish, and the providers differ in how they show it — a reaction on the trigger comment, a check run, a commit status — so the rule names the shape and leaves the instance to the convention, with Codex as the observed case rather than the definition. No signal at all is the old question of whether the trigger fired, which has its own window and its own single reissue; folding it in would make every slow provider a stalled one. A provider that distinguishes queued from running is telling the run it has not started, and a second request joins the same queue behind the first. A signal still showing after the provider answered is a mark nobody cleared, so the answer, not the mark, decides.

**Why the clock starts at the signal.** Measured from the trigger, a provider with a long queue would be re-triggered for its queue rather than for stalling once it started. Where the forge stamps the signal that time is used; where it does not, the first read that saw it is the conservative bound, since it can only start the clock late.

**Why 20 minutes needs no timer.** A stalled review produces no event, so the observation is made by whatever pass next reads the PR — the subscription's other events or the backstop check-in, whose backoff starts at 20 minutes (`rules/wake-budget.md`). Arming or shortening a wake for this would be a second watch on top of the one the wake rule allows, and the cost of a later observation is only that the re-trigger comes later.

**Why any second trigger on the round spends the allowance, the owner's included.** The rule exists to stop requests stacking on one head, and a trigger the owner posted by hand, or the read-back reissue, is a second request exactly as the run's would be. It is also the only reading a restart can make: the timeline shows two triggers on the head, not who intended which. Counting by the triggers posted is the conservative direction.

**Why two answers are one round.** The re-trigger requests the same review of the same commit, so a second review is a duplicate, not a second round: it does not count twice toward `review rounds completed` and does not need the first to finish. Read through *CI and review verdicts*, either summary establishes the head was reviewed and every thread either one roots is feedback, so a late answer that found something still makes the round not clean.

**Why a round still stalled after it is reported, not re-triggered.** A provider that did not answer two requests is not going to answer a third sooner, and a third is where the once-per-round bound would start to become a schedule. **The threshold applies to the re-trigger too (pre-merge audit of #200):** read on the pass straight after it was posted, the original's signal is still showing, so without one the round would be declared stalled before the second request had any time. It is surfaced rather than `waiting` for the reason a round owed after someone else's push is (`skills/supervise-prs/NOTES.md`, *Outcomes*): nobody here may request it again, so waiting on it would only run the wake budget out. It holds the merge, and the owner's options are offered as a `DECISION` (below).

**Why a request still in progress holds the merge although the round is complete (contradiction pass before the first push).** Either answer completes the round, so a clean early answer would otherwise let the gate open while the other request could still land findings on the same commit. The gate fails closed (protected rule 8), so the open request holds the merge, surfaced, until it answers or an owner reply chooses to merge without it. **Why the hold is stated in the verdicts rule (pre-merge audit of #200):** it was first written here and in `supervise-prs`, and neither merge gate reads either — `settle-and-merge` and the dependency orchestrator's merge read *A review is clean* and whether the round completed, and by this section's own words it had. Stated in item 1 of *A review is clean*, it is where both gates already look, and it holds for any second request on the head, not only a stall's. **The open request gets its own time before it is surfaced (contradiction pass of the same audit):** surfaced at once, a PR could finish a minute after its re-trigger was posted, and a wave settle, while that request could still land findings; it is `waiting` until the same threshold a re-trigger gets has passed.

**Why the allowance is counted from the timeline at the decision.** Callers pass counters and trigger states that carry no stall field, and *Adopt* rebuilds only where none were passed, so a record-only count would let a caller-loop pass spend the allowance twice. The timeline is the one source every pass reads. A reviewer that reviews every push takes no first trigger, so any trigger on its head is already the further one.

**Why a carried-forward round still qualifies.** Under `ci-mode: deferred` a mechanical base update moves the head while the round on the earlier head still counts; reading only the literal current head would make that round impossible to re-trigger. **Why the allowance travels with it (pre-merge audit of #200):** as first written, any head move reset the allowance and only the new head's triggers were counted, so each mechanical base update bought the same stalled round another request — bounded by mechanical pushes, which no budget counts, against *Re-triggers*' never after a mechanical push. The allowance is the round's: a move it carries forward across resets nothing, and its triggers are counted on every head it spans. **Nor does the read-back reissue add one:** a stall re-trigger whose read-back shows an appended footer would otherwise be reissued once its window elapsed, a third request on one head; the reissue is not made where the round has spent its further request, and that trigger stays reported possibly not fired.

**Why a stalled round is raised as a `DECISION` with three options (owner's ruling, round 2 of the pre-merge audit of #200).** As first written the hold had no exit but the request answering, and the notes and two scenarios said "or the owner rules" with nothing in the contract to say what a ruling was. The owner ruled that the exit is protected rule 3's: an owner reply choosing an offered option — merge without the unanswered request, re-trigger once more, or leave it waiting — read the way `backlog-orchestrator`, *Arming the wait when nothing is in flight*, reads any reply to a held item, or the walkthrough's recorded ruling. It is stated in *A review is clean*, item 1, because that is the read both merge gates make, and in the gate's round-completed condition because a stalled round may have no answer at all. **A re-trigger the owner chose is not the allowance spent twice:** the once-per-round bound limits what the run asks on its own initiative, and the owner asking is what the bound reserved; each further one costs an owner reply, so nothing loops. **Merge without releases only what the item named**, as the dependency-view discharge does in `settle-and-merge`: the gate's other conditions still govern, the item is retired by the walkthrough as any `DECISION` is, and a new round ends it.

**Why the item is posted on the PR, and why an unattended choice to merge waits for the walkthrough (contradiction pass of the same fix).** A `DECISION` that lived only in the supervisor's report had no site: the reply watch reads only where an item lives, an unattended settle's decline relies on decisions being durable at their sites, and a later run could not find it. Posted as a supervision comment, it is footered and its write id recorded, so the owner's reply is told from the run's own posts (protected rule 2). The gate holds while any `DECISION` is outstanding, and an unattended reply releases dispatch only (`backlog-orchestrator`, *Arming the wait…*), so merge without takes effect at the gate once the walkthrough retires the item — the same path every owner answer to a held item takes; re-trigger once more needs no such step, since a trigger merges nothing. The item holds the whole wave while it is outstanding, as every `DECISION` does; narrowing that to its own PR, as body-drift `MERGE_RISK` is narrowed, would change the gate and is left to the owner.

**Why the hold reads every head the round spans (round 2 of the same audit).** The allowance was moved to the round in round 1, but the hold still read "that head": under `ci-mode: deferred` a mechanical update after a clean answer moves the head, item 1 matches the earlier head by carry-forward, and a request still running on that earlier head was no longer asked about — the gate opened while it could still root findings on code identical up to mechanical pushes. The deferred-CI base update and the gate's own overlap update both reach it without anyone doing anything wrong. The span is defined once, beside the carry-forward rule in *A review is clean*, and every statement of the hold and the allowance reads it.

**Why a queued or unconfirmed request holds too (round 2 of the same audit).** The hold first counted only a request showing its running signal, and a queued state is by definition not that, so a re-trigger sitting in the provider's queue let a clean answer to the original open the gate two minutes later, and the re-trigger then answered on a merged commit. Any provider mark, running or queued, says the request was taken up and can still answer; a trigger with no mark yet may not have fired, so it holds only through its confirmation window — past that with nothing, it is *Confirming a trigger took effect*'s, not a request in flight.

**Why a trigger is never a choice, one trigger per item, and what an answer is (blind audit after the fix).** Triggers are posted from the owner's account with no footer, so read as replies they would be the owner choosing "re-trigger once more" again on every restart; the run's own writes are excluded, and the choice is counted per item, so a walkthrough recording a ruling from a reply the owner already gave is the same choice, not a second. A provider's acknowledgement or progress note is a reply but not an answer: read as one, it released the hold before the review it announced arrived. A trigger that never showed a mark stops holding once its confirmation window has elapsed — the case *Confirming a trigger took effect* reads as possibly not fired; holding on it instead would raise a `DECISION` every time a first trigger failed and its reissue answered. That is a deliberate trade, and the owner's to revisit.
