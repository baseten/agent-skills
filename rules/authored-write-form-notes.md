# Notes — authored-write-form

Reasoning for `rules/authored-write-form.md`. Deliberately *not* bundled into
each skill: a copy of this per consumer would be design history with no reader,
and the audience for it is a person editing the rule, who has this checkout.

Why the rules in `SKILL.md` are shaped the way they are. Moved here with the
rule itself, from `backlog-orchestrator/NOTES.md`, where it was reasoning about
a section that no longer lives there.

Some of it argues against the posting-identity rule, now `rules/posting-identity.md`
beside this one. The two are read together where they interact.

**Why the footer exists at all, given Posting identity:** that section makes the run *report* who its writes appeared to come from; it does nothing to make a reader of the forge able to tell. On its degraded path — the common one — every comment carries the invoking user's login and `author_association: OWNER`, and nothing in the comment marks it as agent-written. A reviewer reading a reply in the owner's voice has no way to know they are not talking to the owner, which is the same attribution-honesty problem one layer out, and the one a footer actually closes.

**Why the footer marks unread writes rather than every write (the owner's ruling, Sept 2026):** the first version of this section stamped everything the run typed. A marker on every write carries no information. The reader who matters is deciding how much scrutiny a write has already had, and a blanket banner cannot separate the two cases that differ most — an unedited automated reply, where they should read closely because nobody has, from a body its author drafted with an agent, edited, and posted under their own name. So the test is whether this run obtained the person's approval of *this exact text* before posting it.

Three things made the blanket version actively wrong rather than merely uninformative. Attended work is **already** attributed durably: commits carry `Co-Authored-By: Claude`, so a banner on the description adds nothing a reader could not get from the history. A `Generated by Claude Code` stamp on a description its author owns **misstates authorship in the other direction** — and it invites a reviewer to skip the description, which is precisely the failure the brevity rules exist to prevent (see the entry on where the PR-body numbers come from). And the avatar argument above, which is the reason the footer exists, is an argument about the **unattended** case only: it says a reader cannot tell that nobody reviewed this text. It does not reach a write a person authored under their own name.

The direction of the default matters and is the safe one: approval means the person read *this text*, so authorising the run, approving a plan, asking for the PR, or merely being in the session are all No. Where the run cannot say the text was read, the footer goes on.

Two consequences worth naming because they are changes, not restatements. `settle-outstanding-decisions`'s recorded ruling **is the one write whose footer is decided by a condition rather than by its kind**: the owner supplies the answer inside it, and the skill composes the question as asked, the dated marker and what the ruling confirms — so the test is asked of the complete comment, and the footer is omitted only where the owner was shown and approved that whole record. A first version of this entry said the ruling simply carries no footer, on the grounds that the marker already attributes it; both halves were wrong, and the reasoning is in that skill's own NOTES. And the `NEEDS_USER` draft's footerlessness stops being a special case sitting beside the rule and becomes a consequence of it. The review trigger keeps its exemption and now has two independent reasons; the functional one is the one to state, because it is the one that fails silently.

Both negation guards survive untouched — the footer is still not identity evidence, and still not a discriminator for whether a comment is the run's own. Narrowing which writes are marked changes nothing about what the mark may be used for, and the discriminator guard actually gets stronger: it would now break on every attended write.

**What the forge avatar tracks, and why it is not the signal:** on GitHub, a write made through an installed GitHub App acting on behalf of a user renders as the user's avatar with the app's badge on it — the "two icons" a reader sees intermittently. A write made through the user's own credential (a local `gh` on a PAT, say) renders as the plain avatar with no badge. Both are the same run doing the same thing; what differs is only which transport authored that particular write, and transport precedence is chosen for reliability rather than for how it renders. So the badge appears and disappears across a single run's writes, and its absence means nothing at all. That is why attribution is carried by text the run writes rather than by anything the forge draws — and it is also why the footer is explicitly *not* identity evidence: it is the run's own claim, and reading it back as an observation would let the run establish its identity by asserting it, which is exactly what the posting-identity rule's observation clause refuses.

**Why the screenshot rule is conditional on the repository providing a capture (Sept 2026):** it arrived unconditional, ported from #71, which took it from a human author's PR-description style guide. That is the right rule *there*: the actor is a person at a machine who can always take a screenshot. This contract's actor is often a dispatched worker in a container with no browser and no harness, and an obligation an actor cannot meet is not met — it is discharged with a fabricated "N/A", or worse with a claim of a visual check nobody performed, which is the same attribution dishonesty the footer exists to prevent pointed at behaviour instead of authorship.

So the rule is conditional on a capture path existing, and it carries the fallback explicitly: say what changed visually and say no capture was available. The **never imply a visual check that was not performed** clause is the load-bearing half — without it the honest fallback and the fabricated one read alike to a model looking for the shortest compliant output. Guarded against the unconditional form specifically, because that form is what regrows: it is what the source guide says, and #71 still carries it.

**Why the blanket footer kept creeping back (round two, historical):** the rule's previous form — a footer on every authored write — was re-prefixed onto the narrowed sentence and sat there unnoticed, because a check on the corrected clause could not see the old one return. The detector built for it has since been removed with the other prose-grep checks (repository README, *Checks*); the blanket form is still the thing to look for when editing this rule.

**Whether the required-contents enumeration is exhaustive (decided Sept 2026, on `review-docs`):** it is **illustrative of a general rule**, and deliberately not a registry. The rule is *where the write's own site mandates contents, those contents win*; the four named sites are there because each one's omission broke something specific and nameable, which is the evidence for the rule rather than its scope. A new consumer is therefore covered on arrival without editing this file — `review-docs` was the first test of that, its claims table and per-finding `path:line` evidence being required contents of a write whose tempting cut is precisely the evidence, because the evidence is the longest part and reads as padding to anyone applying a word budget. Recorded because the opposite reading is available and costly in both directions: maintained as a registry, the list becomes a thing every new write site must remember to join, and a site that forgets has its required contents silently demoted to whatever brevity allows — which is the failure the general rule already prevents. Growing the list is for a new *failure shape*, not for each new consumer.

**Why brevity is a rule and not a matter of taste:** length is asymmetric. A run pays nothing to write another paragraph and a reviewer pays for every one, on every PR, and the failure is invisible from inside the run — a PR body that restates the issue and narrates the attempts looks thorough to its author and buries the two lines a reviewer needed. The `Fixed in <sha> — <what changed>.` shape was already the worked example in `resolve-pr-comment`'s reply step; making it the rule is what stops it being read as one illustration among possible others.

**Where the PR-body numbers come from, and why they are numbers:** they are ported from the owner's own PR-description style guide (`baseten/ai-alex`, `writing-style/gh-pr-style.md`, merged as that repository's PR #3). The first draft of this section said "a handful of lines", which is the shape of rule that loses every argument with a model that believes its own body is the exceptional case. A word count, a sentence count and a bullet count cannot be reasoned around. The guide itself is a personal file at a local path, so it cannot be cited from skills installed into `~/.claude/skills` or run in a container — hence a self-contained floor here, and the deference rule that lets a repository's or a user's own guide, read through `create-pr`'s existing `CLAUDE.md`/`AGENTS.md` step, override it. Voice rules stay in the personal guide; they are not this section's to state.

**Why *intent, not content* rather than "what changed and why":** that earlier phrasing invited exactly the enumeration the guide forbids, because "what changed" is what a file-by-file inventory answers. The diff already carries the content, and a body competing with it buries the only part a person had to write. The named exclusions — the inventory, the code narration, the investigation log, the journey — are named individually because each is a separate habit and a general injunction to be concise stops none of them.

**The authorship principle these two changes share:** the guide's source argument is *never let AI write a description on your behalf* — generate from the template, then edit it by hand until it sounds like you. That is the same principle as *Handling queries* in `resolve-pr-comment`, arrived at from the other end: a run may do the work of drafting and may not put the result in a person's mouth. The PR body is the case where the person is present to edit, so the rule is a budget and an edit pass; the review thread is the case where they are not, so the rule is that the draft goes to them and nothing is posted. Reading them as two unrelated conventions is how one of them gets relaxed later.

**Why required contents beat brevity rather than the reverse:** every mandated element in this repository exists because dropping it broke something specific — a closing keyword that auto-closes an unfinished issue, a `Depends on:` line the stack topology is read from, a ruling comment a reviewer cannot read the answer out of, a worker report's judgment, which the report's subtraction exists to carry. A brevity rule that could override any of those would be a licence to reintroduce each of those failures, one short write at a time.

**Why the no-wrap rule sits with brevity rather than in a style guide:** it is not a claim about voice, which is why it survives a repository whose own guide governs the prose. It is a claim about the destination — a forge field renders a newline inside a paragraph as a line break, so a paragraph wrapped at a fixed column arrives as a ragged column. Verified rather than assumed: GitHub's own rendered HTML for a wrapped PR body carries a `<br>` at the end of every wrapped line.

**Why it needs stating at all, given nothing else here is a formatting rule:** because the habit is trained by the repository and the write escapes the training. A project that formats its markdown at a fixed width enforces that on every file a run touches, usually in CI; the PR body is composed inline, reaches no formatter, and fails no check. So the one write where the habit is wrong is also the only one nothing corrects — two PRs made the same way, one wrapped at 72–79 columns and one running to 404 characters a line, differed only in whether the author happened to remember.

**Why check lists are banned flat and the gate report moved to the output (#158):** a worker tabled its whole gate report into a PR body, because `create-pr` then required a body gate table and the advisory line sat below the budget. The forge's checks already report them; the caller still reads the gate report, so it moved rather than went.

**Why SHAs are bare (#158):** GitHub autolinks a bare SHA, not one in a code span, so the old reply template posted unlinked SHAs. No-announce sits beside it because that reply is where a repair is answered; a dispatch's worker report names the head as data for the parent, which is a different write.

**Why a skip token is banned from prose too (incident, Oct 2026):** a commit message describing the deferred-CI feature quoted the token, and GitHub skipped CI on that PR and on its squash merge to the base — the one run nothing is meant to defer. The forge matches the token anywhere in the message, so there is no safe way to quote it; the rule names it instead. It extends `merge-stack`'s explicit-merge-message default to every message the run writes, so it is stated once here.

**Why a PR body is edited after creation only under three conditions (#163, owner's ruling 2026-09-30):** a run rewrote a published description a person had read, to add behaviour changes, because the settle reconcile then told it to unconditionally. A draft, a body still carrying the footer, and a repository that granted `auto-merge` are the cases where nobody's read text is overwritten or the owner already handed the PR to the run; everywhere else the drift is reported with a replacement for the author to apply, and the merge still holds on it.

**Why `Depends on:` is exempt, why the governing opt-in counts, and why an allowed edit adds no footer (#163 review, owner's ruling 2026-09-30):** the `Depends on:` line is stack metadata `merge-stack` must keep true on every restack, not a person's prose. The permission follows whichever merge opt-in governs the PR, so a dependency PR under `auto-merge-dependencies` is treated as an implementation PR under `auto-merge`. And an edit the rule allows on a body a person wrote leaves the rest of their text theirs, so a footer would misattribute it.

**Why this rule names the posting-identity and review-feedback rules path-neutrally (#168):** it names them to say which rule owns a neighbouring question — authorship, and the thread-root discriminator — not because a skill applying this rule must apply either to do so. Cited as `references/…` paths, each was copied into every skill carrying this one. Five of those — `normalize-github-dependencies`, `review-skill`, `summarize-wave`, `upgrade-npm-dependency`, `validate-backlog` — make authored forge writes and had reached the posting-identity rule only through this one. Posting identity is a protected rule (repository `CLAUDE.md`, *Protected rules*), so the owner ruled on #168 that no skill making an authored write may lose it: each of the five now declares it and cites it where it writes. A skill must reach the posting-identity rule by its own citation at its write, not through this rule's scope sentence. The restructure in the same change moved the reasons below out of the rule; the entries above already held the rest.

**Why a tracker issue a write names is a link (#195):** orchestrator writes kept naming an issue as a bare identifier ("this belongs in ENG-123"), and every reader then had to look it up. A forge auto-links `#123` only inside its own repository, so a PR or issue named anywhere else needs the link as well.

## A PR body

**Also moved from the rule (#168):** most PR bodies come in far under the 300-word ceiling; and a capture is the only part of a body the diff cannot supply, which is why it is asked for wherever the repository provides a way.

**Why the checklist is capped at 8 grouped items (moved from the rule, #168):** a fifteen-item manual checklist gets skipped entirely, and a six-item one gets done.

**Why a heading stays over a gap only the author can fill (moved from the rule, #168):** deleting a template heading is right where the section will never apply to the change, and wrong where it hides a gap, because the reader then sees an absent section rather than a missing screenshot, and cannot tell which.

## The attribution footer marks the writes nobody read


**Why a gate note carries the footer (pre-merge audit of #197, round 1):** a gate note is text a session wrote and no person approved, so the approval test puts a footer on it. That holds even though no reader of the PR is shown it. The blind audit found the note format left no room for one. Exempting the note would have narrowed protected rule 1. Instead, the footer is the note's last line, and nothing that reads the note counts the footer as a check.

**Why the gate note keeps its footer once identity moved to the ref (author fixes after round 2 of #197):** the footer first did two jobs on a gate note: attribution, and, with the recorded notes-ref commits, telling one writer's block from another's. One session per assigned ref took the second job away, since a note is now known by the ref it is on (`supervise-prs`, *Integration-branch CI*, step 3), so the footer was re-examined. It stays. The approval test above is the whole of the footer rule ("nothing else decides it"), and it asks whether anyone approved the text, not whether a reader is shown it. Dropping it for a note no reader is shown would narrow protected rule 1 by a condition its text does not have, which takes an owner ruling and a rule audit, for the sake of one line no reader counts as a check.

**Why the "attribution already present" bullet exists (moved from the rule, #168):** reading the owner-ruling marker as licence to drop the footer is the mistake it blocks, and an earlier version of this section made it.

**Why a body edit strips a transport's trailing footer, and an approved write reports one (#183):** a transport that appends a footer adds one on every write, so re-writing a body that already ends with one stacks a second. And an approved reply sent through it is not footerless, whatever the run wrote, so the report says what was posted.

**Why a gate note is not a write that reports verification (Oct 2026, owner ruling):** the ban exists so that no reader is shown a claim that checks passed where the forge's own checks are the evidence. A remote session's gate result has nowhere else to go — its return value never reaches the caller — and it must reach `supervise-prs` for a PR into an integration branch, which runs no CI. A git note under `refs/notes/agent-gate/*` is read by the run and shown to no reader of the PR, so it carries the result without being the write the ban is about. Any other carrier stays banned, the `<details>` block included.

**Why protected rule 7's index names the notes ref, not "a write a reader is shown" (owner ruling, after round 2 of #197):** the index once read "no forge write a reader is shown reports verification". Both audit rounds found that wider than this rule: it would also admit a hidden HTML comment in a PR body, which this rule still bans, and whether a notes ref is hidden had been checked only for GitHub. The owner narrowed the index to the one exception this rule then made, a gate note under `refs/notes/agent-gate/*` (the hold-item carve-out below came later), and this rule states the exception in those words, so the index and its home cannot be read apart. The home is narrower still, on purpose: the exemption covers only a note on the ref a dispatcher assigned, where the result cannot reach the caller. The verification audit after round 2 showed that a worker given this rule verbatim under any `ci-mode` could otherwise read the prefix alone as licence to mint its own ref and write its results there — a write nothing reads, and not what the owner ruled for.

**Why a hold item may name the check it holds on (owner ruling, final pre-merge pass of #197):** the round-2 re-audit found hold items naming check outcomes on the issue or thread where the owner answers them, outside both of this rule's exemptions: the full tier's bisect `NEEDS_USER`, already on main, and two added by #197, the full tier's no-note option "with the full tier not run" and the merged-tip hold "reported to the owner with both results". Rewording them to name no check would leave the owner a choice they cannot make — which suite broke, on which commit, decides between a fix issue and opening anyway. So the owner added a narrow carve-out: a hold item may name the check it holds on, failed or not run, and the commits it ran or was due on, and never lists a passing check or a run's results. The ban's purpose, that no reader is shown a claim that checks passed, is untouched, since a hold item now carries no pass at all. The merged-tip hold was reworded from "both results" to the failing check and its head, because the second result was the gate record's passes. Protected rule 7's index line in `CLAUDE.md` states the same carve-out, so the index and this home cannot be read apart.
