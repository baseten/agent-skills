# Notes — watch-and-read

Reasoning for `rules/watch-and-read.md`. Deliberately *not* bundled into
each skill: a copy of this per consumer would be design history with no reader,
and the audience for it is a person editing the rule, who has this checkout.

Moved here with the rule itself when it was split out (#144): arming, the no-change preflight and read discipline from `swarm`, *Supervision*, merged with the PR-specific forms `backlog-orchestrator` held in *Event handling* and *API budget and read discipline*, and those sections' notes. "The run" and "the per-PR block" in the moved entries are `backlog-orchestrator`'s, as they stood when the entry was written.

**Why this is a shared rule (#144):** `swarm` stated the general form and `backlog-orchestrator` the forge form of the same three rules, and each consumer that supervises PRs without running under the other — `implement-issue` supervises its one PR with no `swarm` at all — would otherwise need a third copy. The two versions had already drifted: `swarm`'s polled-item clause did not say that a poll that did not run is a blind spot, and `backlog-orchestrator`'s change-signal list was the only one to name the scheduled check-in.

## Arm the watch when the item enters the tracked set

**Why arming is followed by a read:** the subscription is forward-only and says so nowhere in its result, so a late arming looks exactly like an early one from the inside — both return success, both then deliver events. What differs is an unread interval that no later event will ever cover. Pairing every arming with one read of checks, reviews and comments makes the two cases distinguishable at the only moment the run can still tell them apart; stating the interval as unread rather than empty is the same rule the transport case of `absence-is-not-a-verdict` states, applied to time instead of to a transport.

**Why arming names the posture rule (#154):** arming is the moment a PR-activity subscription hands the session the platform's drive-to-green posture, and this rule is what every supervising skill reads at that moment. The override itself is `rules/platform-pr-posture.md`'s, since its binding reaches the session answering the wake as much as the one arming; the pointer here is so a reader arming a watch meets it.

**Why the post-arming read reconciles rather than samples:** the first version read checks, reviews and comments — which is what the gap was noticed through, not what it contains. A merge, a close, a force-push and a moved base pass through the same blind interval, and a run that reads three of the five holds a stale head or supervises a PR that already merged, both of which look like healthy state from the inside.

## The no-change preflight

**The incident behind the no-change preflight:** a run tracked three PRs with check-ins alone, the `event subscription` field never recorded, an hourly poll, and a "nothing changed" report at 18:20Z. The owner merged at 18:46Z; the next poll was due 19:16Z. From the inside that run was indistinguishable from a healthy one, because "no events because nothing happened" and "no events because nothing was listening" produce the same quiet — and it was the owner who noticed, not the run.

**Why the no-change preflight outranks all of it:** the cheapest possible supervision loop is one that reads nothing and reports quiet, which is exactly the 18:20Z failure above. Every rule here had to be written so that it cuts reads that were finding nothing, and never a read that establishes something is still being watched.

## Reading on a change signal

**Why the polling fallback names where its bound comes from:** "bounded parent polling" left the bound to the reader, and a supervision loop reads an unspecified bound as every cycle, everything — which is the shape the overrun below was made of. The fallback is still polling; what changed is that its bound is the read-discipline rules rather than the run's own judgment.

**Why the rules target the loop and not the calls:** nothing in the old text was individually wasteful. Each read was justified where it stood; the cost came from the loop's shape — a full reconcile of every tracked PR every cycle, then per-concern reads within it, then a fresh reconcile per merge event in a landing stack. Multiplied by the wave and by the cycle count, that is the whole overrun, and none of it produced a finding. This is why the rules are about *when* a read is due and how many questions it answers, rather than about which endpoint to prefer.

**Why the scheduled check-in is on the re-read list:** catching what the subscription missed is the entire reason the check-in exists — CI success, new pushes and merge-conflict transitions are the known-unreliable deliveries — so a re-read rule that fires only on delivered events makes the backstop cycle read nothing and fold cached state into a confident no-op. The version of the list that omitted it would have let a PR waiting on CI sit unread until a human noticed, which is the 18:20Z failure again with a budget rule as the excuse.

**Why one read per PR, and never one nested read of everything:** CI, then reviews, then threads, then comments, then merge state is the same PR fetched five times for one decision. The opposite error is as expensive: pulling nested thread and check collections across the whole tracked set to discover that nothing changed is the single most costly way to learn nothing, and it is what "one consolidated pass" invites if the pass is not also bounded to what the cycle needs.

**Why no agent is dispatched to make a query the run could make itself:** a worker spawned to re-ask a refused question is a retry loop wearing a different hat. It draws on the same credential's buckets, so it neither spreads the cost nor waits out the reset, and it hides the retry from the deferral rule that would otherwise have stopped it.

**And why that rule had to be narrowed to dispatch-as-reading:** stated as "no agent is ever dispatched to perform a query this run could make itself", it forbade the mandatory preflight. `validate-backlog` is required before any new implementation worker and it reads dependency edges, hierarchy and project structure — all queries the run could make itself — as do `summarize-wave` and the settle skills. A model applying the absolute literally would skip the one check standing between a merge-changed graph and a dispatched worker, trading a correctness guarantee for a budget saving the rule never meant to buy. The same collision as the worker read ban in this section's first round: an absolute written for one case reaching a contract two sections away.

## Allowances belong to the credential

**The incident:** a diagnostic mid-run read **7/5000 REST and 10,447/5000 GraphQL** — the allowance overrun twice over while REST sat at a rounding error. The split is the finding: the two budgets are separately metered, and in that run it was GraphQL the supervision reads were landing on — PR state, checks, reviews, threads and comments, through the tools that run happened to be using. Read that as what those tools did, not as a property of those reads: several have REST endpoints, and which bucket any of them draws on is settled by the contract's evidence rule, never by the fact that this incident found them all on one side. What generalizes is the asymmetry — a run can look thrifty by one budget's measure while exhausting the other, so a single remaining figure is never the whole picture.

**Why transport is not mandated either way:** the obvious fix — "use REST" — optimizes the label rather than the cost, and would replace one cheap graph query with five round trips often enough to lose. What is mandated is the minimum total, with the targeted-vs-broad call decided per question.

**Why the flat/graph split is not written on tool names:** a skill cannot see which transport a first-class tool uses underneath, and precedence tells it to prefer that tool anyway — so "use the REST one" is not expressible here and would be wrong the moment an implementation changed. The split itself is uneven in the loop's favour: the transition checks nearly every cycle needs are flat, and only thread resolution — genuinely lacking a flat equivalent — is not.

**Why shape is only the prior, and observation the authority:** the first draft of that rule attributed a read to a bucket by shape alone, which review correctly called a heuristic dressed as a fact. Shape misses in both directions — REST paginates collections, and a graph query can return one record — and the cost of misattributing is not a wasted call but the two failures the whole section exists to prevent: hammering an exhausted bucket, or idling a healthy one. Two things fix it without going back to names. Where the run chooses the endpoint (`gh api graphql` versus `gh api /path`, or a direct call) the bucket is *known*, so nothing is inferred. Where a first-class tool hides it, the run gets ground truth for free the first time a limit bites: this session watched `get_review_comments` refused while `pull_request_read: get` and comment writes went through on the same PR in the same minute, which attributes all three with certainty. Recording that per tool converts a guess into evidence, and it accumulates the same way transport-visibility proofs do.

**Why the incremental bound is the earliest `last read` in the batch:** one endpoint takes one bound and tracked PRs will not share a timestamp, so a later bound drops what arrived for the PR read longest ago — which is the PR most likely to have something waiting. Over-fetching and filtering per PR costs one request; under-fetching loses an event silently.

**Why deferral is scoped to the exhausted resource, and the wake armed at the reset:** the incident's own numbers are the argument — a credential-wide stop would have abandoned a REST budget at 7/5000 because GraphQL was gone. Retrying into an exhausted allowance is what turns a throttled hour into a dead one, and a 20-minute wake against an allowance that resets in 50 fires early and spends a call to be refused again, which is why the reset (or a supplied `Retry-After`) is a floor under the wake time. It is only a floor: an earlier draft had it *win* over the backoff outright, which reversed the guard whenever the backoff had climbed past the reset — a run at the 4-hour cap with an allowance resetting in 20 minutes would have gone back to waking every 20 minutes. The two statements of that composition had drifted apart, the same failure the seam behind the wake's single counter produced four times (`rules/wake-budget-notes.md`); the schedule is now stated once, in `rules/wake-budget.md`, *The budget and the backoff*, as the later of the two.

**Why a floorless deferral is defined rather than left implicit:** a secondary limit is tied to no resource, so it has no reset, and GitHub can send one without `Retry-After` — the two bounds the floor is built from can both be absent. Read strictly, "never arm before the reset" then forbade arming the resuming wake at any time at all: the watch could be neither re-armed nor allowed to expire against its budget, and later PR changes were never observed — an unbounded silence where the design promises bounded waking. The fix defines the absent case as *no floor* rather than inventing a third constant: the backoff's 20-minute first step is already longer than the pause a secondary limit asks for, so a dedicated fallback number would duplicate the backoff's job while giving the two schedules a way to drift.
