# Notes — agent-policy

Reasoning for `rules/agent-policy.md`. Deliberately *not* bundled into
each skill: a copy of this per consumer would be design history with no reader,
and the audience for it is a person editing the rule, who has this checkout.

Moved here with the rule itself, from `backlog-orchestrator/NOTES.md`, where it
was reasoning about a section that no longer lives there.

**Why a config file and not prose or a skill override:** a `CLAUDE.md` paragraph gets interpreted, and interpretation must not decide whether a run may merge. A project-level skill override is not the mechanism either: `bootstrap.sh` installs these skills to `~/.claude/skills`, and a personal skill shadows a project skill of the same name, so a project copy would silently never load.

**Why there is no reviewer-identity option:** an `auto-fix-reviewers` key used to gate auto-fixing on the comment's author — a boolean, or a list of vetted bot logins tested against the forge's author type. It was removed rather than re-defaulted. Author identity is a poor proxy for the only thing that matters, which is whether the comment asks for a code change: automated reviewers routinely raise design questions no run should answer, and human reviewers routinely file one-line nits any run can fix. The key therefore erred in both directions at once, and no default fixed that — a permissive default auto-answered humans' design questions, a restrictive one reserved trivial fixes and stalled unattended runs. The kind test the repair path already applied was doing the real work the whole time; the key was a second gate in front of it that agreed with it only by accident. Removing it also collapsed a fail-closed special case: it was the one key whose built-in default was its permissive end, so a corrupt policy file had to resolve it *against* its default to avoid granting more than a parsed file would.

**Why `auto-merge` is one grant rather than per-consumer keys:** splitting the key per consumer would gate which skill happened to open the PR, which is not a security property, and would leave the real boundary — the gate — unchanged.

**Why the off-only keys are listed only in *Precedence* (second blind audit of #175):** `implement-issue` restated the rule as "(`auto-merge`: off only)". When `auto-resolve-comments` became off-only too, that copy let an invocation turn the new key on, and the `true` flowed down to a skill that trusted its caller. Every other site now cites *Precedence*, and `resolve-pr-comment` trusts a `true` only when its source is the repository's file.

**Why `minimize-ci-runs` is not a waiver, and why only the file turns it on (#179; blind audit of #181):** it subtracts no condition from the gate. CI green on the current head and a clean review are still required, and the overlap narrowing of the stale-green re-check is written into `settle-and-merge` itself, so the gate keeps one definition. The review carry-forward across mechanical pushes is likewise written into the clean-review rule the gate reads, not into the key. It was first given ordinary precedence on the reasoning that its permissive end is not a merge. The audit found that reasoning too narrow: `true` still loosens two checks the merge gate reads — stale-green and the reviewed head — so an invocation able to turn it on could loosen the gate of a repository whose owner never opted in — the shape `auto-merge` and `auto-resolve-comments` are off-only for. An invocation can still turn it off.

**Why `ci-mode` is one enum and `minimize-ci-runs` an alias (owner's request, Oct 2026):** a second CI-saving mode arrived — batching a run's PRs into an integration branch — and as a second boolean beside `minimize-ci-runs` the two could both be on, with no answer for which governs a PR. They are alternatives: an integration-branch PR runs no CI at all, so there is nothing to defer. One key with three values makes them exclusive by construction, and `deferred` names what the old key did. The old key stays readable so no committed file changes meaning; where both are present and disagree the repository falls to `per-pr`, because a file that says two things has said neither, and `per-pr` grants nothing.

**Why `integration-branch` grants merges, and only into its branch (same request):** batching only pays if the run can land each issue PR in the integration branch itself; with `auto-merge` off that would leave the owner merging a dozen PRs into a branch they never read, which is the work the mode exists to remove. But the grant is narrower than `auto-merge` on purpose: it cannot reach the default branch, so the one PR that does — the integration PR, with the single CI run — merges only where the owner also set `auto-merge`, and is otherwise theirs. It is file-only for the reason `auto-merge` is, and grants no body edit because no owner asked for one.

**Why `review-defer-severity` is file-only (same request):** a deferred finding is resolved and no longer holds the gate, so turning it on from an invocation would loosen a repository's gate its owner never loosened — the `minimize-ci-runs` shape (#181 audit, above). Lowering it toward `off` only holds more, so an invocation may.

**Why a value outside a key's enum fails closed (blind audit of #186):** the enum keys are strings, so a wrong value is still the right type and slipped past the type check. Read generously, `"P1"` would defer P1 findings — more than any valid file grants — and `"integration"` would be guessed as the mode that grants merges. Either is the misspelled-`auto-merge` case, so it defaults and is reported.

**Why `publish-triggers-review` takes the ordinary precedence and defaults to `false` (#190):** publishing is inert unless the repository's configuration says otherwise (`settle-and-merge`, *Merge behavior*), and this key is how a repository whose reviewer acts on a publish from outside its files says so. Neither value opens the gate: `false` still requires a clean review on the current head, and `true` only adds a fresh round to wait for. So it is not one of the keys an invocation can only switch off, and its built-in default is not a permissive reading the fail-closed rule would have to guard.

**Why `conductor` reads at its start and at each restart, and why its key's range is named (2026-10-31, PR #201):** a conductor runs for days, clearing its context in the same session (`conductor`, *8. Context clear*); a restart after a clear re-derives from durable truth, so it takes a restart's fresh read like any other run-starting skill, and the ledger's copy of the value only reports. `conductor-clear-at` is the first key with a maximum, and a value outside 1–99 would otherwise have been honoured as written. It is named in the fail-closed list rather than covered by a general range clause, so the change touches no other key.

**Why `branch-update` rebases every PR branch, with two exceptions (owner's rulings, 2026-11-02 and 2026-11-03, PR #201):** the owner force-pushes, at work and on their own projects, and wanted runs to do the same. A first draft kept a merge commit in nine cases; the owner overruled all but two. Counters are matched by `Repair-Pass` id, never by SHA, and a rebase records the ids it carries first, because a plain rebase drops a commit whose patch is already upstream. A parent is rebased and its children restacked. History the run did not write is protected by the lease, which is always pinned to the head recorded before the rebase — a bare lease checks a remote-tracking ref a background fetch can advance. Under `ci-mode: deferred` a rebase keeps the head's skip token, so the trigger puts the one untokened empty commit on top; under `integration-branch` a rebased PR needs no token where its workflows do not run on PRs into the branch, and otherwise costs one CI run. What stays: never force-pushing a branch another session is pushing to — that would destroy its work, so the run waits and then rebases — and the run's own integration branch merging the default branch in, because every open PR in the batch is based on it.

**Why a wrong or unreadable `branch-update` falls to `merge` (PR #201, contradiction pass and re-audit):** every other key's built-in default is its closed end. `branch-update`'s built-in is `rebase`, the value that licenses a force-push, so a typo, a wrong type or an unparseable file resolves to `merge`, reported, and an absent value in a caller's input is `merge` too; `supervise-prs` and `repair-pr` take the key as an input for that reason. The key is in *Precedence*'s list, since an invocation can set `merge` and never `rebase`. **Two corrections from running git (re-audit):** a pinned lease protects only commits pushed after the recorded head — commits already on the branch are rewritten whoever wrote them, which is the owner's ruling, stated plainly rather than as protection; and a plain `git rebase` drops a commit whose patch is already upstream, trailer included, so the ids are recorded before the rebase and a dropped one stays counted.
