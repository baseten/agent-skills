# Notes — posting-identity

Reasoning for `rules/posting-identity.md`. Deliberately *not* bundled into
each skill: a copy of this per consumer would be design history with no reader,
and the audience for it is a person editing the rule, who has this checkout.

Moved here with the rule itself, from `backlog-orchestrator/NOTES.md`, where it
was reasoning about a section that no longer lives there.

**The attribution-honesty argument:** a run posting under the invoking user's login produces conversations that read as though the owner wrote them — status reports in their voice, replies arguing with their own automated reviewer — and `author_association: OWNER` lends every one the owner's authority. A distinct identity also removes an identity collision at its source: run-authored and owner-authored comments become distinguishable by author instead of only by the structural tests in `rules/review-feedback.md`.

**The observed false claim behind "never established by a claim":** in one verified environment the MCP surface and the ambient token both resolved to the invoking user's own account, and no distinct identity existed anywhere — while ambient text asserted the surface "posts as a bot".

**Why re-authoring makes the credential a predictor, and why the read-back costs nothing:** relayed and integration transports re-author writes, so the account a credential authenticates as and the author its writes carry can differ. Reading the author off an authored write the run was making anyway costs no probe — which is why establishing identity by observation does not reintroduce the identity call that deferring to the credential record was meant to avoid.

**The overwrite and collapse failures the composite, per-kind map prevents:** two workers can use the same named transport under different credentials, and a transport can reauthenticate mid-run, so a transport-only key silently overwrites one worker's observation with another's — and trigger selection then reuses an invoking-user observation for an agent-authored credential, or the reverse. Collapsing to one identity per run, per skill, or per report loses whichever entry the collapse discards, and the entry most often discarded is the invoking-user one the trigger rule exists to find; a run legitimately writes through several transports whose observed authors differ without any of them being wrong. The per-kind split exists because platforms re-author per operation, not per credential: an app-scoped token attributes most endpoints to the user and some to the app, a tracker can accept per-call author overrides, and integration re-authoring comes with no guarantee of uniformity across write paths. `create-pr` returning the PR's entry and the trigger comment's entry separately is the rule in action — under a shared pair, a single-author entry would hold whichever observation was merged last.

**Why the unselected-tier reporting rule cannot re-admit the credential self-report:** identity comes only from an authored write, and neither rerouting nor probing an unselected tier is permitted — so any claim about such a tier's identity could only be its credential's self-report, re-entering through the reporting requirement the section just rejected. Calling that identity "available" would oblige the run to a reroute it may not perform. And reordering precedence to reach a better author would trade a reliability rule for a cosmetic one: attribution honesty is not worth routing a write through a path more likely to under-report or fail.

**Why degradation is decided by observation, not by a second credential test:** an integration transport can carry a credential that identifies as the invoking user and still have the platform re-author its writes as an agent — the credential and the observation disagree, and the observation decides. Preserving `unestablished` matters for the same reason: resolving it to "invoking user" would overwrite a real observation slot with an inference. The checkpoint naming turns "the owner's login on every comment" into a stated fact rather than a discovered one.

**The silent trigger failure:** a trigger comment authored by anything but the invoking user is not refused — nothing errors, so the trigger rules that reissue through another mechanism on an explicit refusal never engage, and the run waits out a review that was never going to arrive. That is what makes the trigger's authorship functional where every other write's is cosmetic, and why the exception licenses rerouting for that one comment: the no-rerouting argument holds only where a wrongly-authored write still works.

**Why PR-creation authorship does not predict comment authorship:** a pair whose PR creation carried the invoking user can still have its timeline comments re-authored as an agent, and a trigger sent on that prediction fails in exactly the silent form above — hence selection on evidence of the trigger's own write kind.

**The bootstrap deadlock and its cost accounting:** on a fresh run the only write read back is `create-pr`'s PR creation — a different kind — so a gate demanding comment-kind evidence before permitting the comment deadlocks: standalone `implement-issue` could never fire its first automated review, and an orchestrated run without an earlier ordinary comment would fare no better. The mandatory read-back is what separates the bootstrap from silently posting under an unknown author: a wrong author observed means the run knows immediately instead of waiting out a review that never arrives. The cost of a wrong prediction is one stray timeline comment that reads as conversation; the cost of the gate without a bootstrap was the first review of every fresh run.

**Why the trigger's unavailable-for-now never earns a run-long suppression:** a reviewer refusal is a fact about the repository's review configuration — repository-scoped and stable, which is what earns it run-long standing. Trigger unavailability is a fact about what the run has so far observed, and at the first PR it may have observed almost nothing; suppressing on it would skip review on every later PR in that repository on the strength of evidence not yet gathered. Recording the escalation as provisional and identity-based is what lets a later pass tell the two apart — a run that conflates them inherits the run-long suppression it was just denied.

**The thread-root test's two jobs:** it closes the identity collision — the one job a distinct identity subsumes, where one exists — and it separates feedback-to-act-on from conversation on the PR timeline, a comment-kind distinction no author identity can make: the invoking user's timeline comment is still conversation, and their thread root is still an instruction, whoever the run posts as. Because availability degrades per write, the collision-closing job returns whenever the condition fails; deleting either rule as redundant re-opens exactly the ambiguity it closes.

**Why `appends footer` is a map property (#183):** a transport adding its own footer is a property of the write path, like authorship, and three rules need it: trigger confirmation, body edits and approved writes. Recorded once on the pair, it travels with the map.

**The GraphQL/REST transport note (#183):** reported from a field run, in a session where GraphQL was blocked: `gh pr comment` failed and `gh api -X POST repos/{owner}/{repo}/issues/{number}/comments` posted. It was not re-run for this change, since a check would post a real comment; it is recorded as observed in that report.

**Why the invoking user's comments need every write id (blind audit of #184):** on the degraded path the run posts as the invoking user, so a run reply whose id was lost reads exactly like the owner's own comment. Read as the owner's, it would skip the hold and turn the run's own words into instructions it then acts on. So a comment counts as the owner's only while the run holds the id of every review-thread comment it posted under that account in this run, or posted under another account. After a restart, or on a fresh invocation over a PR an earlier run wrote to, it cannot show that, and every comment under that account is a person's: the held direction. The account itself comes only from the invocation or session, the owner's own statement, never from a credential, because the credential is exactly what the run and the owner share.

**Why a conductor's dispatch names the invoking user (owner's ruling, 2026-11-03, PR #201):** a session a `conductor` dispatches is started by the owner's go, in the owner's own conductor session, so the account its dispatch prompt names is the owner's own statement carried to the session it started — the same standing as an invocation naming it. Treating it as unknown held the owner's own review threads for approval, spent repair budget on the owner's own review rounds, and merged instead of rebasing the owner's PRs. It is still a statement, never read from content: no footer, title, credential or map entry names the invoking user. Threads with another person stay held (protected rule 1). Scenario: `implement-issue`, `a-conductor-dispatched-session-treats-the-owner-as-the-invoking-user`.

**Why own writes are known by id only (owner's ruling, 2026-11-04):** protected rule 2 read *own writes are known by id or footer, never content*, while the *authored write form* rule said the footer is not identity evidence and never a discriminator. The two disagreed, and the disagreement failed safe only by luck: every site that accepted a footer happened to be one where a pasted footer did little harm. The owner ruled that own writes are known by id only — a write id the run recorded, or the forge's own id for the write (comment, review, issue, PR, commit) — because the footer is text: anyone can paste it, a person quoting a run's comment copies it, and an earlier session's footer names a session that is not this one. #200 found one footer test in `rules/review-trigger-notes.md` and fixed it; the sweep after the ruling found the rest. Follow-ups filed for deferred findings were excluded from the filing run's scope by their footered body (`backlog-orchestrator`, `supervise-prs`'s rebuild); a held worker's retirement record was recognised by footer or id (`swarm`, `settle-outstanding-decisions`); and a remote worker's report, and a review session's comment, were recognised by the footer naming the session (`swarm`, *Releasing a worker*); and the body-edit table took a footered body as the run's own text (`rules/authored-write-form-notes.md`). Each now reads an id, and three chains had to be completed for the id to reach its reader: follow-ups, already in `supervise-prs`'s per-PR record, are now passed back to it and carried in `backlog-orchestrator`'s state block; retirement records' ids, which `backlog-orchestrator` said its state block carried but whose schema had no field for them, now have one and are passed through `settle-and-merge` to its gate and the walkthrough; and a remote worker names its report's URL in its final message, which its own session record carries, as well as in its push.

**What the id-only reading costs where an id is lost.** A write whose id the reader does not hold is not the run's own — the rule says so once, and each site says what follows. A retirement record whose id was lost retires nothing: the item stays outstanding and the gate holds until the parent observes the ending again and posts a record whose id it keeps. A follow-up whose URL no record holds is read like any other descendant, and a re-raised finding is filed again rather than linked. A remote worker stopped on a permission prompt for the send tool has named its report's URL nowhere, so it is held for the owner instead of released (`skills/swarm/NOTES.md`). Each of these trades a cost — a second record, a duplicate issue, a container kept — for never taking someone else's text as the run's own, and none falls back to the footer, which would reopen exactly the case the ruling closes. Scenarios: `swarm`'s `a-pasted-footer-does-not-make-a-comment-a-workers-report` and `a-send-tool-prompt-before-the-report-url-is-named-is-held`; `backlog-orchestrator`'s `a-retirement-record-whose-id-was-lost-retires-nothing` and `a-follow-up-known-only-by-its-footer-is-an-ordinary-descendant`; `supervise-prs`'s `a-rebuild-reads-no-follow-ups-off-footered-replies`; `settle-outstanding-decisions`' `a-retirement-record-without-a-passed-id-ticks-nothing`.
