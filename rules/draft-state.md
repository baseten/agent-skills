# Draft state

This is the rule other skills mean when they cite *draft state*: when a run may promote a draft PR to ready, the direction it never moves one, and what an explicitly held draft is.

**It is not a skill and nobody invokes it.** It is a shared rule, held once at
`rules/draft-state.md` and copied into each skill that applies it by
`scripts/refresh_shared_rules.sh`. A skill reads its own
`references/draft-state.md`, which works after `bootstrap.sh` has
installed only that skill's directory, and travels with the skill if it is
moved into a plugin. Edit the source, never a copy; check_shared_rules.py fails if a generated copy diverges.

## Promotion

**A run does not promote drafts on its own, and it defers where a repository's own convention instructs promotion.** Promoting a draft to ready is a social act — it is how you ask another person to review — so it is never the run's judgement call. **A documented convention is the owner performing that act in advance**, which is what makes deferring to it the same rule rather than an exception to it: a repository whose `CLAUDE.md` says to mark a PR ready once CI is green, the review is back and every actionable finding is resolved has already decided, and a run that leaves those PRs in draft is overriding the owner rather than protecting them.

So:

- **a repository convention that instructs promotion is carried out, on that convention's own conditions and no others.** Read them literally: the conditions are the convention's, not the run's. Where the convention is ambiguous about a condition, it has not instructed promotion for that case. This governs the convention route and never narrows the merge path's own publish, which publishes a gate-passing PR as a step of merging it;
- **with no such convention, promotion survives in exactly two places**: the owner promotes a PR themselves, whenever they choose; and the merge path, where publishing is a step of merging (see `settle-and-merge`, *Merge behavior*). With the convention, those are the three forms of promotion;
- **a run never flips a PR back to draft**, whatever any convention says. That direction is not symmetric: withdrawing a PR from review is a decision about somebody's attention, and no convention has been observed to ask for it;
- **an explicitly held draft is untouched by all of it**, below;
- **before promoting, read the ready-to-draft transition from the forge's own timeline, never from the run's own record of the PR.** That record is cached run state, so a restart or a missed event leaves it unable to answer the one question that matters — and promoting a PR a person withdrew does not merely re-request their review, it **destroys the evidence**: the held-draft discriminator is *currently a draft and ever ready*, and a promoted PR is no longer currently a draft, so it can never be classified held again and the gate will merge it. **Held-ness observed once stays recorded**, and the timeline read is a precondition of every draft-state change a run makes, exactly as it is of the gate;
- **the convention is read once, and recorded per repository** — like the publish-triggers observation and the transport and identity maps — read from that repository's own docs at the run's first preflight (its start, where it has no separate preflight). `create-pr` reports what decided the *as-created* state and carries no promotion condition, so there is no chain to inherit it from. **Its conditions are then evaluated on each supervision cycle**, which is where the run already re-reads CI, review and thread state, so a PR that becomes eligible mid-run is promoted when it becomes eligible rather than at whatever moment something happened to look. A convention derived ad hoc at an arbitrary moment makes the same PR merge or not depending on when the run glanced at it;
- **a promotion under a convention is a publish**, so it takes the three-state rule in `settle-and-merge`, *Merge behavior*, for its **classification and un-settle consequence only, and authorizes no merge** — that section's states are written as merge decisions and one of them ends "publish and merge", which at a supervision cycle would be a merge with no gate evaluated and no summary to evaluate it from. Where publishing is observed to trigger, or is unknown, the tranche un-settles for that PR and the gate is reached where it always is, at the settled step.

## Explicitly held drafts

**An explicitly held draft** is a PR that a decision outside the run keeps in draft: an explicit user instruction to hold it, a repository's prose convention **that a PR of this kind stays in draft** — not one that instructs promotion, which is the case above and the opposite instruction — a draft preference a caller passed through `implement-issue-core`, or a human returning the PR to draft after it was ready. This is the term's only definition; the merge gate (`settle-and-merge`, *The merge gate*) and each run's report consume it. An explicitly held draft is reserved from the merge path — excluded from the gate, neither published nor merged, however clean its review and CI — and reported as held, awaiting the owner.

**A PR that is currently a draft and has ever been ready is held**, and that is the discriminator to use — not as-created versus current, which cannot see it. Created-as-draft, marked ready by a human, returned to draft by them leaves both values reading `draft`, identical to a PR nobody ever touched, so a run that consults only those two publishes and merges exactly the PR a person deliberately withdrew. The stronger reading is available because of the rule above, and survives the run promoting under a convention: what the discriminator reads is the **ready-to-draft** direction, and a run never moves a PR that way for any reason, so **every** ready-to-draft transition on a PR of a run's is someone's decision — whoever made the draft-to-ready one before it. Track as-created and current draft state in the run's record of the PR (`create-pr` reports the as-created state) for reporting, but read the transition from the forge's own timeline before applying the gate: that record is cached run state, and a restart or a missed event leaves it unable to answer the one question that matters here.
