- When you name a tracker issue, make it a link to the issue, never a bare identifier such as `ENG-123`. That holds in a chat reply as much as in a PR, comment or message you write. Use the URL the tracker returned, or its canonical issue URL. A PR or issue named outside its own repository is a link too, since `#123` auto-links only there.
- When choosing the skill to start a task with, where an available skill declares that it extends another — `metadata.extends` in its frontmatter, or its description saying so — use it rather than the one it extends. It holds the settings and invokes that skill itself.
- A skill named by its bare name, such as `create-pr`, is the same skill as one listed with a plugin prefix, such as `agent-skills:create-pr`.
- When moving a project to a new Node or pnpm version, or changing how its Claude Code cloud environment installs them, follow the *Node and pnpm upgrades* rule, `references/node-and-pnpm-upgrades.md` in the `upgrade-npm-dependency` skill's directory. In that move, never install pnpm through Corepack.
- Showing the user a draft first exists so an agent never talks to another person on their behalf without their say. So a write nobody else sees until the user publishes or sends it needs no approval first: a draft pull request's body, a chat-app draft, a pending review. Write it there and give the user the link. A skill's own rule for a write it makes governs that write.
- In a review thread another person is in, even alongside a bot, push the fix and hand the user the reply, with the thread's link, to post and resolve themselves; never reply in it or resolve it yourself. A thread only bots and the user are in is resolved once a pushed fix fully answers it, with a one-line reply naming the fix's commit. Either way, a thread carrying a question, an objection the user has not ruled on, or a fix you could not verify stays open, and you say so. Never resolve threads in bulk. Where a skill governs the thread, its rules are the detail (`resolve-pr-comment`, *Replies held for the owner*).
- Before editing anything in response to review findings, in any repository: take every finding of the round, classify each as local, rule or shape, and fix a shape finding across its whole axis rather than instance by instance; before committing a rule change, find everything in the repository it now contradicts; where a finding is about behaviour, run it; never add a check that greps prose. The method and its reasoning: https://raw.githubusercontent.com/baseten/agent-skills/main/docs/review-fix-workflow.md
- Start a new branch or worktree from the base fetched fresh from the remote (`git fetch origin <base>`, then branch from `origin/<base>`), and say which base you used; never inherit whatever branch is checked out. Sub-agents working on one repository at once each get their own worktree.
- When you push a branch that no running skill opens a pull request for, open a draft pull request for it at once, before it holds anything worth reviewing: it is how another session finds out the work exists.
- When the user says conductor, orchestrator, worker, reviewer or planner, they mean the session kinds in `references/conductor-exchange.md`, *The run's title*, in the `conductor` skill's directory.
