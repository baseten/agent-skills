# Settle and Merge

Close out a finished run over a set of PRs: summarize it, put its outstanding decisions to the owner, rank it, and merge what the gate passes.

This file is the contract; the reasoning and incident history behind its rules live in `NOTES.md` beside it, keyed by section. NOTES explains; it never overrides.

**The caller decides when; this skill decides what settling does.** It takes its inputs from whichever skill invokes it — today `backlog-orchestrator` over a wave and `implement-issue` over one PR — and the sequence is the same for every caller. No caller owns a copy of it.

## Inputs

**Everything that differs between callers arrives as an input; this skill never reads its caller's contract to find out what to do.** "Wave" below means the set of PRs the caller passes. A one-issue run is a wave of one, and every wave-phrased clause reads for that one PR. Each caller states in its own text what it passes for each input, as a value or a result — never a pointer this skill would have to follow into the caller's text. **An input the caller did not pass takes the default in the last column** — never a value inferred from which skill the caller is.

| input | what the caller passes | where it is absent |
| --- | --- | --- |
| **PR set and scope** | the scope the PRs were built for — a manifest, an issue URL, or the brief of a run with no issue — and the PRs to settle, which may be none | no scope: there is nothing to settle against, so return, naming the missing input. **An empty PR set with a scope still settles**: step 2 runs and `summarize-wave` writes its one line, and the walkthrough and gate have nothing to act on |
| **findings** | the worker and review findings the run produced | summarize from durable state alone, and say the run's own findings were not passed |
| **held-reply records** | from `supervise-prs`'s record: every approval-pending reply item, verbatim, which step 4 passes to the walkthrough; and every rejected held reply and mixed-thread fix, which step 7 only lists. Each held reply's outcome from the walkthrough — approved with its write id, or rejected as thread and fix SHA — is returned to the caller for `supervise-prs` to record | none to ask or list; say they were not passed |
| **posting-identity map** | the run's map (`references/posting-identity.md`) | start from an empty map: every entry is `unestablished`, and writes degrade as that rule states |
| **resolved policy** | `auto-merge` and `publish-triggers-review` per PR and `auto-request-settle` for the run, as the caller resolved them, and `ci-mode` per PR with whether it has effect in that PR's repository — under `deferred`, whether its overlap narrowing does too (`supervise-prs`, *Deferred CI*); under `integration-branch`, the branch's name, whether its integration PR is open, whether merges into it are stopped by an observed refusal and the item raised for it, each PR's local gate record (*Integration-branch CI* there). An integration check's result comes with the head SHA of every branch it integrated and with the check itself, so it can be re-run here. Or "none apply", with the reason | the stale-green re-check and the tool-bump rule apply — absent is not "none apply" — with no authority to update a branch. No integration result was passed, so there is none to compare, and the report says no integration check was passed |
| **outstanding recovery refs, per PR** | the recovery refs outstanding for each PR's branch, as the caller's own ender judges them where it keys one on PR state | `swarm`'s generic lifecycle decides (`swarm`, *Checkpoint compliance*, *The recovery ref's lifecycle*) |

Where a step un-settles the wave (step 3, step 5), this skill stops there and returns the wave and the finding verbatim, with any held-reply outcomes a walkthrough that already ran produced, having ranked and merged nothing; the caller's own un-settle rule, in its own text, takes it from there | the same |

Work a caller runs alongside a step — a reconciliation of its own at step 1, say — is stated in the caller's text and run by the caller. It changes nothing here.

## Composed skills

- `summarize-wave`, then `settle-outstanding-decisions` while `auto-request-settle` is on, then `plan-merge-order` where the caller ranks — in that order (step 5);
- `merge-stack` for any merge or restack this skill performs — required wherever the resolved `auto-merge`, or `ci-mode: integration-branch`, leaves the gate reachable. The caller checks it at its preflight, where policy resolves, and never discovers it at the gate. What an unavailable one does to the run is the caller's to state.

## The merge gate

**Merges are opt-in per repository, and gated even then.** By default the run performs no merge. It may merge a PR only when that PR's own repository opted in via `auto-merge` in its policy config — or, for a PR whose base is the integration branch, via `ci-mode: integration-branch` (see `references/agent-policy.md`, *Merge permissions*, for both) — **the repository's opt-in is the only route to a merge: an invocation argument can switch `auto-merge` off for a run, narrowing the gate, but never on — an invocation cannot open it** (`references/agent-policy.md`, *Precedence*, states the same exemption) — **and** the gate holds: the wave has no `DECISION`, `MERGE_RISK`, or `NEEDS_USER` item outstanding — anywhere in the wave, not only on that PR, bar a body-drift `MERGE_RISK` and a stalled review round's `DECISION` (`references/review-trigger.md`, *A stalled round*), each of which holds only its own PR — and a `DECISION` that settled without being ruled on is outstanding: unruled is not clean; a held worker's `NEEDS_USER` item is outstanding until its hold retires it, whatever is ruled — a ruling accepting its PR included, which retires it only at the observed archive — and closed once it has (`swarm`, *Blocked workers*, its last rule, says what retires one) — **and** CI is green on the PR's current head (`references/ci-and-review-verdicts.md`, *CI is green*, a head with no run read through *Path filters* there, which also says what a required check a filter keeps from reporting holds, and a PR into the integration branch read off its local gate record), **and** it has no merge conflict — a `dirty` mergeable state is one, whatever CI shows — **and** its review is clean on its current head — a publish changes no head, so it stales no review, though under `publish-triggers-review: true` it requires a fresh round (Merge behavior) — (`references/ci-and-review-verdicts.md`, *A review is clean*, says how that is read; **every automated review round the PR's routing requires, completed** — or stalled and released by an owner's choice to merge without it, once the walkthrough has retired its `DECISION`, never on a reply a declined or absent walkthrough did not retire (`references/review-trigger.md`, *A stalled round*) — `references/review-trigger.md`, *Documentation-review routing*, decides it, and where it puts two conventions on one PR, the faster one completing is not this condition met — every actionable finding resolved or answered, no thread reserved for the owner or holding an approval-pending reply), **and** no recovery ref for its branch is outstanding (`swarm`, *Checkpoint compliance*, names the ref, and its *The recovery ref's lifecycle* says what ends one; the caller passes which are outstanding where its own ender judges them (Inputs) — captured work that never reached the head is work a merge would silently drop), **and** it is not an **explicitly held draft** (see `references/draft-state.md`, *Explicitly held drafts*) — a held draft is neither published nor merged, and is reported as held — **and** the dependency view the PR was built on is proven complete or explicitly answered for (the caller passes it per PR, and Merge behavior says what discharges it; a view unproven because the run's dependency transport is unavailable may have been accepted for dispatch and still holds this condition — proceedable is not mergeable). This is the gate's only definition; every other site defers to it, `backlog-orchestrator`'s invariant 12 included. Everything outside the gate stays where it was: the user's separate `merge-stack` authorization.

## The settle sequence

In order:

1. reconcile tracker + remote state one final time, so both the summary and the ranking are computed from durable truth rather than cached run state, and each PR's body against its diff (Merge behavior);
2. invoke `summarize-wave` with the scope, the PR set, the findings the caller passed, and each body drift step 1 could not edit;
3. **act on its action points before ranking anything** — an action point that un-settles the run hands it back to the caller (Inputs, *un-settling*);
4. request `settle-outstanding-decisions`, passing the summary as its seed **and the run's posting-identity map — its recorded rulings are authored writes, and the map is what they select from** (see `references/posting-identity.md`) — **and every approval-pending reply item in the held-reply records** (not the rejected ones, nor any on a thread that has since become mixed — `references/review-feedback.md`, *Approval-pending replies*), which the walkthrough has no other way to find (`references/review-feedback.md`, *Approval-pending replies*: a held reply is run state) — **and, for each PR whose repository opted into `auto-merge` and whose dependency-view input is unproven, a `DECISION` naming the boundary and asking the owner to answer for the view**, the one discharge that needs a person (Merge behavior); nothing upstream raises it — unless `auto-request-settle` was turned off for this invocation. The `auto-request-settle` gate covers only the request; whether the walkthrough may actually ask is that skill's call — its *Attendance is the precondition* section governs, and a run settling on a scheduled wake gets a one-line decline. **The decline relies on the decisions being durable at their own sites, not in the summary** — held replies excepted, which step 7 lists: the summary and this run's closing report are cached run state, not durable truth, while the worker records, review threads and tracker comments they were read *from* survive and are what the walkthrough's own discovery reads later; what is lost is the aggregation and run-context enrichment — **the draft reply attached to a reserved thread is exactly that**, so a later walkthrough regenerates it from the thread — reading any rejected-draft record there first — rather than treating its absence as work nobody did (`settle-outstanding-decisions`, *What qualifies as an outstanding decision*) — a real cost, accepted deliberately (NOTES: the removed decision docket and what it cost). **Merge every posting-identity entry it returns into the run's map before continuing** — all of them, not the first: one walkthrough can rule at sites needing different transports, a ruling can be the first authored write through a transport this run has not used, and the observation can re-open a review trigger marked provisionally unavailable — which matters immediately, since step 6, and anything the caller does after a merge, issue further writes under whatever identity the map then holds. This step sits between summary and ranking because a ruling changes what the ranking is computed from: it can retire a `DECISION`, reshape a `MERGE_RISK`, or reverse which of two PRs should merge;
5. invoke `plan-merge-order` with the scope, the PR set, **each cross-branch collision the caller passed, marked independent where the caller showed it** (unmarked, that skill treats it as interacting), **the held issue set — anything classified `NEEDS_USER` for a resolved premise, which that skill excludes from its unblock counts** — and every summary item with an ordering consequence — the `MERGE_RISK` and `DECISION` items as the walkthrough left them, and any other class that also carries one. **Translate each ruling back into an action point before invoking** — `plan-merge-order` accepts summary action points and nothing else, and a raw ruling's likely readings are both wrong: keep ranking a PR the owner just rejected, or hold a merge behind a gate they just opened. A settled decision either drops out as a constraint, or becomes the constraint its answer implies — a `MERGE_RISK` carrying the consequence, an ordering requirement stated on the item. **A ruling choosing to re-trigger a stalled round drops out here**: the round stays unanswered, so the gate still holds it, and the caller's supervisor posts the trigger from the ruling's site (`references/review-trigger.md`, *A stalled round*). **A ruling that requires code to change is neither: it is an `IN_FLIGHT_FIX`, and the wave is no longer settled.** Take that row: hand the wave back to the caller exactly as step 3 does, before ranking anything (NOTES: why translating it into a ranking constraint is the step-3 defect arriving one step later) — so the ranking is computed against answers where answers exist and against the open constraint where they do not. **Where the caller does not rank, it passes its translated action points; nothing is ranked** — one PR has no ordering to rank. This skill hands it the walkthrough's rulings here and takes back what its own translation made of them, as gate consequences for step 6 (Inputs, *ranking*); a translated `IN_FLIGHT_FIX` hands the wave back as above;
6. evaluate the gate (see The merge gate) for each open PR whose repository opted into `auto-merge`, or into `ci-mode: integration-branch` where the PR's base is that branch and no integration PR from it is open (Inputs, *resolved policy*; a PR into a branch whose integration PR is open is held, reported `waiting for the integration PR`, and one into a branch whose merges are stopped is held, reported `merges stopped: <refusal>`) — reporting it `not evaluated: no resolved policy passed` where the caller passed none — and merge the PRs it passes (see Merge behavior). A merge the forge refuses, for its method or on a rule, is returned to the caller as that observation and never retried by another method. This step exists here and not earlier because the walkthrough's rulings and the ranking are its inputs; each merge it performs is reported to the caller as it lands, and what a merge does to the rest of the caller's run is the caller's own rule;
7. surface the summary and action points first, then the walkthrough's report where one was requested — rulings recorded, or its one-line decline — then the ranking table, as the run's closing output, with every gate-authorized merge, every explicitly held draft and every published PR whose body this run edited named beside it, and name the still-unruled `DECISION` and decision-shaped `NEEDS_USER` items as the set the owner can settle by running `settle-outstanding-decisions` themselves: it re-asks nothing already ruled. **List from the held-reply records every held reply not yet posted** — thread URL, fix SHA and the one-line text — every rejected one, including those rejected at an earlier settle, as *reply not posted — thread open for you* with thread and SHA, the text where still held, and every mixed-thread fix as *fix pushed — thread left for you (it also asks a question)*, or *(a further change is deferred)* (`references/review-feedback.md`, *Approval-pending replies*: nothing recovers them later). **State the watch where the caller passed it** (Inputs, *watch state*): a settle is not the end of the watch, so say it is still armed, what wakes it and how to stop it.

Summarize before ranking. An action point can change whether something should merge at all, and a ranking the user has already begun acting on is the wrong place to discover that. Run the summary once per settled wave rather than saving one up for the end of a whole backlog: its findings come from run context that the next session will not have, and follow-ups need to exist while later waves are still running, so they get picked up instead of rediscovered.

The ranking is never authorization to merge — the gate is the only thing that is, it is evaluated after the ranking (see Merge behavior), and a repository that did not opt in gets no merge from this run at all.

## Merge behavior

By default orchestration never merges. The merge gate above is the one gate under which it may, and a repository's `auto-merge` key — or, for a PR into its integration branch, `ci-mode: integration-branch` (see `references/agent-policy.md`, *Merge permissions*) — is what makes that gate reachable for its PRs.

Where the gate is reachable, evaluate it at step 6, after the summary, the walkthrough, and the ranking — the gate's `DECISION` and `MERGE_RISK` inputs do not exist before `summarize-wave` produces them, so an earlier evaluation is a guess wearing the gate's name. Merge the PRs it passes in the ranking's order, bottom-up within a stack, restacking descendants exactly as any merge requires; each merge is then reported to the caller like any other (step 6). A PR in a repository that did not opt in is untouched whatever its siblings did — the gate resolves per PR, from that PR's repository.

**Under `ci-mode: deferred`, refresh lazily** — where the mode resolved for the PR and has effect in its repository (`supervise-prs`, *Deferred CI*). Merge back-to-back first, in the ranking's order, every PR the gate passes whose changed files are disjoint from every merge since its green, so its green still discharges the condition. **After a merge, refresh only the PR that merges next** — the overlap update below, made at its gate — never every PR the merge left stale or conflicted; each waits until it is next. **The refreshed PR keeps its turn**: no other PR merges until it has merged, or failed and been reported. Return that PR to the caller as a refresh owed (`supervise-prs`, Inputs) where a repair or a review round is due on it, so the refresh rides in the pass's one push and **the final review round is requested only on the refreshed head**. Restacking a stacked descendant is not a refresh, and still follows every merge (`merge-stack`).

**The gate's dependency-view condition is answered by the caller, per PR, because the machinery that answers it differs between callers and the condition must not** (Inputs, *dependency view*). A validated preflight answers it for one caller, a worker's completeness report for another; the condition means the same thing whichever did. **A view the caller accepted for dispatch as unproven is not discharged for merge**, and the case that matters is `dependency transport unavailable`, which is proceedable for dispatch. The acceptance argument does not carry over, because both of its premises stop at the gate. Blocking dispatch on the warning would halt every run over a forge whose dependency graph the transport cannot read, permanently, while holding a merge degrades exactly to the default no-merge behavior the run has anyway — the PRs still get built, reviewed, summarized and ranked. And dispatch leaves a person standing between every PR and the default branch, which the gate is precisely the removal of. A READY computed from prose alone is a narrower claim than one computed from a corroborated graph, and the merge is where the difference stops being reportable and starts being landed: a blocker nobody wrote into prose is undetectable by construction, and nobody is left downstream to catch it. So a PR whose dependency view rests on such a boundary holds this condition exactly as a `MERGE_RISK` holds the gate — reported with the boundary and the discharge path — and its merge stays the owner's. **The discharge must answer for the whole view, because completeness is what is unproven.** A single user-confirmed edge discharges nothing here: under this boundary caller context is a targeted answer whose omissions prove nothing, and the known-true-case proof needs a working transport to observe the edge through (see `implement-issue-core`, *Back the completeness of the set*), so a re-invocation carrying one edge returns the same unproven report and the gate stays closed while the record claims a path out. Two things actually discharge it: a run whose dependency transport can read the graph and prove the boundary; or the owner explicitly answering for the view itself — a decision-shaped hold this sequence already knows how to carry, surfaced as a `DECISION` naming the boundary, ruled through the walkthrough or answered directly, with the recorded ruling retiring the hold exactly as the translation rules retire a constraint (step 5 here, or the translated action points a caller that does not rank passed back). That ruling retires this condition and nothing more: the repository's opt-in and every other gate condition still govern, since a ruling never opens the gate. **A standing answer is not one of the two discharges.** Where the owner wants this condition lifted for every future run rather than for this wave, that is a change to what the gate requires, and this skill has no mechanism for it — deliberately. The merge gate is the gate's only definition, and a second site that can subtract a condition from it is a bypass whoever writes that site controls. Report what would be needed and leave the condition standing; a ruling discharges this wave and says nothing about the next one. **If such a mechanism is ever built, its removal trigger has to be something a preflight can execute itself** — not a condition needing the very capability whose absence justified the lift, and not a human assertion, an issue being closed included, since issue state is queryable and still somebody's say-so one step removed. The gate means the same thing whichever caller supplies the condition — which is the point of the shared `auto-merge` grant.

**Green is a statement about a tree, not about a PR** — this paragraph through the tool-bump one apply where the caller's freshness input says the stale-green re-check does (Inputs, *freshness checks*). The gate requires green CI on the current head, and a PR's head can be unchanged while the tree its green describes has ceased to exist: the base moved underneath it. Three merges later the forge still reports that PR mergeable and green, because nothing it touched was touched by the intervening merges — and the result is a statement about a tree that no longer exists anywhere.

So before merging on an existing green, compare the PR's base to the current head of its base branch. **Where they differ, the green is stale and does not discharge the condition.** What discharges it depends on what the checks actually run against, which is a property of the repository's CI configuration and is established rather than assumed (`references/establish-do-not-assume.md`): where checks run against the PR merged with its base, re-running them produces a result about the tree that will exist, and a re-run is enough; where they run against the branch alone, a re-run proves exactly what the stale one did, and the branch has to be updated before the green means anything. **Update it only where the caller passed authority to** (Inputs, *freshness checks*); otherwise report the PR as stale — naming the moved base — and hold it. This skill never updates a branch on its own authority. Establish which, once per repository, and record it beside the other per-repository observations.

**Under `ci-mode: deferred`, a moved base makes the green stale only on overlap** — where the mode resolved for the PR and it and its overlap narrowing have effect in its repository (Inputs, *resolved policy*); this is the owner's opt-in narrowing of the check above. Overlap means the set of files changed on the base since the base the green run tested intersects the set of files the PR changes. **No overlap**: the green discharges the condition, and the PR merges on it. **Overlap**: the green is stale, and CI runs once more before the gate opens, **always by updating the branch from its base**, whichever ref the repository's checks run against: the update's merge commit carries no token, so its run tests the merged tree. Never a dispatch, which checks out the branch alone. Update only under the authority rule above; without it, report the PR stale and hold it. A review round carries forward across that update (`references/ci-and-review-verdicts.md`, *A review is clean*). The tool-bump rule below applies either way. Under any other mode, or either without effect, the paragraph above governs unchanged. **Every branch update this skill makes is returned to the caller as a caller push**, tagged by `references/mechanical-pushes.md`, for its supervisor to adopt.

**Under `ci-mode: integration-branch`, the stale-green re-check does not apply to a PR into the integration branch**: its gate record attaches to its head, a moved base does not stale it (`references/ci-and-review-verdicts.md`, *CI is green*), and the caller's full gate on the integration branch tests the combination before the integration PR opens. A conflict still holds it, and its refresh is the lazy one above, except that the update's merge commit carries the token where one applies (`supervise-prs`, *Integration-branch CI*, step 1), so it starts no run and the record carries across it as a mechanical push. **The integration PR is re-checked as any PR is, and never refreshed for it**: this skill neither updates its branch nor re-runs its CI, so a stale green holds it, reported as owed to the owner.

This is not the rejected rule that every branch be up to date before merging, which serialises every merge behind every other. It is narrower: the freshness check is paid at the gate, on the PRs the gate is about to open for, and only where the base has actually moved.

**Where the caller passed an integration check's result, that result is a statement about a tree too** (Inputs, *freshness checks*). It carries the head SHA of every branch the check integrated, not just their names — the set can be unchanged while a tip has moved, which is what another session opening or force-pushing a PR does to it. At the gate, compare the current set and each tip against those SHAs; where the set or any tip differs, or a result arrived without them, the clean result describes a combination nobody tested and the check the caller passed is re-run before anything merges. A cached clean result over a moved tip is the same failure the check exists for, arriving through the check itself.

**A bump to any tool whose output is a required check always needs a fresh run, however small its diff.** A formatter or linter upgrade verified against a tree that does not contain the code it will format has verified nothing that matters — and it is exactly the PR most likely to look safe: a one-line manifest change, conflicting with nothing, green. Two such sat three merges behind a default branch that had gained several thousand lines in between. This is the one case where the diff's size is evidence in the wrong direction.

**The PR-body reconcile runs at step 1, for every PR, before anything publishes or merges.** Re-read each body against its current diff whether or not a repair flagged drift (NOTES). Where they disagree, `references/authored-write-form.md`, *Editing a PR body after it is created*, decides: an allowed edit is made — or the PR held, saying why — and one to a published PR is named at step 7 — which PR, what changed, and why; where it forbids one, the drift goes to step 2 with a suggested replacement, which `summarize-wave` reports as a `MERGE_RISK`. **An unreconciled body holds that PR** — a body contradicting its own diff is not a clean PR, whatever CI says.

**A merge never happens on a draft.** For each PR the gate passes, the merge path **publishes it to ready first, then merges** — publishing is part of the merge path, not a precondition that might already hold, so a PR still in draft when its gate opens is published by the act of merging it, never skipped for being a draft. A PR `create-pr` opened ready under a merge grant has nothing to publish, so the step is a no-op for it. This is one of the three forms of promotion (see `references/draft-state.md`, *Promotion* — the others are the owner doing it themselves, and the run carrying out a repository's own promotion convention), and it never reaches an **explicitly held draft**: the gate already excludes those, so the merge path neither publishes nor merges one — report each as held, awaiting the owner.

**Publishing is inert unless the repository's own configuration says it starts something.** This governs every publish of a PR in the set, whoever performed it — the merge path's, the owner's, or one under a promotion convention. A publish changes no head, so **a completed clean review on the current head still satisfies the gate after it**, and publishing never by itself requires another round. What re-opens the review condition is unchanged: a push after the review still needs re-review (`references/review-trigger.md`; `references/ci-and-review-verdicts.md`, *A review is clean*). Only three sources say publishing starts something:

- **`publish-triggers-review` resolved `true`** (Inputs, *resolved policy*), or the repository's `CLAUDE.md` or `AGENTS.md` on the base stating that publishing starts a review: a fresh automated review round on the current head, completed after the latest publish, is required before the gate opens — the round the publish starts, or, where none has appeared within the window of `references/review-trigger.md`, *Confirming a trigger took effect*, one triggered under that rule;
- **a workflow triggering on `pull_request` with type `ready_for_review`**, read from the workflow files on the base and the head as `references/ci-and-review-verdicts.md`, *Path filters*, reads filters, either one counting, or those docs naming a check publishing starts: **only the checks that event starts gate the merge**. The gate's CI condition reads their runs on the current head as it reads any — a required check only that event starts is owed after the publish, not before it — and no clean review is re-requested;
- **nothing else is evidence** — a review provider's or bot's description of itself in a PR comment included. Docs count only as evidence that a publish starts something: one saying it starts nothing never outweighs a workflow file that says otherwise. Publishing is inert, and the PR publishes and merges on the evidence the gate accepted.

Where publishing starts something, the merge waits for a later pass, is **never awaited inline**, and is never decided by an immediate read, which a run the publish started need not exist for yet (`references/absence-is-not-a-verdict.md`): the published PR returns to the caller and is re-evaluated when the caller settles again, through whatever watches the PR for it; where the caller has no later pass, it is returned named as published and awaiting re-evaluation. What publishing starts is recorded per repository, like the transport and identity maps.

A re-review that finds something is the system working: that PR is no longer clean, it does not merge, and it returns to the ordinary repair path — now as a ready PR, since publishing is not undone.

`merge-stack` authors forge writes of its own — the merges, and the retargeting and body edits it makes on descendant PRs — so pass it the run's posting-identity map and merge the observations it returns, exactly as for implementation and repair workers (NOTES).

**The merge gate is itself the authorization `merge-stack` needs, for exactly the PRs it passed.** Every merge and restack this skill performs goes through that skill (Composed skills), and a gate-approved merge must restack its descendants like any other, so without this a repository that opted in would have no compliant way to perform the merge its own policy authorized. The grant is scoped to the gate-approved set and nothing wider: it does not extend to a sibling the gate excluded, to a repository that did not opt in, or to any stack operation outside that merge. Where the user separately authorizes `merge-stack`, that authorization is the ordinary one and is unaffected by this. Reconcile tracker completion after every merge, gate-authorized ones included.
