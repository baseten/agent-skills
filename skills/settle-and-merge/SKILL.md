# Settle and Merge

Close out a finished run over a set of PRs: summarize it, put its outstanding decisions to the owner, rank it, and merge what the gate passes.

This file is the contract; the reasoning and incident history behind its rules live in `NOTES.md` beside it, keyed by section. NOTES explains; it never overrides.

**The caller decides when; this skill decides what settling does.** It has two callers, and the sequence is the same for both. Neither owns a copy of it.

## Callers and inputs

"Tranche" below means the set of PRs the caller passes. A one-issue run is a tranche of one. This skill uses the policy its caller resolved and never reads `.claude/agent-policy.json` itself (`references/agent-policy.md`, *Resolution*).

| input | `backlog-orchestrator` | `implement-issue` |
| --- | --- | --- |
| when to settle | *Settled tranche*, which owns the settled predicate | *Settle*: its one issue reached a terminal state |
| the PR set and scope | the manifest/scope and this run's PR set | the canonical issue URL and its one PR |
| findings | the worker and review findings the run produced | the worker and review findings the run produced |
| posting-identity map | the run's map (`references/posting-identity.md`) | the run's map |
| resolved policy | `auto-merge` per PR and `auto-request-settle` per run (`references/agent-policy.md`) | the same keys, resolved for its one PR (`implement-issue`, *Policy and budgets*) |
| ranking inputs (step 5) | the cross-branch collisions, the held issue set, and the translated rulings | none: step 5 does not run |
| the dependency-view supplier (Merge behavior) | the validated preflight | core's completeness report (`implement-issue`, *Merge*) |
| un-settling (steps 3 and 5) | *The summary can un-settle the run*, and *A settle finding is the third repair shape* | *Settle* (un-settling, and its re-entry rule) |

| the stale-green re-check, the integration check's head SHAs, and the tool-bump paragraph (Merge behavior) | apply; the integration check is `backlog-orchestrator`, *Cross-branch artifact collisions* | do not apply: it runs no integration check and has no authority to update a branch |

`implement-issue` reads the tranche-phrased clauses for one issue, and those readings are its own (`implement-issue`, *Merge*). It does not run step 5, and what it does in its place is its ruling translation (`implement-issue`, *Settle*).

## Composed skills

- `summarize-tranche`, then `settle-outstanding-decisions` while `auto-request-settle` is on, then `plan-merge-order` — in that order, the last never under `implement-issue` (step 5);
- `merge-stack` for any merge this skill performs — required wherever the resolved `auto-merge` leaves the gate reachable. The caller checks it at its preflight, where policy resolves, never discovers it at the gate; what an unavailable one does to the run is the caller's (`backlog-orchestrator`, *Model and skill policy*; `implement-issue`, *Composed skills — all required*).

## The merge gate

**Merges are opt-in per repository, and gated even then.** By default the run performs no merge. It may merge a PR only when that PR's own repository opted in via `auto-merge` in its policy config (see `references/agent-policy.md`, *Merge permissions*) — **the repository's opt-in is the only route to a merge: an invocation argument can switch `auto-merge` off for a run, narrowing the gate, but never on — an invocation cannot open it** (`references/agent-policy.md`, *Precedence*, states the same exemption) — **and** the gate holds: the tranche has no `DECISION`, `MERGE_RISK`, or `NEEDS_USER` item outstanding — anywhere in the tranche, not only on that PR, and a `DECISION` that settled without being ruled on is outstanding: unruled is not clean — **and** CI is green on the PR's current head, **and** it has no merge conflict, **and** its review is clean (**every automated review round the PR's routing requires, completed** — `create-pr` owns the routing, and where it puts two conventions on one PR, the faster one completing is not this condition met — every actionable finding resolved or answered, no thread reserved for the owner), **and** no recovery ref for its branch is outstanding (see `backlog-orchestrator`, *Checkpoint compliance* — captured work that never reached the head is work a merge would silently drop), **and** it is not an **explicitly held draft** (see `backlog-orchestrator`, *Draft state*) — a held draft is neither published nor merged, and is reported as held — **and** the dependency view the PR was built on is proven complete or explicitly answered for (see Merge behavior, which names each consumer's supplier; a view unproven because the run's dependency transport is unavailable is accepted for dispatch and still holds this condition — proceedable is not mergeable). This is the gate's only definition; every other site defers to it, `backlog-orchestrator`'s invariant 12 included. Everything outside the gate stays where it was: the user's separate `merge-stack` authorization.

## The settle sequence

In order:

1. reconcile tracker + remote state one final time, so both the summary and the ranking are computed from durable truth rather than cached run state;
2. invoke `summarize-tranche` with the manifest/scope, this run's PR set, and the worker/review findings it produced;
3. **act on its action points before ranking anything** — an action point that un-settles the run hands it back to the caller, whose un-settle rule governs (`backlog-orchestrator`, *The summary can un-settle the run*; `implement-issue`, *Settle*);
4. request `settle-outstanding-decisions`, passing the summary as its seed **and the run's posting-identity map — its recorded rulings are authored writes, and the map is what they select from** (see `references/posting-identity.md`) — unless `auto-request-settle` was turned off for this invocation. The `auto-request-settle` gate covers only the request; whether the walkthrough may actually ask is that skill's call — its *Attendance is the precondition* section governs, and a run settling on a scheduled wake gets a one-line decline. **The decline relies on the decisions being durable at their own sites, not in the summary**: the summary and this run's closing report are cached run state by invariant 1 (`backlog-orchestrator`, *Core invariants*), while the worker records, review threads and tracker comments they were read *from* survive and are what the walkthrough's own discovery reads later; what is lost is the aggregation and run-context enrichment — **the draft reply attached to a reserved thread is exactly that**, so a later walkthrough regenerates it from the thread — reading any rejected-draft record there first — rather than treating its absence as work nobody did (`settle-outstanding-decisions`, *What qualifies as an outstanding decision*) — a real cost, accepted deliberately (NOTES: the removed decision docket and what it cost). **Merge every posting-identity entry it returns into the run's map before continuing** — all of them, not the first: one walkthrough can rule at sites needing different transports, a ruling can be the first authored write through a transport this run has not used, and the observation can re-open a review trigger marked provisionally unavailable — which matters immediately, since step 6 and any later frontier advance issue further writes under whatever identity the map then holds. This step sits between summary and ranking because a ruling changes what the ranking is computed from: it can retire a `DECISION`, reshape a `MERGE_RISK`, or reverse which of two PRs should merge;
5. invoke `plan-merge-order` with the manifest/scope, this run's PR set, **each cross-branch collision, marked independent where `backlog-orchestrator`, *Cross-branch artifact collisions*, showed it** (unmarked, that skill treats it as interacting), **the held issue set — anything classified `NEEDS_USER` for a resolved premise, which that skill excludes from its unblock counts** — and every summary item with an ordering consequence — the `MERGE_RISK` and `DECISION` items as the walkthrough left them, and any other class that also carries one. **Translate each ruling back into an action point before invoking** — `plan-merge-order` accepts summary action points and nothing else, and a raw ruling's likely readings are both wrong: keep ranking a PR the owner just rejected, or hold a merge behind a gate they just opened. A settled decision either drops out as a constraint, or becomes the constraint its answer implies — a `MERGE_RISK` carrying the consequence, an ordering requirement stated on the item. **A ruling that requires code to change is neither: it is an `IN_FLIGHT_FIX`, and the tranche is no longer settled.** Take that row: hand the tranche back to the caller exactly as step 3 does, whose un-settle rule governs (`backlog-orchestrator`, *The summary can un-settle the run* and *A settle finding is the third repair shape*), before ranking anything (NOTES: why translating it into a ranking constraint is the step-3 defect arriving one step later) — so the ranking is computed against answers where answers exist and against the open constraint where they do not. **`implement-issue` does not run this step** — one PR has no ordering to rank — and translates its rulings into gate consequences instead (`implement-issue`, *Settle*);
6. evaluate the gate (see The merge gate) for each open PR whose repository opted into `auto-merge`, and merge the PRs it passes (see Merge behavior). This step exists here and not earlier because the walkthrough's rulings and the ranking are its inputs; each merge it performs is consumed as a frontier-advancing event like any other (`backlog-orchestrator`, *Frontier advance on merge*);
7. surface the summary and action points first, then the walkthrough's report where one was requested — rulings recorded, or its one-line decline — then the ranking table, as the run's closing output, with every gate-authorized merge and every explicitly held draft named beside it, and name the still-unruled `DECISION` and decision-shaped `NEEDS_USER` items as the set the owner can settle by running `settle-outstanding-decisions` themselves: it is idempotent, so running it after a declined or interrupted walkthrough re-asks nothing already ruled.

Summarize before ranking. An action point can change whether something should merge at all, and a ranking the user has already begun acting on is the wrong place to discover that. Run the summary once per settled tranche rather than saving one up for the end of a whole backlog: its findings come from run context that the next session will not have, and follow-ups need to exist while later tranches are still running, so they get picked up instead of rediscovered.

The ranking is never authorization to merge — the gate is the only thing that is, it is evaluated after the ranking (see Merge behavior), and a repository that did not opt in gets no merge from this run at all.

## Merge behavior

By default orchestration never merges. The merge gate above is the one gate under which it may, and a repository's `auto-merge` key (see `references/agent-policy.md`, *Merge permissions*) is what makes that gate reachable for its PRs.

Where the gate is reachable, evaluate it at the settled step, after the summary, the walkthrough, and the ranking — the gate's `DECISION` and `MERGE_RISK` inputs do not exist before `summarize-tranche` produces them, so an earlier evaluation is a guess wearing the gate's name. Merge the PRs it passes in the ranking's order, bottom-up within a stack, restacking descendants exactly as any merge requires; each merge is then an ordinary frontier-advancing event (see `backlog-orchestrator`, *Frontier advance on merge*). A PR in a repository that did not opt in is untouched whatever its siblings did — the gate resolves per PR, from that PR's repository.

**The gate's dependency-view condition names its supplier per consumer, because the machinery differs and the condition must not.** Under `backlog-orchestrator` it is discharged by the validated preflight: an unproven relationship boundary over dispatchable scope is a `FAIL` that never reaches dispatch, a proof invalidated mid-run raises the *unproven dependency view* `NEEDS_USER` that the gate's outstanding-item test already refuses, and a frontier advance re-validates before anything new dispatches — so for boundaries with a working dependency transport the condition costs the gate nothing it was not already paying. What it changes is the one case the preflight deliberately accepts: **`dependency transport unavailable` is proceedable for dispatch and is not discharged for merge.** The acceptance argument does not carry over, because both of its premises stop at the gate. Blocking dispatch on the warning would halt every GitHub backlog permanently, while holding a merge degrades exactly to the default no-merge behavior the run has anyway — the PRs still get built, reviewed, summarized and ranked. And dispatch leaves a person standing between every PR and the default branch, which the gate is precisely the removal of. A READY computed from prose alone is a narrower claim than one computed from a corroborated graph, and the merge is where the difference stops being reportable and starts being landed: a blocker nobody wrote into prose is undetectable by construction, and nobody is left downstream to catch it. So a PR whose dependency view rests on such a boundary holds this condition exactly as a `MERGE_RISK` holds the gate — reported with the boundary and the discharge path — and its merge stays the owner's. **The discharge must answer for the whole view, because completeness is what is unproven.** A single user-confirmed edge discharges nothing here: under this boundary caller context is a targeted answer whose omissions prove nothing, and the known-true-case proof needs a working transport to observe the edge through (see `implement-issue-core`, *Back the completeness of the set*), so a re-invocation carrying one edge returns the same unproven report and the gate stays closed while the record claims a path out. Two things actually discharge it: a run whose dependency transport can read the graph and prove the boundary; or the owner explicitly answering for the view itself — a decision-shaped hold the settled step already knows how to carry, surfaced as a `DECISION` naming the boundary, ruled through the walkthrough or answered directly, with the recorded ruling retiring the hold exactly as the translation rules retire a constraint (step 5 here; `implement-issue`, *Settle*, its ruling translation). That ruling retires this condition and nothing more: the repository's opt-in and every other gate condition still govern, since a ruling never opens the gate. **A standing answer is not one of the two discharges.** Where the owner wants this condition lifted for every future run rather than for this tranche, that is a change to what the gate requires, and this skill has no mechanism for it — deliberately. The merge gate is the gate's only definition, and a second site that can subtract a condition from it is a bypass whoever writes that site controls. Report what would be needed and leave the condition standing; a ruling discharges this tranche and says nothing about the next one. **If such a mechanism is ever built, its removal trigger has to be something a preflight can execute itself** — not a condition needing the very capability whose absence justified the lift, and not a human assertion, an issue being closed included, since issue state is queryable and still somebody's say-so one step removed. `implement-issue` supplies the same condition from its worker's completeness report (see `implement-issue`, *Merge*), so the gate means the same thing whichever consumer evaluates it — which is the point of the shared `auto-merge` grant.

**Green is a statement about a tree, not about a PR** — this paragraph through the tool-bump one apply under `backlog-orchestrator` only (Callers and inputs). The gate requires green CI on the current head, and a PR's head can be unchanged while the tree its green describes has ceased to exist: the base moved underneath it. Three merges later the forge still reports that PR mergeable and green, because nothing it touched was touched by the intervening merges — and the result is a statement about a tree that no longer exists anywhere.

So before merging on an existing green, compare the PR's base to the current head of its base branch. **Where they differ, the green is stale and does not discharge the condition.** What discharges it depends on what the checks actually run against, which is a property of the repository's CI configuration and is established rather than assumed (`references/establish-do-not-assume.md`): where checks run against the PR merged with its base, re-running them produces a result about the tree that will exist, and a re-run is enough; where they run against the branch alone, a re-run proves exactly what the stale one did, and the branch has to be updated before the green means anything. Establish which, once per repository, and record it beside the other per-repository observations.

This is not the rejected rule that every branch be up to date before merging, which serialises every merge behind every other. It is narrower: the freshness check is paid at the gate, on the PRs the gate is about to open for, and only where the base has actually moved.

**The integration check's result is a statement about a tree too** (the check is `backlog-orchestrator`, *Cross-branch artifact collisions*). Record the head SHA of every branch it integrated, not just their names — the set can be unchanged while a tip has moved, which is what another session opening or force-pushing a PR does to it. At the gate, compare the current set and each tip against what was recorded; where the set or any tip differs, the clean result describes a combination nobody tested and the check is re-run before anything merges. A cached clean result over a moved tip is the same failure the check exists for, arriving through the check itself.

**A bump to any tool whose output is a required check always needs a fresh run, however small its diff.** A formatter or linter upgrade verified against a tree that does not contain the code it will format has verified nothing that matters — and it is exactly the PR most likely to look safe: a one-line manifest change, conflicting with nothing, green. Two such sat three merges behind a default branch that had gained several thousand lines in between. This is the one case where the diff's size is evidence in the wrong direction.

**Re-read the PR body against its current diff before publishing or merging, and always where a repair pass reported changing a behaviour the body asserts** (`repair-pr` returns that flag rather than editing the body, since a PR with rounds left does not need its body correct yet). The body is the first thing a human reviewer reads and nothing in the repair path re-reads it, so a body written at round 0 can end up arguing for a design the rounds removed. **Update it, or hold the PR and say why** — an update is an authored write, in the form `references/authored-write-form.md` states — a body contradicting its own diff is not a clean PR, whatever CI says. This is the last point at which the fix is cheap, and it is the same comparison the charter check (`backlog-orchestrator`, *PR promotion and central supervision*) has already been making.

**A merge never happens on a draft.** For each PR the gate passes, the merge path **publishes it to ready first, then merges** — publishing is part of the merge path, not a precondition that might already hold, so a PR still in draft when its gate opens is published by the act of merging it, never skipped for being a draft. This is one of the three forms of promotion (see `backlog-orchestrator`, *Draft state* — the others are the owner doing it themselves, and this run carrying out a repository's own promotion convention), and it never reaches an **explicitly held draft**: the gate already excludes those, so the merge path neither publishes nor merges one — report each as held, awaiting the owner.

**Publishing may not be inert, and whether it is is a fact about this repository** — the three states below govern `backlog-orchestrator`'s publish (Callers and inputs). Marking a draft ready is an event some review providers and some CI configurations act on and others do not — `create-pr` mentions the possibility and names no provider, so it is not evidence that any given repository behaves that way (`references/establish-do-not-assume.md`). **There are three states here, and the third is where a first run and every restart begin:**

- **Observed to trigger.** Publishing un-settles the tranche for that PR: the clean-review and green-CI evidence the gate just accepted describes the PR as it was one moment before it changed, so merging on it is merging on a reading publishing invalidated. The merge waits for a later pass and is **not awaited inline** — a wait with no observable completion condition either re-reads the same stale evidence a moment later and merges anyway, or blocks the run indefinitely, which `backlog-orchestrator`, *Arming the wait when nothing is in flight*, already forbids outright.
- **Observed not to trigger.** Publish and merge. No evidence is coming, and a timeout would end in a merge on evidence nothing invalidated.
- **Unknown.** Not having observed a trigger is not evidence that publishing is inert (`references/absence-is-not-a-verdict.md`), and merging straight through on pre-publish evidence would land the PR before a run that publishing started could report. **Take the un-settle branch and establish it from there:** publish, un-settle the tranche for that PR as the first state does, and classify the repository on the next delivered pass — a queued run or review may not yet exist at the moment of publishing, so a read taken there can only distinguish *nothing was triggered* from *nothing has appeared yet* by accident, and the answer it records is the one every later publish in this repository will be decided by. This is the same rule `implement-issue` states for draft→ready under *Evidence freshness*: the read that settles it is taken no earlier than the next check-in, and a run that cannot keep watching returns the checkpoint with the PR named as published and awaiting re-evaluation. One pass, and the repository is in one of the two states above for good.

The observation is recorded per repository, like the transport and identity maps.

The machinery for the first case already exists — the PR's own subscription and the settled-condition check (`backlog-orchestrator`, *Settled tranche*) — and is not something the merge path holds open.

A re-review that finds something is the system working: that PR is no longer clean, it does not merge, and it returns to the ordinary repair path — now as a ready PR, since publishing is not undone.

`merge-stack` authors forge writes of its own — the merges, and the retargeting and body edits it makes on descendant PRs — so pass it the run's posting-identity map and merge the observations it returns, exactly as for implementation and repair workers. It is easy to miss because it is invoked as an operation on the graph rather than as a worker that reports; the writes are no less authored for that.

**The merge gate is itself the authorization `merge-stack` needs, for exactly the PRs it passed.** The stack rules (`backlog-orchestrator`, *Stack mutation while PRs are open*) require that skill for any merge or restack, and a gate-approved merge must restack its descendants like any other, so without this a repository that opted in would have no compliant way to perform the merge its own policy authorized. The grant is scoped to the gate-approved set and nothing wider: it does not extend to a sibling the gate excluded, to a repository that did not opt in, or to any stack operation outside that merge. Where the user separately authorizes `merge-stack`, that authorization is the ordinary one and is unaffected by this. Reconcile tracker completion after every merge, gate-authorized ones included.
