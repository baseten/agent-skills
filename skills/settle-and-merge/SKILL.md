# Settle and Merge

Close out a finished run over a set of PRs: summarize it, put its outstanding decisions to the owner, rank it, and merge what the gate passes.

This file is the contract; the reasoning and incident history behind its rules live in `NOTES.md` beside it, keyed by section. NOTES explains; it never overrides.

**The caller decides when; this skill decides what settling does.** It has two callers, and the sequence is the same for both. Neither owns a copy of it.

## Inputs

**Everything that differs between callers arrives as an input; this skill never reads its caller's contract to find out what to do.** "Tranche" below means the set of PRs the caller passes. A one-issue run is a tranche of one, and every tranche-phrased clause reads for that one PR. Each caller states in its own text what it passes for each input. **An input the caller did not pass takes the default in the last column** — never a value inferred from which skill the caller is.

| input | what the caller passes | where it is absent |
| --- | --- | --- |
| **PR set and scope** | the PRs to settle, and the scope they were built for — a manifest, an issue URL | there is nothing to settle: return, naming the missing input |
| **findings** | the worker and review findings the run produced | summarize from durable state alone, and say the run's own findings were not passed |
| **posting-identity map** | the run's map (`references/posting-identity.md`) | start from an empty map: every entry is `unestablished`, and writes degrade as that rule states |
| **resolved policy** | `auto-merge` per PR and `auto-request-settle` for the run, as the caller resolved them. This skill never reads `.claude/agent-policy.json` itself (`references/agent-policy.md`, *Resolution*) | `auto-merge` is off — an unmentioned permission was not granted — and `auto-request-settle` is on, its built-in default — the walkthrough's own attendance precondition still decides whether anything is asked |
| **ranking** | whether step 5 runs. Where it does: each cross-branch collision the caller found, marked independent where the caller showed it, and the held issue set — anything classified `NEEDS_USER` for a resolved premise. Where it does not: the caller's own ruling translation, which runs in step 5's place | step 5 runs. A caller that does not rank and passes no ruling translation still gets step 5, because an untranslated ruling reads as clean at the gate. An unpassed collision set is reported as not checked, never as none |
| **dependency view, per PR** | whether the view the PR was built on is proven complete or unproven on a named boundary, what answered that, and the discharge where one exists (Merge behavior) | unproven: the gate's dependency-view condition holds that PR |
| **freshness checks** | which gate-time freshness rules apply, and the result of each check the caller ran. The stale-green re-check (with the tool-bump rule it carries) applies or does not. An integration check's result comes with the head SHA of every branch it integrated and with the check itself, so it can be re-run here. Or "none apply", with the reason | the stale-green re-check and the tool-bump rule apply — absent is not "none apply". No integration result was passed, so there is none to compare, and the report says no integration check was passed |
| **publish rule** | the caller's own rule for the merge path's publish of a draft, where it has one | the three-state rule under Merge behavior governs |
| **recovery-ref ender** | the caller's own ender for a recovery ref, where it keys one on PR state, replacing `swarm`'s generic one (`swarm`, *Checkpoint compliance*, *The recovery ref's lifecycle*) | `swarm`'s generic lifecycle ends the ref |
| **un-settling** | the caller's un-settle rule — where the tranche goes when a step un-settles it (step 3, step 5) | return to the caller at that step, the finding verbatim, having ranked and merged nothing |

Work a caller runs alongside a step — a reconciliation of its own at step 1, say — is stated in the caller's text and run by the caller. It changes nothing here.

## Composed skills

- `summarize-tranche`, then `settle-outstanding-decisions` while `auto-request-settle` is on, then `plan-merge-order` where the caller ranks — in that order (step 5);
- `merge-stack` for any merge or restack this skill performs — required wherever the resolved `auto-merge` leaves the gate reachable. The caller checks it at its preflight, where policy resolves, and never discovers it at the gate. What an unavailable one does to the run is the caller's to state.

## The merge gate

**Merges are opt-in per repository, and gated even then.** By default the run performs no merge. It may merge a PR only when that PR's own repository opted in via `auto-merge` in its policy config (see `references/agent-policy.md`, *Merge permissions*) — **the repository's opt-in is the only route to a merge: an invocation argument can switch `auto-merge` off for a run, narrowing the gate, but never on — an invocation cannot open it** (`references/agent-policy.md`, *Precedence*, states the same exemption) — **and** the gate holds: the tranche has no `DECISION`, `MERGE_RISK`, or `NEEDS_USER` item outstanding — anywhere in the tranche, not only on that PR, and a `DECISION` that settled without being ruled on is outstanding: unruled is not clean — **and** CI is green on the PR's current head, **and** it has no merge conflict, **and** its review is clean (**every automated review round the PR's routing requires, completed** — `create-pr` owns the routing, and where it puts two conventions on one PR, the faster one completing is not this condition met — every actionable finding resolved or answered, no thread reserved for the owner), **and** no recovery ref for its branch is outstanding (`swarm`, *Checkpoint compliance*, names the ref, and its *The recovery ref's lifecycle* says what ends one, with the caller's own ender where it passed one (Inputs) — captured work that never reached the head is work a merge would silently drop), **and** it is not an **explicitly held draft** (see `references/draft-state.md`, *Explicitly held drafts*) — a held draft is neither published nor merged, and is reported as held — **and** the dependency view the PR was built on is proven complete or explicitly answered for (the caller passes it per PR, and Merge behavior says what discharges it; a view unproven because the run's dependency transport is unavailable may have been accepted for dispatch and still holds this condition — proceedable is not mergeable). This is the gate's only definition; every other site defers to it, `backlog-orchestrator`'s invariant 12 included. Everything outside the gate stays where it was: the user's separate `merge-stack` authorization.

## The settle sequence

In order:

1. reconcile tracker + remote state one final time, so both the summary and the ranking are computed from durable truth rather than cached run state;
2. invoke `summarize-tranche` with the scope, the PR set, and the findings the caller passed;
3. **act on its action points before ranking anything** — an action point that un-settles the run hands it back to the caller, whose un-settle rule governs (Inputs, *un-settling*);
4. request `settle-outstanding-decisions`, passing the summary as its seed **and the run's posting-identity map — its recorded rulings are authored writes, and the map is what they select from** (see `references/posting-identity.md`) — unless `auto-request-settle` was turned off for this invocation. The `auto-request-settle` gate covers only the request; whether the walkthrough may actually ask is that skill's call — its *Attendance is the precondition* section governs, and a run settling on a scheduled wake gets a one-line decline. **The decline relies on the decisions being durable at their own sites, not in the summary**: the summary and this run's closing report are cached run state, not durable truth, while the worker records, review threads and tracker comments they were read *from* survive and are what the walkthrough's own discovery reads later; what is lost is the aggregation and run-context enrichment — **the draft reply attached to a reserved thread is exactly that**, so a later walkthrough regenerates it from the thread — reading any rejected-draft record there first — rather than treating its absence as work nobody did (`settle-outstanding-decisions`, *What qualifies as an outstanding decision*) — a real cost, accepted deliberately (NOTES: the removed decision docket and what it cost). **Merge every posting-identity entry it returns into the run's map before continuing** — all of them, not the first: one walkthrough can rule at sites needing different transports, a ruling can be the first authored write through a transport this run has not used, and the observation can re-open a review trigger marked provisionally unavailable — which matters immediately, since step 6 and any later frontier advance issue further writes under whatever identity the map then holds. This step sits between summary and ranking because a ruling changes what the ranking is computed from: it can retire a `DECISION`, reshape a `MERGE_RISK`, or reverse which of two PRs should merge;
5. invoke `plan-merge-order` with the scope, the PR set, **each cross-branch collision the caller passed, marked independent where the caller showed it** (unmarked, that skill treats it as interacting), **the held issue set — anything classified `NEEDS_USER` for a resolved premise, which that skill excludes from its unblock counts** — and every summary item with an ordering consequence — the `MERGE_RISK` and `DECISION` items as the walkthrough left them, and any other class that also carries one. **Translate each ruling back into an action point before invoking** — `plan-merge-order` accepts summary action points and nothing else, and a raw ruling's likely readings are both wrong: keep ranking a PR the owner just rejected, or hold a merge behind a gate they just opened. A settled decision either drops out as a constraint, or becomes the constraint its answer implies — a `MERGE_RISK` carrying the consequence, an ordering requirement stated on the item. **A ruling that requires code to change is neither: it is an `IN_FLIGHT_FIX`, and the tranche is no longer settled.** Take that row: hand the tranche back to the caller exactly as step 3 does, whose un-settle rule governs, before ranking anything (NOTES: why translating it into a ranking constraint is the step-3 defect arriving one step later) — so the ranking is computed against answers where answers exist and against the open constraint where they do not. **A caller that does not rank does not run this step** — one PR has no ordering to rank — and the ruling translation it passed runs in its place, turning its rulings into gate consequences before step 6 (Inputs, *ranking*);
6. evaluate the gate (see The merge gate) for each open PR whose repository opted into `auto-merge`, and merge the PRs it passes (see Merge behavior). This step exists here and not earlier because the walkthrough's rulings and the ranking are its inputs; each merge it performs is reported to the caller as it lands, and what a merge does to the rest of the caller's run is the caller's own rule;
7. surface the summary and action points first, then the walkthrough's report where one was requested — rulings recorded, or its one-line decline — then the ranking table, as the run's closing output, with every gate-authorized merge and every explicitly held draft named beside it, and name the still-unruled `DECISION` and decision-shaped `NEEDS_USER` items as the set the owner can settle by running `settle-outstanding-decisions` themselves: it is idempotent, so running it after a declined or interrupted walkthrough re-asks nothing already ruled.

Summarize before ranking. An action point can change whether something should merge at all, and a ranking the user has already begun acting on is the wrong place to discover that. Run the summary once per settled tranche rather than saving one up for the end of a whole backlog: its findings come from run context that the next session will not have, and follow-ups need to exist while later tranches are still running, so they get picked up instead of rediscovered.

The ranking is never authorization to merge — the gate is the only thing that is, it is evaluated after the ranking (see Merge behavior), and a repository that did not opt in gets no merge from this run at all.

## Merge behavior

By default orchestration never merges. The merge gate above is the one gate under which it may, and a repository's `auto-merge` key (see `references/agent-policy.md`, *Merge permissions*) is what makes that gate reachable for its PRs.

Where the gate is reachable, evaluate it at the settled step, after the summary, the walkthrough, and the ranking — the gate's `DECISION` and `MERGE_RISK` inputs do not exist before `summarize-tranche` produces them, so an earlier evaluation is a guess wearing the gate's name. Merge the PRs it passes in the ranking's order, bottom-up within a stack, restacking descendants exactly as any merge requires; each merge is then reported to the caller like any other (step 6). A PR in a repository that did not opt in is untouched whatever its siblings did — the gate resolves per PR, from that PR's repository.

**The gate's dependency-view condition is answered by the caller, per PR, because the machinery that answers it differs between callers and the condition must not** (Inputs, *dependency view*). A validated preflight answers it for one caller, a worker's completeness report for another; the condition means the same thing whichever did. **A view the caller accepted for dispatch as unproven is not discharged for merge**, and the case that matters is `dependency transport unavailable`, which is proceedable for dispatch. The acceptance argument does not carry over, because both of its premises stop at the gate. Blocking dispatch on the warning would halt every GitHub backlog permanently, while holding a merge degrades exactly to the default no-merge behavior the run has anyway — the PRs still get built, reviewed, summarized and ranked. And dispatch leaves a person standing between every PR and the default branch, which the gate is precisely the removal of. A READY computed from prose alone is a narrower claim than one computed from a corroborated graph, and the merge is where the difference stops being reportable and starts being landed: a blocker nobody wrote into prose is undetectable by construction, and nobody is left downstream to catch it. So a PR whose dependency view rests on such a boundary holds this condition exactly as a `MERGE_RISK` holds the gate — reported with the boundary and the discharge path — and its merge stays the owner's. **The discharge must answer for the whole view, because completeness is what is unproven.** A single user-confirmed edge discharges nothing here: under this boundary caller context is a targeted answer whose omissions prove nothing, and the known-true-case proof needs a working transport to observe the edge through (see `implement-issue-core`, *Back the completeness of the set*), so a re-invocation carrying one edge returns the same unproven report and the gate stays closed while the record claims a path out. Two things actually discharge it: a run whose dependency transport can read the graph and prove the boundary; or the owner explicitly answering for the view itself — a decision-shaped hold the settled step already knows how to carry, surfaced as a `DECISION` naming the boundary, ruled through the walkthrough or answered directly, with the recorded ruling retiring the hold exactly as the translation rules retire a constraint (step 5 here, or the ruling translation a caller that does not rank passed in its place). That ruling retires this condition and nothing more: the repository's opt-in and every other gate condition still govern, since a ruling never opens the gate. **A standing answer is not one of the two discharges.** Where the owner wants this condition lifted for every future run rather than for this tranche, that is a change to what the gate requires, and this skill has no mechanism for it — deliberately. The merge gate is the gate's only definition, and a second site that can subtract a condition from it is a bypass whoever writes that site controls. Report what would be needed and leave the condition standing; a ruling discharges this tranche and says nothing about the next one. **If such a mechanism is ever built, its removal trigger has to be something a preflight can execute itself** — not a condition needing the very capability whose absence justified the lift, and not a human assertion, an issue being closed included, since issue state is queryable and still somebody's say-so one step removed. The gate means the same thing whichever caller supplies the condition — which is the point of the shared `auto-merge` grant.

**Green is a statement about a tree, not about a PR** — this paragraph through the tool-bump one apply where the caller's freshness input says the stale-green re-check does (Inputs, *freshness checks*). The gate requires green CI on the current head, and a PR's head can be unchanged while the tree its green describes has ceased to exist: the base moved underneath it. Three merges later the forge still reports that PR mergeable and green, because nothing it touched was touched by the intervening merges — and the result is a statement about a tree that no longer exists anywhere.

So before merging on an existing green, compare the PR's base to the current head of its base branch. **Where they differ, the green is stale and does not discharge the condition.** What discharges it depends on what the checks actually run against, which is a property of the repository's CI configuration and is established rather than assumed (`references/establish-do-not-assume.md`): where checks run against the PR merged with its base, re-running them produces a result about the tree that will exist, and a re-run is enough; where they run against the branch alone, a re-run proves exactly what the stale one did, and the branch has to be updated before the green means anything. Establish which, once per repository, and record it beside the other per-repository observations.

This is not the rejected rule that every branch be up to date before merging, which serialises every merge behind every other. It is narrower: the freshness check is paid at the gate, on the PRs the gate is about to open for, and only where the base has actually moved.

**Where the caller passed an integration check's result, that result is a statement about a tree too** (Inputs, *freshness checks*). It carries the head SHA of every branch the check integrated, not just their names — the set can be unchanged while a tip has moved, which is what another session opening or force-pushing a PR does to it. At the gate, compare the current set and each tip against those SHAs; where the set or any tip differs, or a result arrived without them, the clean result describes a combination nobody tested and the check the caller passed is re-run before anything merges. A cached clean result over a moved tip is the same failure the check exists for, arriving through the check itself.

**A bump to any tool whose output is a required check always needs a fresh run, however small its diff.** A formatter or linter upgrade verified against a tree that does not contain the code it will format has verified nothing that matters — and it is exactly the PR most likely to look safe: a one-line manifest change, conflicting with nothing, green. Two such sat three merges behind a default branch that had gained several thousand lines in between. This is the one case where the diff's size is evidence in the wrong direction.

**Re-read the PR body against its current diff before publishing or merging, and always where a repair pass reported changing a behaviour the body asserts** (`repair-pr` returns that flag rather than editing the body, since a PR with rounds left does not need its body correct yet). The body is the first thing a human reviewer reads and nothing in the repair path re-reads it, so a body written at round 0 can end up arguing for a design the rounds removed. **Update it, or hold the PR and say why** — an update is an authored write, in the form `references/authored-write-form.md` states — a body contradicting its own diff is not a clean PR, whatever CI says. This is the last point at which the fix is cheap.

**A merge never happens on a draft.** For each PR the gate passes, the merge path **publishes it to ready first, then merges** — publishing is part of the merge path, not a precondition that might already hold, so a PR still in draft when its gate opens is published by the act of merging it, never skipped for being a draft. This is one of the three forms of promotion (see `references/draft-state.md`, *Promotion* — the others are the owner doing it themselves, and the run carrying out a repository's own promotion convention), and it never reaches an **explicitly held draft**: the gate already excludes those, so the merge path neither publishes nor merges one — report each as held, awaiting the owner.

**Publishing may not be inert, and whether it is is a fact about this repository** — the three states below govern the merge path's publish unless the caller passed a publish rule of its own, which then governs instead (Inputs, *publish rule*). Marking a draft ready is an event some review providers and some CI configurations act on and others do not — `create-pr` mentions the possibility and names no provider, so it is not evidence that any given repository behaves that way (`references/establish-do-not-assume.md`). **There are three states here, and the third is where a first run and every restart begin:**

- **Observed to trigger.** Publishing un-settles the tranche for that PR: the clean-review and green-CI evidence the gate just accepted describes the PR as it was one moment before it changed, so merging on it is merging on a reading publishing invalidated. The merge waits for a later pass and is **never awaited inline** — a wait with no observable completion condition either re-reads the same stale evidence a moment later and merges anyway, or blocks the run indefinitely.
- **Observed not to trigger.** Publish and merge. No evidence is coming, and a timeout would end in a merge on evidence nothing invalidated.
- **Unknown.** Not having observed a trigger is not evidence that publishing is inert (`references/absence-is-not-a-verdict.md`), and merging straight through on pre-publish evidence would land the PR before a run that publishing started could report. **Take the un-settle branch and establish it from there:** publish, un-settle the tranche for that PR as the first state does, and classify the repository on the next delivered pass — a queued run or review may not yet exist at the moment of publishing, so a read taken there can only distinguish *nothing was triggered* from *nothing has appeared yet* by accident, and the answer it records is the one every later publish in this repository will be decided by. The read that settles it is taken no earlier than the next check-in, and a run that cannot keep watching returns the checkpoint with the PR named as published and awaiting re-evaluation. One pass, and the repository is in one of the two states above for good.

The observation is recorded per repository, like the transport and identity maps.

The merge path holds nothing open for the first case: the published PR returns to the caller's own supervision — its subscription on the PR, its settled condition — and is re-evaluated when the caller settles again.

A re-review that finds something is the system working: that PR is no longer clean, it does not merge, and it returns to the ordinary repair path — now as a ready PR, since publishing is not undone.

`merge-stack` authors forge writes of its own — the merges, and the retargeting and body edits it makes on descendant PRs — so pass it the run's posting-identity map and merge the observations it returns, exactly as for implementation and repair workers. It is easy to miss because it is invoked as an operation on the graph rather than as a worker that reports; the writes are no less authored for that.

**The merge gate is itself the authorization `merge-stack` needs, for exactly the PRs it passed.** Every merge and restack this skill performs goes through that skill (Composed skills), and a gate-approved merge must restack its descendants like any other, so without this a repository that opted in would have no compliant way to perform the merge its own policy authorized. The grant is scoped to the gate-approved set and nothing wider: it does not extend to a sibling the gate excluded, to a repository that did not opt in, or to any stack operation outside that merge. Where the user separately authorizes `merge-stack`, that authorization is the ordinary one and is unaffected by this. Reconcile tracker completion after every merge, gate-authorized ones included.
