# settle-and-merge — design notes

Companion to `SKILL.md`. That file is the contract; this one holds the reasoning and the incident history behind its rules, keyed by section. Read a section's note before changing its rules or when applying them to a case the contract doesn't obviously cover. Nothing here overrides the contract.

**Most of these entries were written while their sections lived in `backlog-orchestrator`**, or in `implement-issue`'s *Merge*, and moved with them when the settle sequence and the merge gate were split into this skill (#132). Read "this skill", "here" and "the run" in them as the calling skill and its run as they stood when the entry was written; the incidents are the same incidents.

## Inputs

**Why this is its own skill (#132, the second cut of #78):** `backlog-orchestrator` and `implement-issue` both end a run with the same sequence — summary, walkthrough, ranking where there is one, the gate, the merge — and `backlog-orchestrator` defined all of it while `implement-issue` evaluated invariant 12's gate "exactly as backlog-orchestrator defines it" and restated parts of the merge mechanics in its own *Merge*. One sequence with two readers is the shape #78 says to split on. What stays with each caller is what differs between them: when to settle, how an un-settle is handled, which supplier answers the gate's dependency-view condition, and the wave-only inputs to the ranking. The move was meant to change no behaviour, and eval round 3 is the check.

**Why the caller table became an input contract (#138):** the split left a table here describing each caller from the callee's side — 27 pointers up into `backlog-orchestrator` and `implement-issue`, most of them from that table, the rest naming wave concepts this skill used and did not own (the integration check, the charter check, stack rules, draft state, un-settling). To know what to do, a reader of this skill had to read both callers, and a third caller would have had to be written into this file. The dependency now runs downwards: this skill names what it needs and what it does without each, and each caller's settle step says what it passes. What each input does where it is absent is chosen so an omission narrows or stays visible, never opens anything. Absent `auto-merge` is off. An absent dependency view is unproven. An absent freshness input applies the stale-green re-check rather than skipping it. A caller that declines to rank without passing a ruling translation still gets step 5, because an untranslated ruling reads as clean at the gate. Of the wave concepts: draft state became the shared rule `rules/draft-state.md`, since three skills apply it. The integration check, the dependency-view supplier and the draft→ready freshness rule became inputs. The charter-check aside was dropped, being commentary rather than anything this skill does. The stack rules' requirement of `merge-stack` is this skill's own *Composed skills*. No behaviour change was intended, and eval round 6 is the check.

**Why inputs are values, never pointers (#139 review):** the first cut let a caller pass "the ruling translation below" or "its evidence-freshness rule", so this skill would have executed text in the caller's contract — the dependency the change set out to remove, relocated into the arguments. So every input is a value or a result. A caller that does its own ruling translation passes `caller translates` and hands back translated action points. A caller with its own publish rule once passed `hand back` and took the published PR back to run that rule; since #190 one publish rule governs every caller, so the input is gone. Un-settling is not an input at all: control always returns the same way, and what happens next is the caller's. Where a default applies, it is either visible or narrowing. A scope with no PRs still settles, because a run that blocked before any PR existed carries the most decision-shaped material. An absent policy reports the gate as not evaluated rather than merging nothing silently. A stale green this skill has no authority to refresh holds the PR, since updating a branch is never this skill's own call.

## The merge gate

**Why a stalled round released by the owner counts for the round-completed condition (round 2 of the pre-merge audit of #200, owner's ruling):** a review round still stalled after its one re-trigger can have no answer at all, so an owner's choice to merge without it would release item 1's hold and leave this condition shut, and the option offered would be one the gate could never honour. It is named here, beside the condition it qualifies, and defined in `rules/review-trigger.md`, *A stalled round*; like the dependency-view discharge, it releases what the item named and nothing else.

**Why a stalled round's `DECISION` holds only its own PR (owner's ruling on #200, after the final pre-merge audit):** as first written it held the whole wave, as every `DECISION` does, and that was reported to the owner as a choice the change had left open. The owner ruled it narrows like a body-drift `MERGE_RISK`: the question it asks — merge this PR without the unanswered request, ask once more, or wait — is about one review round on one PR, and nothing a sibling merges changes the answer, while a provider that stalls on one PR would otherwise hold every clean PR in the wave on a question that does not bear on them. Its own PR stays held by it, and by item 1, until a request answers or an owner reply chooses an option; the release rule is unchanged, so an unattended "merge without" still reaches the gate only once the walkthrough retires the item. It is protected rule 8's gate gaining a second per-PR exception, and is defined at the gate beside the first; every other site that states the scope cites it there.

## The settle sequence

**The removed decision docket (why the unattended decline's aggregation loss is accepted):** a second durable record written to close that gap is the decision docket this skill already carried and removed — it needed an in-place rewrite `permissions.json` cannot perform and stopped an unattended session on the prompt `backlog-orchestrator`'s step 8 forbids. Re-deriving a lost aggregate costs one summary; the record that would have prevented it cost four review findings and could not run.

**Why a code-changing ruling must not become a ranking constraint (the step-3 defect one step later):** choosing the other side of a decision a worker already implemented creates actionable work *after* step 3 processed the action points. Translating it into a ranking constraint would leave an orchestrator-owned fix undispatched and rank a PR that is not finished — the exact defect the `IN_FLIGHT_FIX` row guards against, arriving one step later.

**Why step 4 seeds the dependency-view `DECISION` (Oct 2026, the existing-branch entry's contradiction pass):** *Merge behavior* names the owner answering for the view as a discharge, "surfaced as a `DECISION`", but nothing produced that item: `implement-issue` forbids routing the hold through `summarize-wave`'s classification, and the walkthrough's sources never named it. The gap was latent while only core's unproven case reached it; `implement-issue`'s existing-branch entry makes every such run unproven by construction, so an opted-in repository would never have merged one. It is seeded only where the repository opted into `auto-merge`, because elsewhere no gate is evaluated and the question would answer nothing.

**Why a re-trigger ruling drops out at step 5 rather than un-settling (round 2 of the pre-merge audit of #200):** it changes no code, so it is not an `IN_FLIGHT_FIX`, and the round it re-requests is still unanswered, so the gate holds it without a constraint of its own. What carries it out is the supervisor reading the ruling at the item's site, which is where the trigger rule puts it.

## Merge behavior

**Why no waiver mechanism was built (Sept 2026):** a proposal asked for waived gate conditions recorded in the policy config with a machine-checkable removal trigger. The trigger requirement is right — a removal condition a preflight cannot execute is a promise nobody keeps, and both observed attempts failed it, one by living in a PR body no preflight reads and one by being circular, needing the very capability whose absence justified the lift. What the proposal did not carry is everything around it: which conditions may be waived at all, who may author the entry when the run is forbidden from honouring a config its own workers wrote, what a rejected trigger does, and what a consumer with no preflight does with an entry it cannot probe. Built as asked it is a second site that can subtract from invariant 12, controlled by whoever writes that site. The gate already has a discharge for an owner who wants a condition answered — a ruling, per wave — and the honest answer to a standing lift is that this skill does not have one. The trigger constraint is recorded where it would apply if one is ever built.

**Why a waiver's removal trigger has to be a probe (Sept 2026):** a waiver is a promise to re-examine something, and the promise is only worth what the thing that would act on it can observe. Two attempts failed in the same way at different depths. The first recorded a bare boolean with the justification and the removal condition in the PR body — and a preflight reads the config, never a pull request, so the workaround would have outlived the tooling gap silently. The second attached a condition that read as checkable and was circular: *migrate the prose dependencies to native ones* cannot be confirmed complete without the native read the waiver exists because the run lacks. That one is worse than the boolean, because it looks like it has been handled.

**Why the stale-green rule is not the rejected up-to-date requirement:** requiring every branch be current before merging prevents this and serialises every merge behind every other, which a handover rejected and rightly. What landed is narrower in three ways: it is paid at the gate rather than continuously, only on the PRs about to merge, and only where the base has actually moved. The formatter case is carved out because there the diff's size argues in the wrong direction — a one-line tool bump conflicting with nothing is exactly the PR whose green is most likely to describe a tree without the code the tool will process.

**Why the stale-green check narrows to overlap under `minimize-ci-runs` (#179, owner-approved spec):** the re-check re-ran CI on every PR whenever the base moved, and in a busy wave the base moves after every merge, so it was one of three causes of a month's CI allowance spent in a morning. A base change that touches no file the PR touches cannot change what the PR's own diff does to those files; what it can still change — an interaction through a file only one side touched — is the risk the owner accepted by opting in, which is why it is a key and not the default, and why the default rule stands unchanged without it. The tool-bump rule is kept under the key because its case is exactly the PR whose files rarely overlap and whose green most needs the new tree. This changes protected rule 8, so it carries pinning evals 13–17. The overlap update is mechanical, so a review round carries forward across it under the key (`rules/ci-and-review-verdicts.md`) and the update goes back to the caller as a caller push, or the supervisor would reset the round on a head nobody changed (blind audit of #181). Where branch protection requires branches to be up to date, the forge re-checks freshness itself, so the narrowing has no effect there.

**Why the integration result carries head SHAs (round 1):** the first version recorded which branches were integrated, which is enough to see a partial set and not enough to see a moved one. Another session opening or force-pushing a PR leaves the set of names unchanged while the trees change under it, so a cached clean result would let the gate merge a combination nobody ran — the check's own output becoming the thing that hides what the check exists to find.

**Why what discharges a stale green is established rather than stated:** whether a repository's checks run against the branch or against the branch merged with its base decides whether a re-run means anything, and it differs by configuration. Asserting either would make the rule confidently wrong in half the repositories it runs in — a re-run that proves nothing, or a branch update nobody needed.

**Why the body reconcile runs at step 1 and edits only under the write-form rule (#163, owner's ruling 2026-09-30):** in the merge path it either never ran where `auto-merge` was off, or — as `implement-issue` read it — rewrote a published description a person had read. At step 1 it runs on every settle, before anything publishes, and a forbidden edit reaches `summarize-wave` as an action point, where a person looks. Why the comparison ignores the drift flag: `backlog-orchestrator/NOTES.md`, *Why the body comparison is unconditional in both consumers*.

**Why the merge goes through `merge-stack` and passes the map:** the stack rules require that skill for any merge or restack, and a raw forge call is exactly what the required-skills rule exists to prevent. Its merges, retargetings, and body edits are authored writes — easy to miss because it is invoked as an operation on the graph rather than as a worker that reports — and its identity observations are the last ones the structured result's map can carry.

**Why publishing is inert by default, and what counts as evidence (#190, owner's spec):** the rule this replaces had three states — observed to trigger, observed not to, and unknown — and unknown, where every first run and every restart begin, took the un-settle branch: publish, then wait a pass to classify. In one orchestrated run that default met an automated reviewer's boilerplate summary comment saying reviews run when a draft is marked ready, which was wrong for that repository; the run trusted it, waited for a review publishing never started, and ten PRs, each with a clean review on its current head, sat unmerged. The defence of the old rule was the absence rule — not having seen a trigger is not evidence of none — but it treated publishing as if it changed what the review read. It does not: the head is the same commit, so a clean review on it describes exactly what would merge. So the gate's review condition reads the current head, and publishing matters only where the repository's own configuration makes it start something. That is read positively, from the policy file, the repository's own `CLAUDE.md` or `AGENTS.md`, and its workflow files, the way *Path filters* reads what did not run — never from a provider describing itself in a comment, which is the source that failed. A workflow on `ready_for_review` gates only on the checks it starts, because those are the only evidence the event produces; re-requesting a clean review there would be the old failure again. A repository whose reviewer really does act on publish, from outside its files, says so with `publish-triggers-review`.

**Docs, read from the base, count only one way (#190 blind audit):** reading them from the head would let a PR edit away its own evidence, and a doc saying publishing starts nothing cannot outweigh a workflow file that shows it does, because the workflow is what runs. The fresh round under `publish-triggers-review: true` is triggered only after the review-trigger rule's confirmation window, so a reviewer that is merely slow is not asked twice.

**What did not change:** a push after review still needs re-review, the observation is still recorded per repository, and a held draft is still never published or merged. The two superseded entries — why three states, and why classifying unknown took a pass rather than a read — argued about how to learn what publishing does by watching it; reading the configuration makes that classification unnecessary.

**Why the observation is recorded rather than re-derived:** it sits beside the
transport-visibility and posting-identity maps for the same reason those exist —
a fact about a repository that every later decision reads, established once by
observation rather than assumed from a provider's name.

**Why a retired hold item is not outstanding (#151):** the gate reads `NEEDS_USER` items wave-wide, and a held worker's item asks the owner for an act — a permission grant, most often — that no walkthrough ruling records. Without an ending, a grant the worker has already resumed on would hold every PR in the wave for good. What ends it, and on what evidence, is `swarm`'s (*Blocked workers*, its closing rule, and that skill's NOTES entry for #151); the gate states only that it reads the retired item as closed, so the rule stays in one place. Review round one on #153 made the other half explicit: a ruling on a question or mismatch hold is direction, not the hold's ending, so the item stays outstanding until the hold retires it whatever is ruled.

**Why the gate reads path filters and names `dirty` (#180):** both conditions read CI on the head, and both misread an empty rollup. A workflow a filter correctly kept off the head left a PR looking not green; a conflicted PR, which runs no `pull_request` workflow at all, looked like one still waiting. `references/ci-and-review-verdicts.md`, *Path filters*, separates them and fails closed: only a workflow the filters show should not have run is satisfied by not running, and a required check that can never report holds the PR with its cause named rather than being waited on.

**Why refresh is lazy under `minimize-ci-runs` (#180):** an orchestrated run's CI-minute review traced most of its CI runs to conflict refreshes. Refreshing every PR a merge left stale pays a CI run per PR per merge, and all but one of those refreshes is overtaken by the next merge before its PR is next. Refreshing only the PR about to merge pays once per merge, and merging the disjoint PRs first, which need no refresh at all under the overlap narrowing, shrinks the set that pays anything. The final review round goes on the refreshed head for the same reason: a round on the head before it reviews code that never merges.

**Why the refreshed PR keeps its turn (blind audit of #185):** if another PR merges while the refreshed one waits on its CI, the base moves again and the refresh just paid for can be stale before it is used. Holding the order until the refreshed PR merges, or fails and is reported, makes each refresh count once.

**Why a PR into the integration branch skips the stale-green re-check (Oct 2026):** its green is a local gate record on its head, not a run against a merged tree, so a moved base has nothing to re-check that the record ever claimed; re-running it per base move was the bottleneck the mode was built to remove (`supervise-prs/NOTES.md`, *Deferred CI*). The integration branch's full tier tests the combination. The integration PR is re-checked as any PR is, and never refreshed here, because a refresh would start the CI run its owner kept for themselves.
