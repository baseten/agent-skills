# implement-issue — design notes

Companion to `SKILL.md`. That file is the contract; this one holds the reasoning, incident history, and answers to "why not the obvious other reading?" — organized by the contract's section names. Read a section's note before changing its rules, or when applying them to a case the contract doesn't obviously cover. Nothing here overrides the contract.

## Composed skills

This skill is deliberately a one-issue orchestrator that composes primitives rather than duplicating their logic — every rule it needs twice would otherwise drift into two meanings, which is the failure mode PR #27 spent seven review rounds closing across `implement-issue` and `backlog-orchestrator`.

**Why `merge-stack` is checked at preflight rather than discovered at the gate:** the stack rules require that skill for any merge or restack, so a run that could merge without it holding would have no compliant mechanism for the very merge the repository authorized — and the improvised raw merge is exactly what the required-skills rule forbids. Discovering that at the gate, after all the work is done, is the worst possible time; the preflight check costs nothing. A repository that never opted in imposes no requirement — there is no gate to reach. (`backlog-orchestrator` handles the same unavailability differently — degrade-and-report rather than `BLOCKED` — and argues the asymmetry in its *Model and skill policy*: blocking a twelve-issue tranche for its optional final step's tool costs far more than blocking one issue at an invocation its user typically attends.)

**Why `plan-merge-order` is never invoked, and its absence is not an asymmetry to fix:** it ranks a settled tranche's open PRs by downstream leverage and emits review order, merge batches, and forced sequencing. One PR has no ordering to rank, nothing to batch it with, and no descendant to restack — the table would be a single row restating the PR this skill just reported. Where a single-issue run's PR is stacked under work this run cannot see, the ordering belongs to whoever holds the whole stack; a run that can see one node of it is the wrong place to compute one.

## Authority

**Why the `auto-merge` key is shared with `backlog-orchestrator` rather than split per consumer:** the permission is scoped to invariant 12's *gate*, not to whichever skill evaluates it, and the Merge section defers to that gate for every condition rather than carrying a copy. A run that satisfies the whole gate is not riskier for having one issue instead of twelve, so a per-consumer key would gate which skill happened to open the PR — not a property worth gating — while leaving the real boundary untouched. The consequence is stated rather than discovered: a config committed before this skill could merge grants it too, from the moment the skills are reinstalled. An owner who wants no autonomous merging sets `auto-merge: false`; an invocation argument narrows a single run.

**Why the opt-in must live in a committed file:** it is the only place an owner can grant merge authority once and have it mean the same thing to an unattended run they are not watching. Prose gets interpreted, and interpretation must not decide whether a run may merge; an invocation argument's authority comes from whoever composed the prompt, a committed file's from someone with write access to the repository — which is why an argument can narrow the gate but never open it.

## Policy and budgets

**Why the config contract lives in one place (now `rules/agent-policy.md`, which it moved to from `backlog-orchestrator` in #134):** a second copy is how the two consumers would drift into meaning different things by the same key — the reason the config is one file rather than one per skill. The file's name predates its second reader; it is the same file, read the same way. And it is read from the default branch head, never from this run's worktree, because the worktree is the same repository at a revision this run controls — a run must never honour policy its own work wrote.

**Why a caller's complete resolved policy suppresses the read while a partial override does not:** the caller (`backlog-orchestrator`) already read the file once, from the state its run started in; a read here would be a second read at a later timestamp — the child free to override its parent, against the file's whole read-once rule. Omitted permission keys take `false` because a caller that resolved a policy and left a permission out of it did not grant that permission. A partial invocation override is a different object: one argument from a person. Treating it as a resolved policy would hand a repository configured with zero repair cycles two of them because its owner narrowed something else — a built-in default overriding a committed file on the strength of an argument that never mentioned the key. So the file is still read and the argument merges over it per key.

**Why the monitoring cap is not a policy key:** it bounds how long this skill sits watching, which is a property of the invocation, not of the repository's PRs.

## Phase 1 — reading core's result

**Why a block on an unmet dependency is never retried:** it is authoritative information about the graph, not a worker failure — the issue was judged ready against a dependency view that turned out to be wrong, commonly a read that returned part of the blocker list with no indication it had. Nothing about a second identical attempt would differ.

**Why this skill classifies prose-only blockers itself:** there is no orchestrator here to re-derive a frontier, so an unclassified stale edge blocks the issue permanently with no route forward. Prose survives edits that remove a dependency from native metadata, so a prose-only blocker is as likely to be a dependency someone deleted as one nobody built — and that is just as true when the referenced issue happens to have an open PR or an out-of-base merge, which is why the classification cannot be gated on "the work exists nowhere". Classifying before acting on a restack matters because a wrong base becomes the justification for the next one. And the `NEEDS_USER` form must carry both readings: the user can retire a stale edge in seconds, but cannot act on a bare `BLOCKED` that does not say which reading it assumed.

**Why the two `NEEDS_USER` kinds must never be inferred from the blocker list:** they demand opposite responses — one is a question a person answers in seconds, the other is transport evidence — and an empty blocker list is precisely what the dangerous kind looks like. On the unverifiable-prerequisite kind, frame the question as deciding which of two states you are in, not as a step that unblocks the work: told the release has not happened, the prerequisite becomes a known unmet blocker, and a yes clears only that blocker — an external wait core reported alongside can still block the re-invocation. Promising a proceed the user does not get is worse than naming two things to clear.

**Why `PR_OPEN` with an unproven view is normal here and its claim is narrower than it reads:** this skill supplies no graph judgement, so the worker proceeds on the invocation's authority and says the absence of blockers was never proven — *no blocker was visible*, not *none exists*. The two strengthening paths split by transport because of how `implement-issue-core` backs completeness: where a dependency read exists with unproven visibility, a user-confirmed edge is the known-true case that read can be proven against, so it genuinely turns the next run's silence into evidence; where no read exists at all, no edge-level answer can help — completeness is unproven by construction (this split was a Codex round-three finding on the PR that introduced the merge-time hold; the earlier unconditional "a confirmed edge turns silence into evidence" sent users on a re-run that could not change anything).

**Why visibility and availability disagreements are reported as distinct kinds with direction:** they mean different things and warrant different responses. A visibility disagreement says the transport may be partial — the issue just implemented may have blockers nobody in the run could see, and the user can only act on that if the finding names the edge and the sources rather than arriving as a generic mismatch line. An availability disagreement in the obsolete-constraint direction is the user's own stale assertion, and they are the only one who can retire it.

**Why disagreements are passed on even from successful runs:** a run that succeeded while its transport returned a partial view is the case where the evidence is easiest to drop and most worth keeping — nothing else in a standalone run will surface it.

## Phase 2 — supervision boundary

**Why this skill lets `supervise-prs` run its own loop (#144):** here there is no parent to defer to, so watching this PR — the subscription and the scheduled check-in included — is this run's job, and the surrounding session's ambient posture agrees. Under `backlog-orchestrator` nothing dispatched supervises its own PR: the parent fans out `implement-issue-core` directly and runs `supervise-prs` inside its own loop. Before the extraction this skill held its own copy of the supervision rules, and it had drifted: no reconciling read after arming, no one-mutator rule, no refusal exception on re-triggers, and a check-in with an eight-hour cap and no stated cadence.

**Why the check-in now backs off (#144, owner's ruling B6):** `supervise-prs`'s own loop arms its check-in under `rules/wake-budget.md` — 20 minutes doubling to a 4-hour cap, eight unproductive wakes — and the eight-hour monitoring cap still bounds it from outside. A quiet PR therefore stops being watched at whichever comes first, and is reported as still open either way.

The note on why the platform's own auto-merge is called out moved to `supervise-prs/NOTES.md` (#144).

**Why a refused round stops the re-trigger and does not stop settling (#144, owner's ruling):** this skill re-triggered after every pushed repair with no exception for a provider that had answered it was out of budget, so any later pushed repair would have asked it again — the retry `rules/review-trigger.md`, *A refused round*, forbids, which once put twelve rounds on a PR capped at two. And its settle predicate asked for "a completed review round", which a refused round never becomes, so the run would have sat out its monitoring cap waiting for a provider it may not ask. `backlog-orchestrator` already counted a refused round as surfaced — holding the merge, never the settlement — and the ruling was to read it the same way here. For the same reason an expected-red check (`rules/ci-attribution.md`, *A producer merge*) is reported and holds the gate rather than drawing a repair: this skill cannot bring the PR onto the producer's refresh, so it names it.

## Settle

**Why every terminal outcome settles, including Phase 1's:** the two outputs are an account of what the run did and the action points a person still has to manage, and the runs ending `NEEDS_USER`/`BLOCKED`/`BLOCKED_EXTERNAL` carry the most of both — an unverifiable prerequisite to confirm, a prose-only edge to retire or keep, a product question a worker was right not to guess at. Those are the decision-shaped items the walkthrough exists for, and they are perishable: the run context that produced them dies with the session while the durable sites survive. A run with nothing to report gets `summarize-tranche`'s one-line empty case — cheaper than a rule about when to skip the step, and safer than one that skips it exactly where a person was needed most.

**Why the re-entry exemption keys on provenance, not outcome type:** read against two other rules, "every terminal outcome settles" loops — a required settle skill being unavailable returns `BLOCKED`, and `BLOCKED` settles, invoking the unavailable skill again; a spent repair budget returns `NEEDS_USER`, which settles again, recomputes the same summary, and rediscovers the unchanged finding. An outcome the settle phase itself produced returns directly because the phase has already run as far as it can — re-entering re-runs it against inputs nothing has changed — and keying on provenance means a settle-phase failure invented later inherits the test without a new clause. The exempt return still carries everything the completed steps produced (the summary where step 2 finished) and points at the durable sites for what the missing step would have covered, because a fallback is only useful if it says what was lost. Settling again from step 1 after a repair is not the loop: it follows a repair that changed the PR, and it terminates because every pass consumes budget.

**Why the walkthrough's `auto-request-settle` gate covers only the request:** whether the walkthrough may actually *ask* is its own attendance precondition, so a run settling on a scheduled wake or inside a dispatched worker gets a one-line decline and the decisions stay at their durable sites — which is what makes the decline safe: the sites survive session loss, the aggregation does not.

**Why every ruling is translated before the gate:** the gate cannot see a ruling — only outstandingness — and recording a ruling is exactly what stops a `DECISION` reading outstanding. Untranslated, every ruling therefore reads as clean, the adverse ones included: a ruling to close or hold this PR retires the outstanding item and changes nothing else any gate condition looks at, so the gate would merge the PR against the owner's explicit instruction — and the record afterwards looks tidier than any unruled case. The three-outcome closure is structural, not observed: a ruling's consequence for this PR is a change to its content, a change to its disposition, or neither, and a PR has nothing else for an answer to change — which is also why "read the consequence, not the topic" handles rulings about other things (a convention ratified for future work implies one of the same three here, or implies nothing and drops out with the report).

**Why the run performs no disposition a ruling calls for:** the walkthrough's own reason — every action a ruling calls for already has an owner, and its output names them. The run returns, gate held, the ruling and next owner in the structured result rather than left to evaporate with the session.

**Why a free-text ruling defaults to the disposition row:** the misreadings are not symmetric. Filed there wrongly, a mergeable PR waits for a person; filed anywhere else wrongly, the run does or permits something the owner just refused.

**Why a code-changing ruling hides better than a summary `IN_FLIGHT_FIX`:** the summary case leaves an action point in view, while an owner answering "no, do it the other way" leaves a PR whose decision reads *ruled* while the code still says what they rejected — only the translation stands between the gate and merging the very PR the ruling was against. The finding-repair budget being its own counter, and the argument against drawing on `review-repair-cycles`, are `rules/repair-rounds.md`'s (*The finding budget*, with its notes); the outcome branching (`NO_CODE_CHANGE` consumes nothing) is this skill's own, under *Un-settling*.

## Merge

**Why the gate's dependency-view condition is supplied here by core's report:** invariant 12 states the condition once, and each consumer passes its supplier's answer as `settle-and-merge`'s per-PR dependency-view input — `backlog-orchestrator` the validated preflight's; here, the one line core preserves, because a standalone run has none of that machinery by design. Everywhere short of a merge the unproven-view caveat is survivable, because a person still stands between the PR and the default branch; the gate is where nobody does.

**Why the discharge must answer for the whole view:** completeness is what is unproven. One confirmed edge is a targeted answer whose omissions prove nothing, and the known-true-case proof needs a working transport to observe the edge through (`implement-issue-core`, *Back the completeness of the set*) — so a re-invocation carrying one edge returns the same unproven report, and the gate would stay closed while the record claimed a path out (a Codex round-one finding on the change that introduced the condition). The owner's whole-view answer travels as a recorded ruling that retires the hold the way the translation rules retire any constraint — never opening the gate, since the repository's opt-in and every other condition still govern.

**Why not route the hold through `summarize-tranche`'s classification:** its contract treats the caveat as a reportable line, not a mandatory `MERGE_RISK`, and making merge safety depend on another skill's classification bar is the seam this corpus keeps having to close.

**Why the freshness rule binds the transition rather than a site, and why it has a terminating case:** marking a PR ready is something review providers and CI act on, so clean evidence gathered while it was a draft describes a PR one transition older than the one a merge would land. The owner can perform the transition at any moment outside the run's control — a run that does not re-read the forge before the gate discovers it only by merging on stale evidence — and the merge path's own publish is the same rule's next instance, not a separate step. Without the terminating case the rule rejects every artifact older than the transition while nothing ever produces a newer one, and the gate becomes a hold nobody ordered: a read showing the transition triggered nothing re-establishes that the pre-transition clean state still describes this PR, which is everything freshness was for — where re-triggering a review just to manufacture post-dated artifacts would spend a cycle to learn what the read already established.

## Posting identity (recurring rule)

Every "merge the returned identity entries into the map" step exists because a repair, walkthrough, or merge can run on transports core never used, and an observation is the only evidence the run will ever have about them — there is no orchestrator here to hold it instead. Entries stay keyed by `(transport, credential)` and are merged, never replaced, and never collapsed to one pair: `create-pr` deliberately routes the PR and the review trigger through different paths, and re-triggering review from a pre-repair map is what makes a trigger silently fail (the trigger must be authored by the invoking user or the convention does not fire). The full rule is `rules/posting-identity.md`.

## Structured result

The resolved policy is reported with sources because an owner should see the authority a run had before they see what it did with it — including a present-but-unhonourable policy file, since a file the run could not read is authority the owner meant to grant and did not. Dependency evidence is reported even on `PR_OPEN` for the reason under Phase 1: nothing else in a standalone run will surface a partial transport view.
