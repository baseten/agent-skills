# review-docs — design notes

Companion to `SKILL.md`. That file is the contract; this one holds the reasoning, keyed by section. Read a section's note before changing its rules, or when applying them to a case the contract doesn't obviously cover. Nothing here overrides the contract.

## Why an automated code reviewer is the wrong instrument here

**Where the numbers come from:** the owner's measurements from one backlog that took four spec PRs to merge — one of those PRs ran **nine review rounds and 28 threads**, and the document was not materially better after round four; all 28 threads checked internal consistency. Both halves of this skill are responses to a measurement rather than to a preference, which is why the contract states them as the reason it exists rather than as background. A later editor tempted to relax either should replace the measurement, not the argument.

**Why the termination argument is about oracles and not about discipline.** The tempting diagnosis of nine rounds is that the reviewer lacked judgment and a better prompt would have it stop sooner. That diagnosis produces a skill that says "be judicious" and runs nine rounds. The real asymmetry is that code review borrows a decision procedure it does not own — a test passes, a compiler accepts — and prose has none, so *"is there anything left to say"* is a question whose answer is always yes and which therefore cannot be the stopping rule. Once that is the diagnosis, the only fix is a stopping point fixed in advance, and everything else in section 4 follows from it.

**Why "reads the document against itself" is a separate failure and not a symptom of the first.** They look like one problem — a reviewer with nothing substantive to check falls back on consistency — but they have different fixes and the fixes are independent. A reviewer bounded to two rounds that still reads the document against itself produces two rounds of shallow findings. A reviewer checking claims against the codebase with no round limit produces nine rounds of decreasingly useful ones. The skill needs both, and stating them as one would lose whichever half a later edit found less convincing.

## What this skill reviews, and what it replaces

**The mixed case was added mid-draft, on the owner's question, and it changed the skill's shape rather than extending it.** The first draft declined a mixed PR outright, reasoning that a document changed beside the code it describes is the case code review handles well because the code is in the diff. That reasoning is true and incomplete: the code reviewer can see both, and still does not test the document's sentences against the diff — it reviews the code and reads the prose. So *"the endpoint returns 202"* beside a handler returning 200 survives a review that looked directly at both, which is the most valuable finding this skill can produce and the first draft refused to look for it.

**Why it is additive on a mixed PR rather than a partition.** The alternative — this skill takes the documentation paths, the code review takes the rest — is attractive and wrong. It narrows the code review on the strength of a path classification made by this contract, so a file misclassified as documentation is a file no reviewer read, and the misclassification is silent. Additive fails the other way: a file wrongly treated as documentation gets reviewed twice, which costs a paragraph. Given one classification and two error directions, the contract takes the cheap one, which is the same reasoning as *cannot tell → not documentation* one level down.

**Why mixed routing is opt-in while docs-only replacement is not.** They differ in what happens when the routing is wrong. Docs-only replacement wrongly applied means a PR got the prose review instead of the code review — recoverable, and the `NOTES`-worthy risk the *cannot tell* rule is aimed at. Mixed routing wrongly applied means a second review comment on every PR that touches a `docs/` path, forever, and the cost is that people stop reading the comment — the same attrition the 28 threads caused, reintroduced by the fix for them. A capability nobody reads is worse than one nobody enabled, so the default is off and the hand invocation always works.

## Which codebase the claims are checked against

**The two cases take different commits, and this is the rule most likely to be "simplified" into one.** A single rule — always the base, or always the PR head — is wrong in one of the two cases, and wrong in the direction that produces confident false verdicts rather than silence. Always-base marks every correctly-documented change in a mixed PR `FALSE`. Always-head is harmless on a documentation-only PR (the code is identical either way) but encodes a coincidence as a rule, and the next reader cannot tell the coincidence from a decision.

**Why the grep prohibition is stated inside the verification step rather than assumed.** This repository already holds the general form of it — a string matcher pointed at meaning goes green on a paraphrase and red on an improvement (`CLAUDE.md`, *The consequence sweep*). The specific form here is that a skill whose entire product is *claims verified against code* can satisfy every one of its own obligations with `grep -q` and report a full table of `TRUE` verdicts that establish nothing. That is this skill's own failure mode reached through its verification step, and it is the shape most likely to appear under time pressure, because it is fast and its output is indistinguishable from the real thing.

## Extract the claims and check them

**The descriptive/prescriptive split is the skill's central judgment and its central risk.** A spec describes a codebase that does not exist yet; a claim-checking reviewer that has not internalised this marks its forward-looking sentences `FALSE` and buries the report in noise. The consequence is not merely a bad report — it is the skill being switched off, after which the false claims it was built to catch go uncaught. So the cheap failure (over-flagging) becomes the expensive one, which is why the contract states it as a failure in *both* directions rather than warning only against missing claims.

**Why `FALSE_PREMISE` is its own verdict and not a note on `PRESCRIPTIVE`.** It is the finding the split is most likely to swallow. Once a sentence is classified as describing the future, the natural next move is to stop checking it — and a prescriptive sentence is exactly where an unchecked present-tense premise hides, because the sentence reads as unfalsifiable while resting on something falsifiable. *"Add `status` to the `scans` table"* is a plan; *"there is a `scans` table"* is a claim, and it is the one that sends someone to write a migration against a table renamed two months ago. A separate verdict makes not-checking it a visible omission rather than a defensible reading.

## What is a finding

**Why `NEEDS_AUTHOR` carries a test and not a description.** Without one it absorbs everything: any sentence a reader found unclear can be phrased as a question only the author can answer, and the class quietly becomes the 28 threads under a new name. The test — *name what would be built wrong without the answer* — is doing the whole job, and a version of this class that states the test as guidance rather than as the admission condition does not survive contact with a reviewer that has found nothing else to say.

**Why contradictions are capped at three rather than ranked or scored.** A cap is crude and cannot be argued with, which is the property wanted here; a ranking is a number a reviewer can always justify producing one more of. Three is not derived — it is small enough that the list is still read and large enough that a genuinely contradictory document is recognisable as one. The substantive rule is the one the cap enforces: past a few, the finding stops being *these two sections disagree* and becomes *this document needs its author*, and enumerating instances of a structural problem is how a review stops being read.

**Why the not-a-finding list is enumerated rather than covered by a principle.** *Only report what changes what gets built* sounds sufficient and stops none of these individually — every item on that list can be argued into consequence by a reviewer already inclined to raise it, and the arguments are locally plausible. The list is also the specific inventory of what those 28 threads were, which is the evidence for the rule and worth keeping attached to it.

## The rounds, and why there are two

**Why round 2 may not raise new findings, stated as an absolute.** It is the load-bearing rule, and it is the one that reads as over-strict at the moment it matters: a rewritten section is genuinely new text, and reviewing new text is genuinely the job. But a re-read of a rewrite is a fresh unbounded reading, and admitting it makes round 2 into round 1, which makes round 3 necessary, which is precisely the nine. The exception for a fix that introduces a false claim is bounded three ways — only that finding class, reported inside the existing finding, earning no extra round — because an unbounded exception here is the whole rule.

**Why the round is read off the PR's comments rather than held in run state.** It has to survive a restart, a different worker, and a person invoking by hand, and run state survives none of those. This repository's recurring lesson is that a count kept in run state is a count a later invocation does not carry, and the durable fact is the artifact on the forge — the same reasoning `summarize-tranche` applies to a recorded ruling versus a reservation. A pleasant consequence: the budget cannot be laundered by re-invoking from a fresh session, which is exactly how a well-meaning operator would spend round nine.

**Why the budget is not a policy key, against this repository's own habit of putting budgets in `.claude/agent-policy.json`.** That habit is right for repair budgets, which are a tolerance for cost: a repository that can afford more CI repair attempts should be able to buy them. This is not a tolerance, it is the skill's thesis. A configurable round count is a ceiling, and the run that spent nine rounds would have spent any ceiling it was given — the failure was not that the limit was too low, it was that stopping was nobody's decision. Making it configurable returns the decision to the person who already declined to make it. Stated in the contract so the next editor, who will notice the inconsistency with the repair budgets, finds the reason before the fix.

**The document in this repository that reads as contradicting this, and does not.** `docs/review-fix-workflow.md`, *Automating rounds on this repository*, records that the observed round count for documentation changes is far above `review-repair-cycles`' default and raises the key in config. That is a measurement of a **code reviewer's** rounds on prose — the thing this skill replaces — not evidence that documentation review needs a bigger budget, and the two bounds govern different loops with different exhaustion shapes (that document now says so at its own site). A future editor who finds only one of the two will read them as disagreeing; they are recorded together for that reason.

**Why the budget is per PR rather than per document.** A document returning as a new PR is a new decision to review it, made by a person, and the loop being bounded is the one inside a single PR where no such decision is being made. A per-document budget would also be unenforceable from the forge, which is where the count lives.

## The report is one comment

**Why one comment instead of a thread per finding, beyond volume.** 28 threads did not merely make the review long; it made the *composition* of the review invisible. A reader triaging a column of threads cannot see that two of them concerned the codebase and 26 concerned the document's internal ordering, and so cannot tell a review worth acting on from one worth closing. The claims table exists to make that composition the first thing visible, which a set of threads structurally cannot do.

**Why the comment states its own round and that there is no third.** Half of the original failure was that nobody knew whose job it was to stop, and a reader who cannot see the review is bounded will reasonably wait for the next round. Printing the bound makes the termination a fact the author can act on rather than an absence they have to infer — and it also commits the run publicly, which is a mild guard against a later invocation quietly reopening.

**Why required contents are named against the brevity rule explicitly.** `references/authored-write-form.md` gives the precedence — required contents win, brevity governs how each is written — and this is a write where the tempting cut is the evidence, because the evidence is the longest part and reads as padding to someone applying a word budget. A claims table cut to fit is the review deleting the only thing that distinguishes it from an opinion.

## Enabling it in a repository

**Which repositories this was built for, and why they are not named in the contract.** `crypto-scanner-api` and `crypto-scanner-web-app`, whose spec PRs produced the measurements at the top of `SKILL.md`. They are recorded here and deliberately nowhere in the contract: a repository list inside a general skill is deployment state in a file that governs behaviour, it is wrong the moment a third repository adopts the convention or one of these two drops it, and nothing in the skill reads it — the routing is decided by what each repository documents about itself. The skill is generic by construction, and the only thing these two contributed is the evidence.

**Why the routing lives in each target repository's `CLAUDE.md`/`AGENTS.md` rather than as a repository list in this contract.** `create-pr` already reads those files for review-trigger conventions, so the decision point exists and needs no new mechanism; a list of repository names inside a general skill would be a second place to maintain, invisible to the repository it governs, and wrong the moment a third repository wants this. The consequence is stated plainly in the contract because it is the kind of thing that silently does not happen: until those two repositories add the line, this is installed and inert, and the change that activates it is not a change to this repository.
