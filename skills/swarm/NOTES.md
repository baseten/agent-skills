# swarm — design notes

Companion to `SKILL.md`. That file is the contract; this one holds the reasoning and the incident history behind its rules, keyed by section. Read a section's note before changing its rules or when applying them to a case the contract doesn't obviously cover. Nothing here overrides the contract.

**Most of these entries were written while their sections lived in `backlog-orchestrator`**, and moved with them when the generic worker mechanics were lifted into this skill (#123). Read "this document", "this section" and "the run" in them as that skill's contract and run as they stood when the entry was written; the incidents are the same incidents, and every one of them happened on a `backlog-orchestrator` run. Where an entry still explains a rule that stayed behind, it stayed behind with it.

## Remote worker session arguments

**The incident behind passing the source explicitly (2026-08-30):** a run dispatched four workers through `create_session` with no `source_url`, relying on environment inheritance for the checkout as the section then advised. Three inherited one. The fourth had no `sources` key in its session record at all and no repository on disk — same environment, same call shape, same run. Passing `source_url` and `source_revision` fixed it immediately on redispatch. The defect is intermittent, which is why the wording survived long enough to be trusted: three-for-four looks like a working mechanism from inside a single run, and the fourth case looks like something the worker did.

**Why the rule is dispatch-time verification rather than better supervision:** every signal after the create call reads identically with and without a checkout — success, `RUNNING`, a `task_summary` describing work. The worker sorts under *still working* — the one row of *Releasing a worker*'s three-state table handed to nobody — so no supervision cycle is wrong to leave it there. It was found at ~50 minutes, by a permission prompt for `find / -name "simulator.ts"` — the worker had been hunting the filesystem for the file its own dispatch prompt named. Nothing was pushed; the round was lost. The response signature is written into the contract because `sources` in the create response is the only place the two cases differ.

**Why the failed start has to be ended and not merely abandoned (Codex round one on the PR that introduced this section):** the first draft said an empty `sources` is a failed start and sent it to *Bounded runtime probing*, which retries — and a failed start on this tier is not an absent worker. The session exists, reports `RUNNING`, and holds a container and a slot, so a retry that only creates a second session leaks the first, once per attempt, and the orphan is precisely the filesystem-searching worker the section was written to prevent. Two rules then met in silence: *Releasing a worker* forbids archiving a `RUNNING` session without interrupting it first, and that interrupt is defined as consuming the issue's lost-worker budget. Left as it was, a reader took one of three wrong exits — leave it alive, archive a `RUNNING` session, or spend an issue's recovery budget twice over on a runtime defect before any of its code was written. The budget carve-out is stated with its reason rather than assumed: that budget bounds re-attempts at *work*, and a session that never had a checkout did none, so the redispatch is the first attempt and not the second. *Releasing a worker*'s "Two things are never archived" paragraph carries a pointer to the carve-out for the same reason — an absolute there and an exception here is how the two copies of a rule start disagreeing.

**Why the capture discharge is scoped to creation (Codex round two on the same PR):** the first version of the *Blocked workers* carve-out reused the dispatch-time reasoning — empty `sources`, therefore nothing to capture, therefore archive needs no recovery ref. That is true of a session ended at the verification, which has not run a turn, and false of one found an hour later. `sources` records what the runtime provisioned at creation; it is silent on what the worker did afterwards, and the worker in question is the one *most* likely to have cloned a repository itself, having been told to implement an issue and given nowhere to do it. Reused late, the shortcut archives the only copy of real work on exactly the evidence that looked like proof there was none. The two cases share a cause and split on one fact — whether the session has run — so the carve-out names creation explicitly and the late case takes the ordinary inspection and capture. Same for the lost-worker budget: charged nothing at dispatch, ordinary rules once the worker has been running.

**Why the permission-request branch of *Blocked workers* names this case:** read as a permission problem, it resolves to `NEEDS_USER` naming `find` — and allowlisting `find` buys the next worker a faster search of an empty container. The tool being requested is a symptom two steps downstream of the cause, and it is the only shape in which this failure ever announces itself.

**And the guidance defect is not the runtime defect.** *Environment inheritance intermittently fails to populate `sources`, silently* is a runtime bug worth reporting upstream on its own. The contract change does not wait on it: passing the source explicitly is correct whether or not inheritance is ever fixed, and it is also what makes per-worker `outcome_branch` legal.

## Countermanding the worker's ambient supervision posture

**The blocked-worker incident in full:** the worker that stopped on `AskUserQuestion` was unreachable in every direction. The runtime's own fields disagreed about its state — `session_status` read `SESSION_STATUS_REQUIRES_ACTION` while `status_bucket` read `SESSION_STATUS_BUCKET_BLOCKED`, with the pending tool named only in a third field — a second sighting of the disagreement *Blocked workers* instructs on. It could not be steered out: interrupting the session left the prompt pending, and no message channel reaches a remote worker session mid-prompt, so the only recovery was archive and redispatch — which is why that is a branch of *Blocked workers* in its own right. What made the redispatch succeed was the substitute, not the prohibition: told what to do instead of asking, the replacement worker returned four documented assumptions — one flagged as the thing it most wanted confirmed — which were worth more than the blocked session they replaced. A documented assumption is recoverable; a deadlocked worker is not.

**Why the ban reaches inline polling and not only armed wakes:** a worker that sits waiting for checks to go green is running the same duplicate supervision as one that arms a wake — the parent is already watching that PR — and it is billed to the API allowance rather than to the clock, which is why it survived a rule written only about wakes and triggers.

**What cutting the verification reads would cost:** the worker skills' read-backs are what establish posting identity, and this run consumes the result. A write that went unread comes back `unestablished`, and an unestablished comment-kind entry is a later review trigger this run has no observed author for — so a ban written broadly enough to catch those reads breaks the trigger rule two sections away, silently. The first draft of the ban was written that broadly; review caught it against the worker contracts, which require exactly those reads.

**Why the worker skills cannot carry this alone:** `implement-issue-core` and `repair-pr` forbid delegating a wait as well as performing one, but their earlier wording — bounding duration alone — is what a worker met and satisfied while still leaving a watcher armed, because arming a wake is not entering a loop. That reading is available again to any worker weighing a skill rule against a session instruction, and the skill rule is the weaker of the two on its own.

**The two costs of a worker-armed watcher, and the one observed:** a second watcher duplicates supervision the parent already owns and can act on a PR the parent is mid-repair on. And a worker that arms a wake it is not permitted to disarm — the trigger tools are routinely outside a worker session's allowlist — blocks on a permission prompt with nobody watching, holding a container for hours after its own work merged. The implementation succeeded; the deadlock was entirely in the cleanup.

**The $33.45 and $59.60 sessions — why the risk ordering was corrected:** an earlier version of this section treated the worker that *can* disarm its own wake as the benign branch, because it leaves nothing blocked behind. Two leaked sessions proved the opposite: each woke hourly, re-read a merged PR, found nothing, re-armed, and billed $33.45 and $59.60 respectively before the user found them in a session list. The disarming worker is the expensive branch precisely because it is unblocked — no handler ever sees it. The countermand was present in both placements on both runs and did not hold, which is why the section now points at the reconciliation step rather than at stronger wording.

## How a worker's report actually reaches you

**Where the gap is worst:** a terminal outcome short of `PR_OPEN` usually arrives **before any PR exists** — no PR body, no review thread, no commit message — so the dependency correction that stopped the worker exists only in a transcript nobody will open. A parent pulling the usual sources finds nothing unusual and concludes the worker had nothing to say. Successful runs leak less but still leak: graph corrections and caveats that are not coverage findings have no place they are guaranteed to be written.

**What "persist the run state" would cost instead:** the session record already carries most of the run state for free, written by the runtime. A requirement phrased that broadly writes down a great deal that was already free, into a place that then has to be defended against every reader of it. Scoping the written report to judgment alone is what keeps the sink small and inert.

## Releasing a worker

**The 2026-09-23 ruling, and the incident that forced it.** A run on the remote-session tier dispatched separate implementation, review and repair sessions and never archived a finished one: fourteen were left alive until the owner asked. Two causes. Release was never part of the prompt the run wrote for its own check-in, so it lived in the run's memory and was dropped once the dispatch pattern changed mid-run. And the rule itself — where the worktree cannot be reached, not releasable, raise `NEEDS_USER`, keep the container — fires on *every* worker on that tier, because there the worktree is never reachable. Read literally it yields a `NEEDS_USER` per worker; in practice it yields silent retention; both leak containers. The owner's ruling, confirmed in the session that implemented it:

> Archive a finished session once its PR looks OK: the PR head matches what the worker reported pushing (and for review/repair sessions, their comment/push landed). Do not retain finished sessions for the unreachable-worktree reason.

with one refinement the owner chose: **a mismatch keeps the container and raises `NEEDS_USER`**, because that is the one case where work may really be stranded.

**Why the fail-safe was given up rather than repaired.** Every incident this file records on the subject is a leak — fifteen sessions and one session after their work merged, two billed $33.45 and $59.60 waking hourly on merged PRs, the originating session merged hours before it was found, and now fourteen. **None is lost work.** The fail-safe guarded a hypothetical at the price of a failure that recurred at least five times with a bill attached, and a fail-safe that fires on every case is not one. The residual it accepts is edits made after a worker's last reported push — bounded by the last-checkpoint promise, and near nil once each session has one deliverable and the PR belongs to the run after it.

**Why reachability and not branch existence (correction, Sept 2026):** the canonical example this section and several others were built around was wrong. A session sat `IDLE` for four weeks reporting staged files with no branch on the remote, and was reported — here, in six places — as four weeks of unpushed work. Its PR had merged the day it was created and the forge had deleted the branch, as forges do. The criterion inherited the error: a branch-exists test reads every merged-and-deleted branch as stranded, which on a busy repository is most of them, and would have sent a run chasing captures of work already on the default branch. Reachable is therefore defined on the worker's commit, not on any branch: an ancestor of a remote branch's head or of the default branch, or the head of a merged PR — the last because a squash merge puts the work on the default branch under commits the worker never made. The session is kept as evidence because what it actually showed is worse than stranded work — a finished worker that had grown into an unsupervised orchestrator, pointed at a pre-migration organisation, with the owner believing it was live. The lesson about the example is the one this document keeps writing down: a motivating case recalled rather than re-read is a claim, and this one was repeated six times before anyone checked it.

**Why the ask does not satisfy condition 2 (round 1, Sept 2026; superseded as a release rule by the 2026-09-23 ruling above, and kept as the mismatch remedy):** the first version made the branch existing the success criterion, which is the cheap half of exactly the rule it cites — a stale branch from an earlier push passes instantly, and a plain push can create a branch from an already-committed head while the staged edits stay in the container. Checking the head moved fixes that. What it does not fix is completeness: the parent cannot see the worktree, so "everything is committed" is another claim with no carrier, and the worker is still not releasable. The lever is worth having anyway because it moves the captured work from zero to most of it, but it had to stop claiming to close the gap.

**Why the push ask is verified against the remote and not against the reply (Sept 2026):** a worker's "pushed" is an assertion about state, in the class the settles-column rule already covers — the same shape as a `fixed in <sha>` naming no reachable commit. The verification is one read of the remote and it is the difference between capturing work and archiving it. (The session first cited here as four weeks of unpushed work was not: its PR had merged and the forge had deleted the branch. See *Releasing a worker* for what that session did show, and for why reachability rather than branch existence is the test.) The ask itself sits before archival rather than after, because archival destroys the only copy.

**Why the lever is conditioned on the caller-side channel:** asking requires sending. Where this session cannot address that worker, there is nothing to ask and no reply to wait for — and the run has to say that, because an absent reply is otherwise read as an absent problem.

**Why the remote-session row needed writing down:** on two of the four tiers release *is* the absence of an action, so a reader generalizing from those reads "release the worker" as a remark about attention rather than an instruction — and on the tier a degraded run most often lands on, the same words name a real resource that then leaks silently. Nine finished worker sessions still holding containers after a run, found by the user in a session list rather than by the run in its own report, is what that reads like from outside.

**Why condition 2 is three positive clauses and not an outcome table (round 2 of the ruling's review):** the first version keyed a seven-row table on what the worker returned. That enumeration missed the dominant leak shape outright — an idle finished worker on a merged PR, not on a prompt, whose return never reached the parent — released a no-branch `NEEDS_USER` whose push had failed with staged edits in the container, and gave a no-code repair two rows with different answers. The input was also unreadable: on the remote tier a structured return lands in a transcript the parent never reads, so *reported* has to mean the report on the PR, which is why that report now names the pushed head. Stated positively — delivered, finished, or never started — each case lands in exactly one place, and whatever lands in none is the mismatch. Round 3 of that review tightened the first clause twice, both times for the same reason — one shared identity and an honest report can each vouch for work that is not on the remote: a report counts only when it carries the session's own footer, since an implementation worker's report on the same PR otherwise stands in for a repair session that wrote none; and a head the worker *found* counts only for `NO_CODE_CHANGE`, since "pushed nothing" after a rejected push is true and leaves the fix in the container. It also read an early stop's return off the session record, because a stop before any PR exists writes no report and would otherwise never be done — and off the record rather than off `IDLE`, since a worker between turns waiting on a subagent is also idle and would otherwise be archived mid-issue.

**Why the releasable test is stated once:** restating it in situ is how successive versions of it came to disagree about the same worker — every review round the section has had found one such disagreement, each introduced by the fix for the last. That includes the copy that required a PR still be open, which excluded precisely the merged-PR deadlock the test exists for.

**The incident behind "merged is the common case":** a wake armed at PR creation outlives the PR that armed it, so by the time anyone notices the blocked session the work has usually landed. The session that prompted the whole rule had merged hours before it was found.

**The two later runs (2026-08-28/29), and why the fix is verification, not wording:** two orchestrator runs in different repositories leaked worker sessions after their work had merged — one leaked 15, one leaked 1 — and they failed in *different places*. The first never reached the release step. The second ran it: it read the worker's outcome, checked the worktree, wrote "repair worker archived" into its own supervision notes, and never called the archive tool. Both failures are invisible to any rule stated more forcefully, and both are caught by the same check: compare what the runtime says is alive against what the run tracks, every cycle. Reporting an action is not performing it, and the run's own memory is not evidence about the runtime — invariant 1 applied to the run's own workers.

**Trigger deletion defeated:** during recovery, deleting a leaked session's scheduled trigger caused the session to arm a replacement one minute later. The session arms the wake, so only archiving the session stops it. This cost a recovery cycle to discover.

## Blocked workers

**The checkpoint consequence, and why it was missed twice (Codex round three on the same PR):** promoting the missing channel to tier level contradicted two rules that had been written on the opposite assumption — *Checkpoint compliance*'s nudge-then-capture escalation, and *Where the parent cannot reach*, which listed remote sessions among the tiers where sending an instruction works. The failure direction was the costly one: a run spending a nudge that cannot land, then waiting a full cycle to conclude the instruction did not land, with the only copy of the work in an ephemeral container for the duration. The fix splits *Where the parent cannot reach* into the three cases its own premise implies — the premise is a conjunction (*see* the checkout and *instruct* the worker) and the two capabilities come apart, which is what collapsed them into two cases in the first place. What generalizes: a limitation stated only where it was observed leaves every rule written on its negation standing, and those rules do not announce themselves — this one was two sections away and phrased as a reassurance.

**Why step 3 states the reachability branch first rather than as an exception (round eleven; the retired carve-out below is superseded by the 2026-09-23 ruling, under which case 1 does release a blocked worker whose PR merged, on either tier):** the step opened with two absolutes — do not resolve this one as `NEEDS_USER` and leave it; recover the slot instead — and then, four sentences later, the unreachable branch required exactly that: `NEEDS_USER`, container retained, do not archive. Both imperatives applied to the same worker, and the second read as a violation of the first. The cause is the same shape as rounds nine and ten: a rule written before a capability split, kept as the general case afterwards, with the new case bolted on where the reader meets it last. The fix is not a softer sentence but an ordering — settle reachability, then branch, so neither path is the exception to the other. Also retired here: an "exception" for a worker that passes the releasable test at case 1, which at the time could not exist on the unreachable tier, because an unreachable worktree then left that test's second condition unsatisfiable. (Historical: since the 2026-09-23 ruling the remote state stands in for that worktree, and case 1 releases such workers on either tier.)

**Why `NEEDS_USER` with a retained container is not the "still waiting" the section forbids (since the 2026-09-23 ruling, only a mismatch reaches this):** that last rule is about visibility and scheduling, not about who is holding a container — a blocked worker must not sit through a run unnamed, and the run must not schedule against capacity that is in use. A reported `NEEDS_USER` satisfies both: the session is named with its head and its question, the held slot is counted as held, and the cost is reported as the price of work that may be stranded rather than absorbed. Reading that rule as a ban on `NEEDS_USER` is what produced the contradiction above; it bans silence.

**Why the repeated nudge got a cadence (round eleven):** the channel-without-path branch said to nudge "repeatedly, because repeating is all that is available" and named no interval, while the supervision loop explicitly has none — sibling completions and PR events drive cycles back to back. So the branch as written authorized a burst of identical reminders to a worker three minutes into reading the code, which is the failure the elapsed-time thresholds were introduced to avoid one section earlier. Tying repetition to those same observations costs nothing new: the clock, the two-observation floor and the escalation it feeds already exist. The acknowledgement question answers itself on this tier — no reply is readable, so the only acknowledgement is an advancing head, which clears the state outright; and the parent must not let its own repetition reset or defer the escalation, since nudges here are unacknowledged by construction.

**The #59 answer, and why it moved the tier:** the question was whether the parent can reach a remote worker's checkout at all. It is answerable without spending a worker, from three facts: a session record's `sources` carries the repository it was given and no filesystem path; each session runs in its own container (`environment_kind`); and no tool in the runtime's surface reads another session's disk, executes in it, or reads its transcript. So the *see* half was never available on that tier, and *Checkpoint compliance* — the mechanism the document leans on hardest for invariant 5 — has never applied to the tier a degraded run most often lands on. Step 11's "cannot be inspected from here" hedge was the accurate rule all along; everything written as though capture were available was the drift.

**What that costs, stated rather than smoothed over:** invariant 5 on that tier rests on the worker's own pushes, and the parent's only levers are the dispatch prompt and an observable remote head. The workflow tier at least admits a structural substitute — stages the script pushes between — and a remote worker session admits none, because nothing in the parent's reach interposes on it. The temptation is to keep the capture language and treat the tier as an exception; the honest version is that the guarantee is weaker there and the run says which enforcement it is relying on.

**And the two capabilities are now detected, not assumed:** `sources` carrying no path answers the checkout question, and `external_metadata.cross_session_inbound` answers the channel question — cheaper and more truthful than sending a message and watching for nothing to happen, which was the previous prescription. Both go on the run's state, because a run that never established them does not know its own invariant 5 story. A self-hosted pool may share a filesystem, which is why these are detections and not rules.

**Why the checkout detection is one-directional (review finding):** the first version read as a two-way test with a shared-filesystem escape hatch — "a self-hosted pool may share a filesystem, that is why this is a detection and not a rule" — and never said how such a run would *enter* the reachable branch. It cannot: `sources` supplies no path in any configuration, and `environment_kind` reports separate containers, which is not the same fact. So the detection proves one direction only, and an absent path defaults to unreachable. A pool that really does mount worker files where the parent can see them is then misclassified, and pays for it by retaining sessions it could have released — the conservative error, chosen deliberately. Since the 2026-09-23 ruling its cost is smaller than it was: an unreachable run releases on remote state too, and what the misclassification loses is the parent-side capture a reachable run has in place of asking the worker to push. If that configuration matters, what it needs is a way to supply a path, which is a capability this contract does not have rather than a branch it forgot to write.

**The release path on an unreachable tier was a stated gap until the 2026-09-23 ruling closed it (below); the five review rounds that established the gap are kept because they say why the ruling reads the remote and not the worker's claim:** (1) scoping *Checkpoint compliance* away left condition 2 unsatisfiable, so nothing on the tier was releasable; (2) "terminal outcome plus durable remote state" fixed `PR_OPEN` and left every pre-PR terminal outcome unreleasable, because durable remote state is defined as requiring a PR; (3) letting condition 1 carry condition 2 fixed that and licensed archiving a worker stopped **mid-edit** — *stopped* and *nothing uncommitted* are different facts, and the worker contracts promise only bounded loss or a push on successful code-changing repairs; (4) requiring an explicit cleanliness assertion fixed that, and the assertion turned out to have **no carrier** — a remote return value is unreadable by the parent and a worker stopping before a PR writes nothing; (5) and the path could not execute anyway, because step 11's archive ban is unconditional on unreachable worktrees, while repair dispatches never asked for the assertion at all.

So the contract stated the gap and failed safe: not releasable, `NEEDS_USER`, container held. The mechanism — a parent-readable carrier, a narrowed step 11, the assertion required of every dispatch and present in the worker Output contracts — was to be its own change. **It is superseded by the owner's ruling of 2026-09-23 (*Releasing a worker*, above), which is not a sixth attempt at the same mechanism.** Rounds 3 and 4 failed trying to make the *worker's* claim of cleanliness count, and that claim has no carrier. The ruling reads something the parent can observe — the remote head against the commit the worker reported — and accepts, by name, the one thing that observation cannot see. Point (3)'s mid-edit case stays excluded: a worker stopped mid-deliverable has no terminal outcome and no reported final push to match, so it never reaches the ruling and keeps its container under *Blocked workers*.

**The generalisable lesson, which is why the sequence is recorded rather than just the outcome:** every one of the first three attempts was **more specific than its evidence**. On a release path extra specificity does not add safety, it subtracts reachable cases — and the case it subtracts is usually the common one. The question to ask when patching a gate is not "does my case pass" but **"which cases can now never pass"**. The later rounds add a second: an assertion is worthless until you have named the channel that carries it.

**How #59 came to be asked:** the channel fix made an old assumption load-bearing where it had been incidental — "the parent captures on first observation" needs the *see* half — and supervision-loop step 11 had been routing a worker "whose worktree cannot be inspected from here" to `NEEDS_USER` all along, which read against the same section's premise for that tier. It was filed rather than answered inline because a `source_url` PR was the wrong place to move a tier. The answer, and what it moved, is above.

**Why the field is half the channel (Sept 2026):** the round-twelve reasoning below is right about what it was answering and was read as settling more than it does. The field reports the target's willingness to receive; the ability to send is the caller's own toolset, and an observed orphan read exactly `available` while the caller held no send tool, resolved no peers, and got no-such-agent from every attempt. The two are independent, so the field is necessary and never sufficient, and the caller's half is established from the caller's side. The consequence that matters is not tidiness: with no send channel the capture lever does not exist, and a run that reads `available` and stops there records a worker as fine whatever is sitting in its reclaimable container.

**Why the field decides the channel and an observed landing no longer gates it (round twelve):** the default this section first shipped — *absent until a message is observed to land* — was written before `cross_session_inbound` existed as the detection, and survived the round that introduced it. The two then said incompatible things about the same worker: the startup rule called the field a cheaper answer than probing, while this section made no field reading sufficient, so the detection could never establish presence and was decorative. It also split the verdict — the checkpoint escalation branches on the recorded capability, so it would nudge the very worker the blocked path had written off. What resolves it is not declaring the field authoritative, which it is not: it reports a *session's* inbound availability, not this parent's ability to address that session, so it can be right about the runtime and wrong about the pair. The field is enough to **act** on and never enough to **wait** on, and the second half is what makes the first safe — a wrongly-presumed channel now costs one composed message, because after the nudge-cadence change nothing in the document blocks on a reply. The cost the old default was buying protection from, a worker stranded behind an answer that cannot come, had already ceased to be reachable one commit earlier; I retired the cost and left the protection standing. A negative observation still wins, and now for a stated reason rather than by default: a send that errors is direct evidence about this parent and this worker, which the field is not.

**The field's value form is part of the rule, not trivia:** it is observed as the string `available`, not a boolean. A truthiness test passes on any non-empty string and fails silently on an absent field, so the contract names the value to compare against. Round twelve's finding was phrased in terms of the field being *true*, which is the reading the text invited.

**Why the channel claim is an observation rather than a rule:** the first draft asserted that no message channel reaches a remote worker session, full stop. That is what was seen, on one runtime, twice — but the tool surface varies by environment, and a session's own listing of reachable agents is exactly the kind of thing that differs between a managed cloud runtime and a local one. Asserting the universal also put the paragraph at odds with its own next sentence, which told the reader to establish the fact per runtime: if it were a rule there would be nothing to establish. So the claim is scoped to the runtime it was observed on, and the unknown case is decided by the recorded capability rather than by an assumption in either direction (see the entry below, which retired this rule's first default).

**The observed incident:** a worker sat blocked for six hours on a prompt to delete a trigger, its PR long since merged, before a human found it in a session list. Its status field read a plain `IDLE` while a separate derived-state field read `BLOCKED`, with the pending tool named only in a third — the disagreement the read-the-right-field rule exists for.

**Why the missing message channel is stated at tier level and not only inside the `AskUserQuestion` branch:** it was first written down as a property of being mid-prompt, which is where it was observed — and read that way it leaves step 2 looking available on the remote tier, so a parent holding a block it could genuinely clear with an instruction composes one and then finds there is nowhere to send it. `SendMessage` does not address remote CCR worker sessions in any state. `interrupt_session` does reach them, which is what makes the limitation easy to miss: something works, it just does not answer the question the worker stopped on. Every recovery on that tier is therefore archive-and-redispatch rather than redirect, and knowing that before a worker blocks is worth a cycle.

## Concurrency: a ceiling, and the caller sets it

**Why there is a default at all (#123):** every caller set its own cap — `backlog-orchestrator`'s `concurrent-workers`, the npm orchestrator's begin-narrow rule — so the skill itself had none, and invoked directly, thirty tasks meant thirty workers. The one full-width dispatch on record is the npm orchestrator's: a batch dispatched at full width exhausted one machine's memory and killed a quarter of the run. **Why 4:** it is the only number a caller had already settled on and run under (`backlog-orchestrator`'s built-in `concurrent-workers`), so making it the default changes nothing for that caller and bounds the standalone case at a width that is known to work. The ceiling-not-target rule and the ban on widening because a runtime can moved here with it from that skill's *Default usage safeguards*, which kept only the budget list and its own override.

## Checkpoint compliance

**Where the reasoning for this section lives.** The stalled-head thresholds — 30 minutes reported, two hours `NEEDS_USER`, measured in elapsed time rather than in cycles — were introduced alongside the decision not to reorder the runtime preference, and that reasoning is recorded with the decision: `backlog-orchestrator` NOTES, *Runtime selection*. The nudge cadence for a channel with no path, and why an advancing head is the only acknowledgement, are under *Blocked workers* above, where the review round that produced them recorded them. The capture itself stayed in `backlog-orchestrator`, and so did its defect history (`backlog-orchestrator` NOTES, *Checkpoint compliance*).
