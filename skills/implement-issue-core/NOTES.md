# implement-issue-core — design notes

Companion to `SKILL.md`. That file is the contract; this one holds the reasoning, incident history, and answers to "why not the obvious other reading?" — organized by the contract's section names. Read a section's note before changing its rules, or when applying them to a case the contract doesn't obviously cover. Nothing here overrides the contract.

## Hard constraints

**Why "never delegate a wait" is stated separately from "never wait":** a scheduled check-in, a trigger or routine, or a PR-activity subscription is monitoring *arranged* rather than performed, and it outlives this invocation exactly as a loop would. An earlier wording that bounded duration alone was met and satisfied by a worker that still left a watcher armed — arming a wake is not entering a loop — and the worker often lacks permission to disarm what it armed, which is how a finished worker ends up blocked on a permission prompt for hours after its own PR merged. The caller supervises the PR, whichever caller it is.

## Step 2 — dependency precondition

**Why the check runs even when a caller judged the issue READY:** that judgement was computed from a dependency read that can be wrong in a way it cannot detect — a scoped or relayed credential returns a partial list with a success status and no warning — and this worker, already reading both prose and native metadata for one issue, is the cheapest detector in the system for that blind spot.

**Why three sources, and why never one alone:** they fail in different directions. Prose goes stale the moment someone edits a ticket without updating it. Native metadata can be silently truncated by a scoped credential — and **a partial list is more dangerous than an empty one**, because it presents as a complete answer: one blocker returned where four exist reads as "nearly ready" and suppresses exactly the doubt that would have sent you looking elsewhere. Individually each source has a failure mode that resembles success; together they are hard to fool.

**Why worker-report comments contribute no edge:** a comment opening with the exact line `**Worker report — unclassified evidence, not a dependency record.**` is a previous worker's report, left on the issue by older tooling because its runtime gave its return value nowhere to go. It records what that worker *observed*, before anyone judged whether the relationship was real or stale — reading it as prose that names a dependency would let an edge the caller already rejected block this issue again, on every later dispatch. Nothing is lost by excluding it: an edge it mentions was observed in the issue's own prose, which this step reads anyway; what the report adds beyond that — a classification — it is precisely not entitled to add.

**Why you probe your own transport instead of adopting the caller's classification:** the same tracker answers differently in two containers — on GitHub the MCP server exposes no blocked-by read (feature-flagged, [github/github-mcp-server#3145](https://github.com/github/github-mcp-server/issues/3145)) while an authenticated `gh issue view --json blockedBy,blocking` does — and an orchestrated worker very often *is* a different container from its caller. Expect the environment's profile (cloud worker: MCP present, `gh` absent; local run: authenticated `gh`, no MCP), confirm rather than assume, and treat a result contradicting the expectation as a finding about the environment.

**Why the two divergence directions get different handling:** finding *more* than the caller makes you the better-sighted party — use the read and report; the result you return is stronger than expected. Finding *less* means you cannot perform the re-read the caller relies on you for: a blocker added between its preflight and your dispatch is invisible to both of you, and the caller's earlier context would otherwise keep backing your completeness claim as though nothing had changed. Only saying so explicitly lets the caller know a contemporaneous read on its side is required before your result can be merged as equivalent to a sibling whose worker could re-read.

**Why a raw `curl` fallback never stands in for a missing dependency read:** it drops cross-repository edges silently (see `validate-backlog`, *GitHub dependency reads depend on where you are running*) — the honest state is "this source is absent", not a read that quietly returns part of the graph.

**Why completeness needs backing separate from resolving every entry:** resolving every blocker you found says nothing about whether you found them all, and readiness depends on completeness. Three sources are hard to fool only while they carry information: where prose names nothing and no caller context arrived, the union collapses to a single native read — the sources agree because two are silent, not because they corroborate. And a union with entries in it is not the safe case, per the partial-list rule above: finding a blocker is not backing.

**Why the known-true case must be observed through the same transport and credential:** having a confirmed edge available proves nothing; the observation is the proof, and only a read through the same path the dependency read used can vouch for that path. If the control does not come back, you have found the blind spot rather than ruled it out. Nothing weaker establishes visibility — not a second read, not another transport or credential — for the reasons `backlog-orchestrator`'s proof rules give at length: every proxy can coincide with the blind spot it stands in for.

**Why the `dependency transport unavailable` carve-out is keyed on *your* failed probe, not the caller's:** where neither container has a dependency read, there is no mismatch to report — the caller did not skip a proof it owed, it recorded a proof that cannot be obtained, and returning `NEEDS_USER` would refuse every issue on that tracker forever while telling the caller something it told you. But where you *did* find a read the caller lacked, it is an ordinary read subject to the ordinary requirement, and it can perfectly well have unproven visibility of its own — finding a read improves your evidence; it does not exempt you from proving what that read can see. The caller's blindness is not a reason to trust yours.

**Why a direct invocation proceeds on an unproven view:** refusing every issue whose dependency view cannot be proven would refuse nearly all of them — the same error as gating on issue state — and the invocation is the authority. What the report must not do is let the PR make the stronger claim: *no blocker was visible*, not *none exists*.

**Why availability is gated by class, not by issue state:** an open blocker does not mean the work is unavailable — a stacked child is dispatched precisely while its parent is implemented but unmerged; that is the normal case, and gating on "the blocker is still open" would refuse nearly every stacked child, worse than no gate at all. Git reachability is the right measure only where this issue builds on the dependency's code; an execution-only ordering, a cross-repo scheduler dependency, or an external prerequisite is *never* reachable from this checkout — not even when entirely finished — so testing those by reachability would misreport a completed cross-repo dependency as a wrong base. The split inside shared-parent fanout is the point: what decides the measure is whether the dependency's code is in your base, not what the edge is called.

**Why an unobservable measure is `NEEDS_USER` rather than `BLOCKED` or proceeding:** treating it as unmet blocks finished work and sends the caller hunting a dependency gap that may not exist; treating it as met is the failure the whole gate exists to prevent. A person can check a deploy dashboard in seconds — the value is asking rather than guessing in either direction. Caller-supplied context is the authority for measures you cannot see, because the caller is claiming something it can verify and you cannot.

**Why `BLOCKED_EXTERNAL` requires *every* unmet blocker outside the authorized set, and why membership comes only from the caller:** membership decides the outcome; class decides only the availability measure — conflating them leaves a same-repo code dependency pointing at an unauthorized issue with no outcome at all. The caller routes the two differently, and only one of them means its readiness computation was wrong: reporting a known external wait as a graph error sends the caller off re-deriving a frontier that was correct. "Outside the authorized set" is a fact about the caller's run, not about the issue — never inferrable from the blocker living in another repository or another team's tracker, which is just what "external" looks like from here whether or not it is in scope. Absent membership data, `BLOCKED` is the safe default: an authorized-but-external-looking prerequisite reported as an out-of-scope wait would make the caller skip the frontier re-derivation an in-scope blocker requires.

**Why mixed blockers rank the way they do:** one outcome cannot describe several states, so rank by what the caller loses if that outcome is the one it sees. A graph correction (`BLOCKED`) is the only response another outcome would suppress — the caller reads `NEEDS_USER` and `BLOCKED_EXTERNAL` as *not* graph errors and may skip re-deriving its frontier. The unproven-view `NEEDS_USER` outranks what follows because its consequence is not confined to this issue: every sibling judged READY through that read shares the blind spot; it also forbids the weaker conclusions — "just a known external wait" is not available from a set you cannot trust to be complete. The reverse precedence would let a single external prerequisite mask an in-scope dependency the caller's graph got wrong. The exception inside the ranking — where your own probe also found no dependency read, unproven completeness ranks nothing — exists because a ranking is applied mechanically: without it, every orchestrated issue on such a tracker refuses implementation, a permanent dispatch deadlock arriving through the one rule nobody re-reads.

**Why everything is reported regardless of which outcome won:** the ranking exists because a single value cannot carry three states, not because the others stopped mattering — an unverifiable prerequisite reported under a `BLOCKED` still needs its question asked. The invalidation asymmetry: where neither probe found a read, unproven completeness invalidates nothing (there was no proof to spend — it restates the run's own condition); where *you* found a read and could not prove its reach, it is a truncated read like any other and does invalidate. Getting that backwards would halt sibling dispatch on every `PR_OPEN` the run produces.

**Why observation beats a "satisfied" assertion but not an "unmet" one:** deferring to a wrong "satisfied" would disable this reconciliation exactly when the caller chose the wrong base, trading a restack the caller could act on for an implementation built without its dependency — but the class qualifier is load-bearing: unreachability is only contrary evidence for a code dependency; overriding on it for an execution-only or cross-repo edge blocks a prerequisite that is complete. The inverse does not flip because the two observations are about different things: unavailability refutes "satisfied", while availability is a fact about *presence*, and "unmet" may be a claim about *soundness* — a merge pending revert, a known-bad implementation, a semantic incompatibility invisible from the code being there. The cost asymmetry agrees: a needless block costs a cycle; building against something the caller knows is unsound costs a wrong PR and everything stacked on it.

**Why "never implement against a contract that does not exist yet":** the behavioural catch in step 1 — blocking when required work is absent — only fires when the absence breaks the code. A UI ticket whose backend is missing will render against the parts that exist, stub the rest, pass its mocked tests, and produce a PR that looks complete and is not.

## Steps 3–5 — durable branch state and checkpoints

**Why commit-before-check:** checks take minutes, and those minutes are exactly when an ephemeral container is most likely to disappear — running a full suite over uncommitted work is the single most expensive habit available here. A commit is a save, not a claim of correctness: green is not a precondition, and neither is coherence — a checkpoint that exists and is imperfect always beats a perfect one that was never made. WIP history is fine; squash-merge removes it.

**Why the parent is expected to commit on your behalf:** observed across runs, workers reliably hold completed work uncommitted despite instructions, so the orchestrator inspects worktrees and captures. Holding a change until it is tidy does not keep it tidy — it hands the commit to something with less context about what you were doing.

## Step 6 — create and verify PR

**Why a coverage finding must be passed to `create-pr` explicitly:** `create-pr` decides the linkage form from it and cannot decide correctly unseen — the default is a closing keyword, so silence auto-closes an issue you knowingly did not finish, and the tracker then reads complete over work that was never done.

**Why the posting-identity map is passed whole, and why omitting it is not a smaller version of passing it:** an invocation is read literally, exactly as a dispatch prompt is — a map left out is a map `create-pr` does not have, whatever the caller sent here. And `create-pr`'s writes need *different* entries from it: an agent-authored entry for the PR itself, an invoking-user entry for the author-sensitive review trigger. Omitting it degrades PR creation and marks an otherwise valid trigger path unavailable, and `create-pr` cannot recover what it was not passed.

## Output

**Why the completeness line is load-bearing:** a `PR_OPEN` carrying an unproven absence is making a narrower claim than it looks like it is making, and this line is the only place the distinction survives — a fully-checked empty blocker list and an empty list because nothing was visible are different claims that look identical.

**Why the credential identity (non-secret) is returned:** a caller comparing it against its own is what turns a caller/native mismatch into a cross-credential demonstration rather than a coincidence, and it cannot make that comparison if you do not say.

**Why the disagreement taxonomy is strict about who can contribute an absence:** *a source's properties are declared, not inferred, and an undeclared property is assumed absent.* Native metadata claims exhaustiveness — it is the structured edge set — so an edge missing from it is a real signal, but only where a native edge set exists at all: where the probed transport returns none, there is nothing to be missing from, and the prose-vs-native test would otherwise fire on every prose-named blocker in the tree, manufacturing false visibility disagreements at scale, invalidating the caller's proof and halting sibling dispatch over a read that never happened. Caller context claims exhaustiveness only when marked as the complete READY set — unmarked, it is a targeted answer (also how a user answers one previously unverifiable prerequisite), and treating it as exhaustive would report every unrelated native edge as a disagreement and tell the user their view was partial when they had answered a narrow question. An edge the caller marked as recorded *outside* native metadata is one your native read is supposed to lack — its absence is not a disagreement about anything. Prose claims nothing: it mentions edges, never purports to list them all, so native-has-it-prose-lacks-it is the ordinary case, not a finding.

**Why "no longer holds" rather than "was wrong" for availability mismatches:** the claim may have been true when made and overtaken since — a revert landed, a branch was force-pushed, a release rolled back. The caller cannot tell those apart from its own error; report what you observed and when, and leave the diagnosis to the side that knows what it claimed. Direction matters because the resolutions differ — a stale base needs fixing; an obsolete constraint needs retiring — and a caller that cannot tell which way the mismatch went cannot act on either. Never collapse the two kinds into one label: a caller that cannot tell them apart must treat a stale base as a possible transport failure, a far more expensive response than the situation needs.

**Why the `NEEDS_USER` kind is stated rather than inferred:** the two kinds demand opposite things of a caller — a question to put to a person versus transport evidence that invalidates a visibility proof and holds every sibling dispatched through the same read — and leaving the caller to infer the kind from whether the blocker list is empty is how the expensive one gets handled as the cheap one.
